# Proposals

A change to VibeLang is decided as a VibeLang improvement proposal (VIP). The [VIP index](/vips/) lists every proposal and its status; an open VIP is not part of the language.

VibeLang had an earlier design, documented on this site until October 2026, that kept functions eager and returned failures as `Result` values instead of building on Effect. This page records where each feature of that design stands today in 0.0.14. A feature with no VIP is only an idea: to pursue one, propose it as a VIP.

## Implemented (opt-in) in 0.0.14

These accepted VIPs are implemented in 0.0.14 behind `"vibe": { "experimental": ["builtins"] }` in `tsconfig.json` or `vibe.config.json` (see the [release feature status](/setup/alpha)).

### Durable execution

A workflow that journals each completed step, so a restart resumes the run instead of repeating finished work. [VIP-55](/vips/0055-durable-tasks-workflows) (`task` and `workflow` declarations), [VIP-56](/vips/0056-durable-waits) (durable timers, signals, human waits, workflow deadlines, and recorded `try.race`/`try.any` outcomes), and [VIP-60](/vips/0060-std-durable) (`Experimental.Durable`) are accepted and **implemented (opt-in) in 0.0.14**, described on [Tasks and workflows](/vibelang-features/119-tasks-and-workflows). [VIP-44](/vips/0044-durable-values) is accepted with its schema mapping supported via VIP-15. Effect's `effect/workflow` modules (`Workflow`, `Activity`, `DurableClock`, `DurableDeferred`, `DurableQueue`) also work from `.vibe` files.

### Coding-agent library

A library for agents that write and run code on each turn in a sandbox with no ambient authority. [VIP-62](/vips/0062-std-model) (`Experimental.Model`), [VIP-63](/vips/0063-std-agent) (`Experimental.Agent`), [VIP-64](/vips/0064-std-tools) (`Experimental.Tools`), and [VIP-65](/vips/0065-std-mcp) (`Experimental.McpClient`) are accepted as standard-library modules (no compiler changes) and implemented (opt-in) in 0.0.14. See the [release feature status](/setup/alpha). Effect's AI modules also call models and tools from `.vibe` files.

### Typed workers

Calls across a worker boundary that keep their success and failure types, with derived transport codecs. [VIP-57](/vips/0057-workers-remote) (`schema service`, `with { type: "worker" }` imports, `Experimental.Rpc`, and worker entry chunks in `vibelang-vite` and `vibelang-unplugin`) is accepted and **implemented (opt-in) in 0.0.14**. Effect's worker modules also run code on worker threads.

### Capabilities and permissions

A capability-based permission kernel guarding platform services (`FileSystem`, `HttpClient`, `ChildProcessSpawner`) with monotonic ceilings on tasks and workflows. [VIP-58](/vips/0058-capabilities) (`Experimental.Capability`, task/workflow `tier` and `capabilities` metadata, plan inspection, and `EK5801`) is accepted and **implemented (opt-in) in 0.0.14**.

### Eval declarations

First-class evaluation suites discovered by file kind (`*.eval.vibe` / `*.eval.vibex`) and excluded from production bundles. [VIP-59](/vips/0059-eval-declarations) (`vibe eval` / `vibelang eval` with `--list`, `--live`, `--update`, and `--trials`, plus bundler import refusal) is accepted and **implemented (opt-in) in 0.0.14**.

## Proposed as VIPs

### Build-time host selection

Choosing a platform implementation at build time and dropping the others from the output. [VIP-54](/vips/0054-consistent-platform-code-open) is an open request for proposal for one consistent model of platform-specific code; it selects no model yet. Today a program provides a platform layer at run time.

## Denied proposals

### Effect handlers

Effect handlers (`control`, `handle`, `resume`, `abandon`) were **denied** on 2026-11-23 in [VIP-35](/vips/0035-handlers-open). The compiler and runtime have no handler implementation, and services, layers, and Effect cover their use cases without delimited continuations. See the [proposal status page](/vibelang-features/111-control-operations-and-handlers).

## Partly shipped

### Validators derived from types

A `schema` declaration ([VIP-15](/vips/0015-schema-declarations)) gives one source for a schema and its type. Deriving a schema from an existing TypeScript type has no VIP.

### Declarations in conditionals

`is` patterns ([VIP-7](/vips/0007-match)) bind names in an `if` or `while` condition. A general declaration in a condition, such as `if (const user = cache.get(id); user !== undefined)`, has no VIP.

## Shipped features

### JSX source files

A `.vibex` file is a `.vibe` file read the way TypeScript reads `.tsx` ([VIP-39](/vips/0039-vibex)).

### Toolchain commands

The earlier design planned one `vibe` command. In 0.0.14, `vibe` and `vibe-format` ship alongside `vibelang` and `vibelang-format`:

| Earlier command | Vibe in 0.0.14 |
| --- | --- |
| `vibe init` | `bun create vibelang my-app` or `npm create vibelang@latest my-app` |
| `vibe check` | `vibe --noEmit` (or `vibelang --noEmit`) |
| `vibe compile --declaration` | `vibe`, with `declaration` set in `tsconfig.json` |
| `vibe run` | `vibe run <file>` (or `vibelang run <file>`), shipped in 0.0.14 to execute `.vibe`, `.vibex`, and `// @vibe` entrypoints directly in Node with source maps |
| `vibe test` | Vitest with `vibelang-vite` and `@effect/vitest` (and `vibe eval` for `*.eval.vibe` suites) |
| `vibe format` | `vibe format` / `vibe-format` (dprint with the `vibelang` plugin; see [Formatting](/setup/formatting)) |
| `vibe lsp` | `vibe --lsp --stdio` (or `vibelang --lsp --stdio`) |
| `vibe inspect`, `vibe doctor` | No command; editor hovers show inferred contracts |

### Bundler plugins

`vibelang-vite` serves Vite and Vitest, and `vibelang-unplugin` serves webpack, Rspack, Rollup, Rolldown, esbuild and Bun. See [Setup](/setup).

## No VIP yet

### Compile-time evaluation

A `comptime(...)` intrinsic that ran deterministic code during compilation and failed the build if the work needed a run-time value.

### Typed asset imports

Non-code files imported as typed modules at compile time through import attributes, with no run-time filesystem dependency.

### Custom loaders

Project-registered compile-time loaders for other import types, such as YAML, SQL or GraphQL, each read file tracked as a build dependency.

### Rust and Zig source imports

A `.rs` or `.zig` file imported like a module, compiled to Wasm with generated typed bindings.

### Shared structs

Shared-memory structs over `SharedArrayBuffer`, with the compiler checking their cross-realm layout.

### Mandatory compiler options

The earlier compiler refused a project whose `tsconfig.json` left off `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `isolatedModules`, `verbatimModuleSyntax` or `useDefineForClassFields`. Today the starter sets `strict`, and the specification sets no mandatory options.

### TC39 adopt-early list

The earlier design planned to adopt Source Phase Imports, the Error Stack Accessor, Discard (`void`) Bindings, Async Iterator helpers and the Cancellation API early. VibeLang adopts a different set: throw expressions, `do` expressions, the Hack pipe operator and pattern matching.

## Sources

The earlier design is preserved in the `smithersai/vibelang` repository at two revisions:

- [`c60eca97`](https://github.com/smithersai/vibelang/tree/c60eca975b01a6778fdad81e5f54d72091481298/docs) (August 21, 2026): `Result` with `.unwrap()`, native and Wasm targets, and the first durable Plan design.
- [`ebe89a2b`](https://github.com/smithersai/vibelang/tree/ebe89a2bc72f1603059dea7b10e661bb0e5c7c49/docs) (September 10, 2026): postfix `!`, TypeScript as the only target, the bundler plugin and static keyed Plans.

The current language is defined by its [specification](/spec/) and the accepted VIPs.
