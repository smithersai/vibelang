# Proposals

A change to VibeLang is decided as a VibeLang improvement proposal (VIP). The [VIP index](/vips/) lists every proposal and its status; an open VIP is not part of the language.

VibeLang had an earlier design, documented on this site until October 2026, that kept functions eager and returned failures as `Result` values instead of building on Effect. This page records where each feature of that design stands today. A feature with no VIP is only an idea: to pursue one, propose it as a VIP.

## Proposed as VIPs

### Durable execution

A workflow that journals each completed step, so a restart resumes the run instead of repeating finished work. [VIP-55](/vips/0055-durable-tasks-workflows) proposes `task` and `workflow` declarations, [VIP-56](/vips/0056-durable-waits) durable timers and signals, [VIP-60](/vips/0060-std-durable) the `Experimental.Durable` runtime, and [VIP-44](/vips/0044-durable-values) durable values. 0.0.13 includes an experimental implementation, described on [Tasks and workflows](/vibelang-features/119-tasks-and-workflows). Effect's `effect/workflow` modules (`Workflow`, `Activity`, `DurableClock`, `DurableDeferred`, `DurableQueue`) work from `.vibe` files.

### Coding-agent library

A library for agents that write and run code on each turn in a sandbox with no ambient authority. [VIP-62](/vips/0062-std-model) proposes model calls, [VIP-63](/vips/0063-std-agent) the agent loop, [VIP-64](/vips/0064-std-tools) standard tools and [VIP-65](/vips/0065-std-mcp) MCP clients. 0.0.13 ships none of them. Effect's AI modules call models and tools from `.vibe` files.

### Typed workers

Calls across a worker boundary that keep their success and failure types, with derived transport codecs. [VIP-57](/vips/0057-workers-remote) proposes `schema service` and worker imports. 0.0.13 does not ship them. Effect's worker modules run code on worker threads.

### Build-time host selection

Choosing a platform implementation at build time and dropping the others from the output. [VIP-54](/vips/0054-consistent-platform-code-open) is an early proposal for one consistent model of platform-specific code; it selects no model yet. Today a program provides a platform layer at run time.

### Effect handlers

Effect handlers (`control`, `handle`, `resume`, `abandon`) remain an open proposal in [VIP-35](/vips/0035-handlers-open) and are not part of the first release. The compiler and runtime have no handler implementation. Use services and layers for the use cases on the [proposal status page](/vibelang-features/111-control-operations-and-handlers).

## Partly shipped

### Validators derived from types

A `schema` declaration ([VIP-15](/vips/0015-schema-declarations)) gives one source for a schema and its type. Deriving a schema from an existing TypeScript type has no VIP.

### Declarations in conditionals

`is` patterns ([VIP-7](/vips/0007-match)) bind names in an `if` or `while` condition. A general declaration in a condition, such as `if (const user = cache.get(id); user !== undefined)`, has no VIP.

## Shipped features

### JSX source files

A `.vibex` file is a `.vibe` file read the way TypeScript reads `.tsx` ([VIP-39](/vips/0039-vibex)).

### Toolchain commands

The earlier design planned one `vibe` command. Today each job has its own tool:

| Earlier command | VibeLang today |
| --- | --- |
| `vibe init` | `bun create vibelang my-app` or `npm create vibelang@latest my-app` |
| `vibe check` | `vibelang --noEmit` |
| `vibe compile --declaration` | `vibelang`, with `declaration` set in `tsconfig.json` |
| `vibe run` | The starter's `start` script, which builds and runs Node |
| `vibe test` | Vitest with `vibelang-vite` and `@effect/vitest` |
| `vibe format` | dprint with the `vibelang` plugin ([Formatting](/setup/formatting)) |
| `vibe lsp` | `vibelang --lsp --stdio` |
| `vibe inspect`, `vibe doctor` | No command; editor hovers show inferred contracts |

### Bundler plugins

`vibelang-vite` serves Vite and Vitest, and `vibelang-unplugin` serves webpack, Rspack, Rollup, Rolldown, esbuild and Bun. See [Setup](/setup).

## No VIP yet

### Compile-time evaluation

A `comptime(...)` intrinsic that ran deterministic code during compilation and failed the build if the work needed a run-time value.

### Typed asset imports

Non-code files imported as typed modules at compile time through import attributes, with no run-time filesystem dependency.

### Custom loaders

Project-registered compile-time loaders for other import types, such as YAML, SQL or GraphQL, each read file tracked as a build dependency.

### Rust and Zig source imports

A `.rs` or `.zig` file imported like a module, compiled to Wasm with generated typed bindings.

### Shared structs

Shared-memory structs over `SharedArrayBuffer`, with the compiler checking their cross-realm layout.

### Mandatory compiler options

The earlier compiler refused a project whose `tsconfig.json` left off `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `isolatedModules`, `verbatimModuleSyntax` or `useDefineForClassFields`. Today the starter sets `strict`, and the specification sets no mandatory options.

### TC39 adopt-early list

The earlier design planned to adopt Source Phase Imports, the Error Stack Accessor, Discard (`void`) Bindings, Async Iterator helpers and the Cancellation API early. VibeLang adopts a different set: throw expressions, `do` expressions, the Hack pipe operator and pattern matching.

## Sources

The earlier design is preserved in the `smithersai/vibelang` repository at two revisions:

- [`c60eca97`](https://github.com/smithersai/vibelang/tree/c60eca975b01a6778fdad81e5f54d72091481298/docs) (August 21, 2026): `Result` with `.unwrap()`, native and Wasm targets, and the first durable Plan design.
- [`ebe89a2b`](https://github.com/smithersai/vibelang/tree/ebe89a2bc72f1603059dea7b10e661bb0e5c7c49/docs) (September 10, 2026): postfix `!`, TypeScript as the only target, the bundler plugin and static keyed Plans.

The current language is defined by its [specification](/spec/) and the accepted VIPs.
