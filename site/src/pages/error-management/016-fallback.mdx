# Fallback

A fallback runs another computation after an expected failure; a catch expression or callback keeps it lazy. An arrow handler can be generic, as in `program catch <E,>(error: E) => "fallback"`; its head follows TypeScript's ordinary arrow-function syntax.


## Recovering with another computation

```vibe
error SourceOffline

effect function latestTitle(): string!SourceOffline {
  throw new SourceOffline()
}

effect function cachedTitle() {
  try Console.log("Reading saved title")
  return "Saved issue"
}

effect function title() {
  return latestTitle() catch effect () => try cachedTitle()
}
// string!!
```

```text
Reading saved title
Saved issue
```

The left operand can be a stored Effect, a property or an expression that constructs one. It is evaluated once, then its Effect runs. A written `try` inside that operand runs first in the enclosing function; only failures of the resulting Effect reach this handler.

The cache is read only if the primary computation fails. The fallback's errors become `title`'s; handling the primary doesn't handle them. A catch expression propagates defects and causes with only interruption. A typed failure beside a defect propagates as a defect, and one beside an interruption is handled.

```vibe
effect function titleInline() {
  return latestTitle() catch effect () => {
    return try cachedTitle()
  }
}
// string!!
```

```text
Reading saved title
Saved issue
```

`x catch effect () => …` runs the left-hand Effect and calls its handler only after an expected failure. The handler is always a function literal: an effect handler can name the error and run Effects before returning its value, and a plain arrow returns a success value. A `throw` in a plain handler is `EK0401`; write `catch effect` for a typed failure, or `catch effect (error) => try die(error)` for a defect. A value, a name or an `effect { … }` block after `catch` is a syntax error. An omitted `=>`, as in `program catch (error) { return 0 }`, reports `EK0509`; write `program catch (error) => { return 0 }`. Independent TypeScript errors in the recovered handler's parameters or body keep their own diagnostics.

Plain function expressions are handlers too: `latestTitle() catch function (error) { return error._tag }`. Their immediate result stays a success value, including a `Promise`, thenable or Effect; it is not awaited or run. A factory called by a plain handler runs while handling the failure, and the Effect it returns stays cold. Parentheses keep the same handler kind. A parameter annotation is an ordinary TypeScript type; it does not filter failures. A statically known `Promise` or thenable result still receives `EK0507`; run it through `promise` or `tryPromise` in an effect handler.

A native `try { … } catch { … }` inside a plain handler can catch a foreign call’s declared exceptions. Calls in a nested function or a `finally` block keep their own throwing checks. Use an `effect` handler and `try Effect.try(…)` when the call should enter the Effect error channel.

Parentheses keep an arrow as the handler: `latestTitle() catch ((error) => error._tag)` receives the failure, just as an unparenthesized arrow does. Its parameter keeps the failure type, and its body still runs only after a failure.

An `async` or generator function is not a catch handler. It receives `EK0509` without extra type errors from the generated callback's call or return type, and its parameters still take the failure's type, so an untyped parameter reports no implicit `any` error. Written return annotations and independent TypeScript errors inside the expression retain their `TS` codes. Its quick fix removes `async` or `*` only when the result is a valid plain handler. Native `await`, `for await`, `await using` and `yield`, returned `Promise` values, and incompatible written return types need an explicit rewrite; the diagnostic explains why no automatic repair is offered.

`try Effect.catch(latestTitle(), () => cachedTitle())` also works, with the same rule as source catch: it leaves a cause with a defect alone and recovers an expected failure beside an interruption, dropping the interruption. When interruption must propagate intact, match on `exit(...)`. `Effect.catchTag`, `Effect.catchIf`, and `Effect.catchFilter` also select domain failures, under Effect's own recovery policy.

## Supplying a default success

```vibe
effect function titleOrPlaceholder() {
  return latestTitle() catch () => "No title available"
}
// string!!
```

```text
No title available
```

`x catch () => value` is `yield* Effect.catch(x, () => Effect.succeed(value))`: the value is computed only after an expected failure, and every expected error of `x` is discarded. If that value may be an Effect, `EK0508` warns that it remains unrun data. To execute it, write `catch effect () => try fallback()`. A straightforward arrow has a quick fix; mixed Effect/data results need an explicit branch. `any`, `unknown` and `never` do not trigger this warning.

To keep some visible, take the failure and rethrow the rest: `latestTitle() catch effect (error) => match (error) { when SourceOffline: "No title available"; default: throw error; }`. An effect handler can run Effects that fail or need services; their errors become the expression's. `try orElseSucceed(latestTitle(), () => "No title available")` still works, with a synchronous callback.

## Typing both sides

```vibe
type Lookup = { _tag: "Found"; title: string } | { _tag: "Offline" }

effect function lookup(): Lookup!! {
  return effect {
    return { _tag: "Found" as const, title: try latestTitle() }
  } catch () => ({ _tag: "Offline" as const })
}
```

```text
{"_tag":"Offline"}
```

The return annotation checks that the successful object and the fallback both produce a `Lookup`. Each `_tag` is kept literal with `as const`. Without a return annotation, the success type is inferred from the two alternatives.

## Trying alternatives until one succeeds

```vibe
effect function bestTitle() {
  return try firstSuccessOf([
    latestTitle(),
    cachedTitle(),
    succeed("Untitled issue")
  ])
}
```

```text
Reading saved title
Saved issue
```

`firstSuccessOf` tries Effects one at a time in priority order and stops on success; if all fail with expected errors, it reports the last error. A cause without an expected failure stops the search, and so does one with a defect; an expected failure beside an interruption activates the next alternative. An empty iterable is a defect: pass at least one.

`catch` has the precedence of `??` and associates to the left. As with `??`, mixing it with `??`, `||` or `&&` needs parentheses. A handler's concise body extends as far as an arrow body does, so in `loadTitle() catch () => savedTitle || "Untitled issue"` the `||` is inside the handler. To try one more alternative after a fallback fails, nest it in an effect handler, which recovers it in turn: `latestTitle() catch effect () => cachedTitle() catch () => "Untitled issue"`.

Mixing `catch` with `??`, `||` or `&&` without parentheses reports `EK0512`. Write `(saved ?? loadTitle()) catch () => "Untitled issue"` to catch the selected operand, or `saved ?? (loadTitle() catch () => "Untitled issue")` to catch only the load. A call, member access or index cannot attach to a closed handler: parenthesize the complete catch expression before using its result. `vibelang --fix` groups an existing mixed operand and writes a function literal around an existing value fallback, preserving the earlier parse.

A catch expression can try the cache before applying a default: `effect { return latestTitle() catch effect () => try cachedTitle() } catch () => "Untitled issue"`. The cache runs after the primary fails, and the title is used after the cache fails. Each recovery uses Effect's cause policy.

The `EK0509` quick fix for a callable value such as `x catch onErr` writes a function literal and chooses a parameter name that does not shadow a name visible to the handler. Escaped identifier spellings and comments do not change that choice. 

A handler written as a parameter list followed directly by a block, `x catch (e) { … }`, is missing its `=>`. It reports the `EK0509` syntax diagnostic while retaining the file's independent errors. The quick fix writes `x catch effect (e) => { … }` when the block has no `break`, `continue`, `await` or `yield` of its own; write `x catch (e) => { … }` instead for a plain fallback. Comments and line breaks before the body remain after the inserted arrow.

For an `async` or generator handler, removing `async` or `*` is offered only when the handler uses no `await` or `yield` at its own function level. Nested functions keep their own modifiers. Otherwise, the diagnostic asks for an explicit body conversion, and CLI and editor offer no modifier edit.

Modifier repairs keep comments after `async` and around `*`, including JSDoc comments.

## Coming from Effect

Pass Effect values directly: `try firstSuccessOf([latestTitle(), cachedTitle()])`. Calling an effect function constructs its Effect. Each run executes its body again. Use `effect { … }` to make an alternative from several statements.

A plain handler's default parameters, destructuring and computed binding keys follow the same known-throwing-call check as its body (`EK0401`). Use an effect handler with nonthrowing parameters, then perform throwing initialization inside its body through `Effect.try`; `try` cannot run in a parameter default. Merely creating a nested function does not execute it.

Write `try x` or `x catch h`. An unparenthesized `try`, `fork` or `join` reached through unary or binary operators reports `EK0505`, even through erased TypeScript wrappers such as `as`, `satisfies`, `!` or an angle-bracket assertion. This syntax check runs before operand typing: a scalar result or a `Fiber` still receives `EK0505`. Generated catch-call type errors are suppressed, including those anchored on `satisfies`; independent type errors in the wrapper remain. Source parentheses stop the search: `(try nested) catch () => fallback` catches the Effect returned by `nested`. Calls, literals and function bodies also stop it. The editor offers repairs for the intended operation; `vibelang --fix` keeps the running left side in an explicit `effect` block. A direct `join` becomes `Fiber.join` so it keeps the fiber in its existing owner. For a direct `fork`, it moves the handler onto the forked Effect and keeps operand evaluation on the caller. It leaves source jumps and wrapped forks for an explicit choice because changing a function boundary could change jump targets or fiber ownership.

A `catch` protects the Effect its head produces. In `decode(try parse(input)) catch (e) => fallback(e)`, a failure from `parse` escapes before the catch is installed; only a failure from the returned `decode` Effect reaches the handler. To protect both executions, write `(effect { return try decode(try parse(input)) }) catch (e) => fallback(e)`. If an older catch head executes code and returns a plain value, `--fix` wraps the head in an `effect` block to preserve its previous recovery boundary. Heads with jumps, owned resources or narrowed property reads can need a manual rewrite.

For `(try x) catch (e) => fallback(e)`, `x` must succeed with an Effect. The handler receives that returned Effect's error type; an error from executing `x` still escapes before recovery. For example, `(try Effect.succeed(Effect.fail("inner"))) catch (e) => e.length` returns `5`.

## Replacing a legacy `try` statement

Effect code rejects JavaScript `try`/`catch` and `try`/`finally`
statements with `EK0503`. Use an `effect { … }` block with a catch
expression for typed failures, and `onExit` for cleanup on every exit:

```vibe
error MissingValue

effect function recover(missing: boolean) {
  return effect {
    if (missing) throw new MissingValue()
    return 1
  } catch () => 2
}

effect function clean() {
  return try Effect.onExit(effect { return 1 }, () => effect { try Effect.log("finished") })
}
```

`vibelang --fix` and `--fix-vip-only` migrate supported legacy statements
to explicit Effect operations. The rewrite preserves fallthrough, returns,
and jumps to enclosing loops, and keeps cleanup outside recovery.
Nested statements migrate from the inside out. A statement with `var`
hoisting, `super`, `arguments`, a `do` expression completion, inferred literal returns,
a `switch` without `default`, producer yields, a jump leaving its
finalizer, or a retired typed or `Cause` clause needs an explicit migration;
the diagnostic explains why no automatic edit is offered.
The fix gate also refuses a rewrite that introduces another error, such as
capturing an owned fiber in a stored effect block.
Plain and `async` functions, including those nested in effect code, keep
JavaScript's native `try` statements.

A catch expression needs an explicit effect scope. An ordinary callback keeps its own plain scope even when an enclosing function is `effect` or the callback is expected to return an Effect; mark that callback `effect` too.
