# Add VibeLang to an existing project

Install VibeLang in a project with an existing `package.json`, verify the compiler, then wire your build.

## TypeScript and npm boundaries

Call your own `.ts` functions and npm packages through `Effect.try` when they may throw, or `tryPromise` for Promises ([TypeScript boundaries](/vibelang-features/114-vibelang-for-effect-users#keep-platform-work-in-effect)):

```vibe
import { parseSettings } from "./settings.ts"
error BadSettings { cause: unknown }

effect function settings(text: string) {
  return try Effect.try({
    try: () => parseSettings(text),
    catch: (cause) => new BadSettings({ cause })
  })
}
```

- **Avoid stem collisions:** Do not place `settings.vibe` beside `settings.ts` — both emit `settings.js` (TS5056). Name the wrapper `load-settings.vibe`.
- **Throwing contracts:** For non-effectful foreign calls, `@throws {never}` permits a direct call; missing annotations mean `unknown` and non-`never` contracts require an `Effect.try` bridge in effect code (`EK0403`). A callable returning an `Effect`, `Stream` or `Layer` is effectful: call it directly, regardless of `@throws`. Run an Effect result with `try` rather than wrapping its factory in `Effect.try`.
- **Platform APIs:** Use Effect services (`Console`, `Clock`, `Random`) for platform, clock, and randomness APIs; direct host/web calls like `crypto.randomUUID()` report `EK4402` ([diagnostics](/getting-started/012-devtools#diagnostics-completions-and-refactors)).

## 1. Check package.json

- **ESM required:** `package.json` must set `"type": "module"`. Check how that affects any existing `.js` files first.
- **Exact Effect pin:** `vibelang-runtime` requires `effect` 4.1.1 exactly. It depends on Effect internals and checks the exact version at load. VibeLang follows Effect 4.0.6's defect precedence, which 4.1.1 keeps: a failure whose cleanup crashes is a defect ([release notes](/setup/release-notes)). Upgrade your existing project to `effect@4.1.1` and verify its tests pass before converting files to `.vibe`.
- **Published libraries:** Keep `vibelang-runtime` (and `vibelang` if launching source children via `vibelang/register` or `vibelang/bun`) in production `dependencies` at a registry version, not a local `file:` path.

## 2. Install the packages

Pin `@effect/platform-node-shared` to `4.1.1` before installing so package managers do not pick a mismatched patch.

**npm** — merge into the root `package.json`:

```json
{
  "overrides": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

**Bun** — merge into whichever pin table the root `package.json` already uses. If only `resolutions` exists, add the pin there (when both exist, [Bun uses only `overrides`](https://bun.com/docs/pm/overrides#resolutions)); if neither exists, use `overrides` above:

```json
{
  "resolutions": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

Install with Bun:

```sh
bun add --exact vibelang-runtime@0.0.13 effect@4.1.1 @effect/platform-node@4.1.1
bun add -d --exact vibelang@0.0.13 vibelang-vite@0.0.13 vitest@5.1.0 @effect/vitest@4.1.1
```

Or with npm:

```sh
npm install --save-exact vibelang-runtime@0.0.13 effect@4.1.1 @effect/platform-node@4.1.1
npm install --save-dev --save-exact vibelang@0.0.13 vibelang-vite@0.0.13 vitest@5.1.0 @effect/vitest@4.1.1
```

With pnpm, configure the [transitive pin](https://pnpm.io/settings/dependency-resolution#overrides) and allow `dprint`'s install script in `pnpm-workspace.yaml` (pnpm 11+ fails with `ERR_PNPM_IGNORED_BUILDS` otherwise):

```yaml
overrides:
  "@effect/platform-node-shared": "4.1.1"
allowBuilds:
  dprint: true
```

```sh
pnpm add --save-exact vibelang-runtime@0.0.13 effect@4.1.1 @effect/platform-node@4.1.1
pnpm add --save-dev --save-exact vibelang@0.0.13 vibelang-vite@0.0.13 vitest@5.1.0 @effect/vitest@4.1.1
```

**Yarn** — use the `node_modules` linker (Yarn 2+: add `nodeLinker: node-modules` to `.yarnrc.yml`), add the pin under root `package.json` [`resolutions`](https://yarnpkg.com/configuration/manifest#resolutions) (Yarn ignores `overrides`), and install `vite` explicitly if not already on Vite 7 or 8:

```yaml
nodeLinker: node-modules
```

```json
{
  "resolutions": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

```sh
yarn add --exact vibelang-runtime@0.0.13 effect@4.1.1 @effect/platform-node@4.1.1
yarn add --dev --exact vibelang@0.0.13 vibelang-vite@0.0.13 vitest@5.1.0 @effect/vitest@4.1.1
yarn add --dev --exact vite@8
```

| Package | Install as | Purpose |
| --- | --- | --- |
| `vibelang-runtime` | Dependency | Small helpers used by compiled code |
| `effect`, `@effect/platform-node` | Dependency | Effect 4.1.1 and Node platform |
| `vibelang` | Dev dependency | Compiler, language server, native binary, and VS Code extension |
| `vibelang-vite` | Dev dependency | Compiles `.vibe` modules for Vite and Vitest |
| `vitest`, `@effect/vitest` | Dev dependency | Vitest 5.1.0 and `@effect/vitest` 4.1.1 |
| `vite` | Dev dependency | Vite 7 or 8 (explicit peer for Yarn) |

Keep `effect`, `@effect/platform-node`, and `@effect/vitest` at `4.1.1`, keep `vibelang`, `vibelang-runtime`, and `vibelang-vite` at one version, and keep optional dependencies enabled so `vibelang` installs its platform binary.

VibeLang uses TypeScript 7, which rejects removed options such as `moduleResolution: "node"` / `"node10"` and `baseUrl` (TS5108 / TS5102); see the [TypeScript 7 migration notes](https://github.com/microsoft/typescript-go/blob/main/CHANGES.md).

## 3. Check the compiler

```sh
npx vibelang --version
```

```text
VibeLang 0.0.13 (TypeScript 7.1.0-dev)
```

## 4. Port Effect TypeScript files

Rename an Effect `.ts` file to `.vibe` (or `.tsx` to `.vibex`) and check it:

```sh
npx vibelang -p tsconfig.json --noEmit
```

- **TypeScript-style Effect code:** Library calls keep working in `.vibe` ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). A piped `Effect.gen(...)` reports `EK1002`: rewrite it as an `effect function` with `provide` and `try`. For retired syntax from earlier releases, see [Migrating retired forms](/setup/migrating-retired-forms).
- **Relative imports and sidecars:** Replace stale `./user.ts` imports that point to a renamed `user.vibe` with `./user.vibe` or `./user.js` ([CLI setup](/setup/vibelang-cli)). `vibelang` writes adjacent `.d.vibe.ts` declarations even with `--noEmit` ([let TypeScript tools read .vibe modules](/setup/vibelang-cli#let-typescript-tools-read-vibe-modules)).
- **Monorepos & project references:** When migrating referenced packages, compile and revert steps refresh affected projects automatically. They follow the reverse reference closure, clear affected outputs, and rebuild reference roots before checking dependents. For native checking with Bun (`bun check --no-script`), route to `vibelang --noEmit` (or `vibelang -b` in build mode).
