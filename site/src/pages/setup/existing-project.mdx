# Add VibeLang to an existing project

Install VibeLang's packages in a project with a `package.json` and check that the compiler runs; then set up the build.

Call your own `.ts` functions and npm packages through `Effect.try` when they may throw, or `tryPromise` for Promises ([TypeScript boundaries](/vibelang-features/114-vibelang-for-effect-users#keep-platform-work-in-effect)). For example, import your parser and capture its input in the callback:

```vibe
import { parseSettings } from "./settings.ts"
error BadSettings { cause: unknown }

effect function settings(text: string) {
  return try Effect.try({
    try: () => parseSettings(text),
    catch: (cause) => new BadSettings({ cause })
  })
}
```

Give a `.vibe` wrapper a different file stem from the `.ts` module it
wraps. For example, `settings.vibe` beside `settings.ts` both emit
`settings.js`, causing TS5056 in the CLI, Vite and Vitest. Name the wrapper
`load-settings.vibe` instead.

Use Effect services for platform, clock and randomness APIs, such as `Console`, `Clock` and `Random`. The compiler reports unwrapped foreign calls as `EK4401`, and platform calls, including the web's clock and randomness reads such as `crypto.randomUUID()`, as `EK4402` ([diagnostics](/getting-started/012-devtools#diagnostics-completions-and-refactors)). A function that cannot throw can be called directly. Library declarations describe thrown types with `@throws {E}`. A missing annotation means the call may throw `unknown`.

## 1. Check package.json

`package.json` must have `"type": "module"`. Before adding it, check how this changes Node's loading of your project's `.js` files.

The VibeLang runtime requires `effect` 4.1.1 exactly. The compiler declares the same exact peer dependency, so package managers can report an incompatible version during installation. The runtime depends on Effect internals and checks the exact version at load. VibeLang follows Effect 4.0.6's defect precedence, which 4.1.1 keeps: a failure whose cleanup crashes is a defect. Read the [release notes](/setup/release-notes) before updating code that inspects causes or recovers mixed failures. If your project depends on another `effect` version, review the migration before changing it. Upgrade an existing project to the pinned Effect version first, fix any failures, and verify its tests. Convert files to `.vibe` only after the Effect upgrade passes.

For a published library, keep `vibelang-runtime` in production dependencies at a registry version. A package that starts source children through `vibelang/register` or `vibelang/bun` also needs `vibelang` in production dependencies. A production `file:` path into a local toolchain does not travel with an `npm pack` tarball.

The migration flow keeps these production dependencies at the staged artifacts' actual release versions while retaining local development pins. Its `.vibelang/toolchain-publication.json` receipt lists the exact versions that must be published before consumers can install the target tarball. A successful local setup does not establish that those releases are available in the registry.

## 2. Install the packages

Before installing, add this transitive pin to `package.json` (npm and Bun both honor `overrides`):

```json
{
  "overrides": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

This keeps the platform package from selecting a newer patch with a different Effect peer requirement.

With Bun, run:

```sh
bun add --exact vibelang-runtime@0.0.11 effect@4.1.1 @effect/platform-node@4.1.1
bun add -d --exact vibelang@0.0.11 vibelang-vite@0.0.11 vitest@5.1.0 @effect/vitest@4.1.1
```

With npm, run:

```sh
npm install --save-exact vibelang-runtime@0.0.11 effect@4.1.1 @effect/platform-node@4.1.1
npm install --save-dev --save-exact vibelang@0.0.11 vibelang-vite@0.0.11 vitest@5.1.0 @effect/vitest@4.1.1
```

With pnpm, first allow the install script of `dprint`, which `vibelang` depends on. pnpm 11 and later fail an install with `ERR_PNPM_IGNORED_BUILDS` when a dependency's build script is neither allowed nor denied. Add this to `pnpm-workspace.yaml`:

```yaml
allowBuilds:
  dprint: true
```

Then run:

```sh
pnpm add --save-exact vibelang-runtime@0.0.11 effect@4.1.1 @effect/platform-node@4.1.1
pnpm add --save-dev --save-exact vibelang@0.0.11 vibelang-vite@0.0.11 vitest@5.1.0 @effect/vitest@4.1.1
```

| Package | Install as | Purpose |
| --- | --- | --- |
| `vibelang-runtime` | Dependency | Small helpers used by compiled code |
| `effect`, `@effect/platform-node` | Dependency | Effect 4.1.1 and its Node platform |
| `vibelang` | Dev dependency | The compiler and language server, its native binary, and the VS Code extension |
| `vibelang-vite` | Dev dependency | Compiles `.vibe` modules for Vite and Vitest |
| `vitest`, `@effect/vitest` | Dev dependency | Vitest 5.1.0 and `@effect/vitest` 4.1.1 for tests |

Keep `effect`, `@effect/platform-node`, and `@effect/vitest` at 4.1.1. `vibelang`, `vibelang-runtime`, and `vibelang-vite` release together; keep them at one version.

Keep optional dependencies enabled: `vibelang` gets its native compiler from one optional dependency per platform, such as `vibelang-darwin-arm64`. If an install skips them, as `npm install --omit=optional` does, `vibelang` cannot find its binary and exits with an error.

VibeLang uses TypeScript 7, which rejects removed options such as `moduleResolution: "node"` / `"node10"` and `baseUrl` (TS5108 / TS5102); update an older tsconfig using the [TypeScript 7 migration notes](https://github.com/microsoft/typescript-go/blob/main/CHANGES.md).

## 3. Check the compiler

```sh
npx vibelang --version
```

The output is:

```text
VibeLang 0.0.11 (TypeScript 7.1.0-dev)
```

## 4. Port Effect TypeScript files

Rename a `.ts` file that uses Effect to `.vibe`, then let the compiler rewrite it:

```sh
npx vibelang -p tsconfig.json --fix --noEmit
```

If a previous migration left `./user.ts` pointing at a renamed `user.vibe`, `--fix` also repairs that stale relative name in VibeLang sources before native-extension fallback is retired. The replacement follows the project's `rewriteRelativeImportExtensions`, `allowImportingTsExtensions` and emit settings: a permitted source name, or the runtime `.js`/`.jsx` name. Existing native files keep their imports. See [CLI migration](/setup/vibelang-cli).

`--fix` applies each rewrite that keeps the program's meaning: Effect error and service classes become `error` and `service` declarations, `Effect.succeed` and `Effect.fail` become returned values and `throw`, catch combinators become `catch`, `Match` chains become `match`, Option pipes become module calls, prelude imports go, a later `is` binding that repeats a name of its block is renamed with its uses, and an `Effect.gen` that is a function's whole body becomes an effect function with `try` replacing `yield*` ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). It refuses a rewrite that would change what other code receives, and prints why. An `Effect.gen` that the file pipes, such as `Effect.gen(...).pipe(Effect.provide(AppLive))`, stays EK1002 for now: write its body by hand inside `export effect function main() { provide AppLive { ... } }`, reading a service as `try Users`.

Code written for an earlier VibeLang release can use forms that are now retired, such as a trailing block or a legacy platform entry marker. `--fix` rewrites those too; [Migrating retired forms](/setup/migrating-retired-forms) describes how.

Run `vibelang` to write adjacent `.d.vibe.ts` declarations, even with `--noEmit`; [configure TypeScript tools to read them](/setup/vibelang-cli#let-typescript-tools-read-vibe-modules).
