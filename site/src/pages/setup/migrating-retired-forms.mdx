# Migrating retired forms

Each retired or legacy form reports a diagnostic. This page names each form and what to write instead. VibeLang ships no automatic rewrite for these forms: edit each reported site by hand. The [specification](https://vibelang.sh/spec/007-tooling#compiler-and-tooling-requirements) states each form's diagnostic. This page is not normative: where it and the specification differ, the specification and the compiler's tests decide.

## General migration rules

**Migration** rewrites toward the VIP form or native Effect TypeScript and preserves evaluation order, captures, the call-versus-run phase, coldness, error and environment channels, and public declarations. It never edits a test or a fixture: a test that bundles `.vibe` passes unchanged, or its modules stay `.ts`. A default plan leaves Effect type-only users in TypeScript. A legacy `try make()` of a removed plain wrapper loses its `try`, whatever the result's shape. An old call whose behavior it can't preserve keeps a `.ts` boundary, with an explicit refusal. It never invents `asEffect()`, never turns `Match.withReturnType<T>()` into an unchecked `as T`, and writes `try Effect.forkChild(program, options)` for the legacy `fork(program, options)`. Prelude cleanup keeps an explicit Effect import where removing it would change the declaration. A tool cache for type-directed compilation is reusable only while its source, declarations, configuration, versions and project are unchanged. A missing validation outcome is unverified: a later stage never inherits an earlier stage's exit. This also applies to legacy setup compile receipts: a missing or invalid setup exit blocks migration admission; retain the receipts and start a fresh setup from the original source. Package paths keep separate compiler results, including `packages/core` and `packages__core`. An older receipt shared by multiple package names is unverified and names the possible owners; preserve it and start a fresh setup. The migrate flow pairs a callback with its original callee, argument position and occurrence, separately from its enclosing function. A callback returning a cold `Effect.gen` program may become an `effect` callback with the same void completion. An `effect { … }` block remains a program returned by its plain factory; a dropped return value or call-time work moved into an `effect` function still fails verification.


## Generator parameter defaults

A default on an `Effect.fn` or `Effect.fnUntraced` generator runs each time the returned Effect executes. A native `effect` function instead binds defaults once when called, as an ordinary TypeScript function does. Moving a generator default onto an `effect` parameter can capture stale state or share an allocated object across executions. Retain the module as TypeScript, or preserve the binding inside a cold `effect { … }` block. Initialize dependent defaults in parameter order and test repeated executions as well as repeated calls.

For example, `Effect.fn(function* (input, value = input.branch) { return value })` can be written with an optional argument and an execution-time binding:

```vibe
function read(input: { branch: string }, value?: string) {
  return effect {
    const resolved = value === undefined ? input.branch : value
    return resolved
  }
}
```

An object default follows the same rule: allocate `{}` inside the block when the argument is `undefined`. Each execution then gets its own object. An explicit argument, including its identity, stays shared as in the original. Ordinary native `effect` parameters keep call-time initialization; they are suitable when the original plain factory bound its defaults before returning an Effect.


## Stale `.ts` specifiers

A relative `./user.ts` is stale when its native target is gone and the migrated `user.vibe` exists; the same applies to a `.tsx` name for a migrated `.vibex` module. With `rewriteRelativeImportExtensions`, write `./user.vibe` or `./user.vibex`; a type-only project allowing source extensions can also use those names. Otherwise write the actual runtime output, `./user.js` (or `.jsx` for a JSX-preserving target). A matching native TypeScript implementation keeps its name. Replace stale names before upgrading to the resolver that rejects stale native extensions.

Package declarations preserve the TypeScript twin's spelling: `./user.vibe` becomes `./user.ts`, while a written `./user.js` remains `./user.js`. Neither `allowImportingTsExtensions` nor `rewriteRelativeImportExtensions` rewrites declaration specifiers. The retired `declarationImportStyle` setting cannot restore an original package's spelling. When a migration requires byte-identical declarations, preserve that spelling at the source or a native declaration boundary, then compare actual output with stock TypeScript using the package's options.

## Trailing blocks

A legacy trailing block reports `EK1101`. Write the block as an explicit argument of the kind and position the legacy call used: an Effect program uses `effect { ... }`, an Effect callback uses `effect () => { ... }`, and a plain callback uses `() => { ... }`. These destinations have different execution behavior, and the callee's parameter type alone cannot decide the kind (VIP-34).

A block after an Effect dual that `0.0.10` ran as the dual's program reports transitional `EK1023` instead, when appending the block as the last argument would type-check with a changed meaning. Keep the original data-first or curried argument position: pass the block where `0.0.10` placed it.

## The retired `try(…)` hatch

The retired `try(…)` hatch form reports `EK4616`. Wrap the native code with `Effect.try` or `tryPromise`, then run its Effect with `try`.

## The retired global `Effect` alias

Preserve existing parentheses, written default slots and required imports when editing this alias. Keep the `Effect` namespace binding unchanged.

## Ordinary mutable-marker migration

Remove the redundant `mutable` marker from an ordinary interface or object-type property or index signature. The field stays writable unless written `readonly`. For a plain `error` payload with a legacy `mutable` marker, write an explicit compatibility class using the existing runtime error factory; it retains tagged matching. Schema fields, schema errors, schema tuples and `data` bodies use their separate rules.

After all migration repositories have zero remaining accepted uses, these ordinary member and plain-error payload markers are rejected with `EK3410`. A method or identifier named `mutable` keeps its TypeScript meaning. This specifies the retirement target; it does not claim the held rejection implementation or consumer migration is complete.

## Legacy data receiver methods

Replace a legacy Effect data receiver method with the resolved module's data-first function: write `Option.some(1).map(f)` as `Option.map(Option.some(1), f)`.

## Legacy prelude shorthand

For a legacy bare prelude `Scope` type, write `Scope.Scope`. A written import, local or ambient type, or type parameter named `Scope` keeps its TypeScript meaning.

For the retired same-named module-export shorthand, write the export: `Option<A>` as `Option.Option<A>`, and `FileSystem.of(impl)` as `FileSystem.FileSystem.of(impl)`. VIP-14 supplies module namespaces; a local type, an ambient type, an already qualified export and a namespace's own member keep their meaning.

## Legacy fork, try-statement and wire migration

Write the transitional bare `fork { ... }` spelling as `fork effect { ... }` (VIP-2 and VIP-17). Explicit Effect operands are unchanged.

A retired statement reports `EK0503`; a typed catch clause also reports warning `EK2112`. Under VIP-5, write old Effect statement catches and finalizers as explicit Effects, `catch effect`, and native cleanup combinators. Keep structural tag matching, handler order, the old successful finalizer input `Exit.void` and the declaration's [API identity](https://vibelang.sh/spec/001-functions#api-identity).

Under VIP-24, replace the retired resolved `wire` intrinsic with explicit `Layer.provideMerge` composition. Supply each layer once, in source order, and keep the dependency order of the old graph and the declaration's [API identity](https://vibelang.sh/spec/001-functions#api-identity). An unrelated local function named `wire` keeps its TypeScript meaning.

After preserving migration, a bare `fork { … }` is `EK1707` and the resolved retired `wire` intrinsic is `EK2401`. The held enforcement changes still require zero remaining uses in every migration repository.

## Empty legacy trust wrappers

The resolved `trusted(f, [])` runtime wrapper is retired with `EK0407`. Capture `f` once at the original declaration, and write each private direct synchronous call in explicit Effect code as `try Effect.orDie(Effect.try({ try: () => f(x), catch: (e) => e }))`. The identity catch mapper keeps the exact thrown value as a defect and leaves the public error channel unchanged. A reviewed `.ts` helper with `@throws {never}` is another replacement. Listed-failure wrappers are outside this migration.

## Legacy entry-dispatch migration

The legacy entry input is a module marked by a side-effect import of `vibelang/platform/node`, `vibelang/platform/bun` or `vibelang/platform/browser`. These compiler-only markers report `EK2601`, including in a module without `main`. A function named `main` alone remains ordinary source and gets no entry diagnostic ([VIP-26](https://vibelang.sh/vips/0026-top-level-and-main#decision)).

If the marked module has no exported, non-default, zero-parameter function declaration `main` with a body, delete the inert marker and keep any explicit runner unchanged.

The legacy compiler started an eligible `main` only when the host started its module, never when another module imported it. A runner call written into the module also runs on import, and the migration must preserve that entry test for the original host. `import.meta.main` follows the host's declarations and behavior; its availability alone does not prove parity with the legacy dispatcher, which is not a migration target. So write the runner where your program starts, for example `import * as NodeRuntime from "@effect/platform-node/NodeRuntime"` and `NodeRuntime.runMain(main())`, then delete the marker.

Use the runner and layers the legacy compiler selected. The `node` and `bun` markers select `NodeRuntime.runMain`; `browser` selects `BrowserRuntime.runMain`. Provide a layer only when the legacy compiler provided it to `main`, with experimental layers in their original nesting order; for `bun`, provide `BunServices.layer` when it was selected. Pass `main()` for a legacy Effect function and `Effect.sync(main)` otherwise, so `main` keeps its callable kind and public declaration.

If the module is only ever started, never imported, write the named imports and runner call in it and delete the marker. Otherwise, write them in a separate entry file that imports `main`. A remaining marker still reports `EK2601`, and current compilation emits no implicit startup.

If an older unmarked application relied on automatic startup, add a written runner to its application entry file, as in [Create a project](/getting-started/004-installation). The normative [entry migration](https://vibelang.sh/spec/007-tooling#legacy-entry-dispatch-migration) states the target forms.

## The VIP-1 function-kind and `try` migration

For source written before VIP-1, write `try` before each call that ran where it stood, whatever the position, and mark `effect` each function the old compiler made an Effect function. Where you remove a known legacy wrapper, also remove the `try` that ran it, even when the success data is an `error` or `schema error` instance, another Effect, or an object with an `asEffect` member. Keeping that `try` would fail with data or run a previously unrun program. A call whose written or native contract already returned the intended Effect keeps its `try`, including an error returned for intentional execution ([VIP-34](https://vibelang.sh/vips/0034-compiler-and-tooling#decision), amended).

In current source, `try make()` intentionally runs the result whenever it passes the [operand test](https://vibelang.sh/spec/002-running#operand-test).

A value that fails that operand test, such as `Option.some(1)` or `Result.succeed(2)`, keeps `EK0502`, whatever methods the value has; write no conversion such as `asEffect()` ([VIP-5](https://vibelang.sh/vips/0005-try-runs-effects#decision), amended).

A plain catch handler returns its result as data, including an error or an `Effect` value, and reports the `EK0508` advisory. To run the returned `Effect` instead, write `effect` before the handler, as in `x catch effect (e) => …`, only when that is the intended behavior.

## Callback completion values

The global `callback` is `Effect.callback`, including in a direct call. Removing a legacy `: infer _` annotation from its registration callback keeps this native API and preserves the written resume argument. Complete it with `resume(succeed(value))`, `resume(fail(error))` or `resume(exit)`. Return a cleanup Effect, such as `sync(cleanup)`, for interruption.

Code using the older `resume(value)`, `resume.fail(error)`, `resume.exit(exit)`, explicit input arguments or cleanup functions can keep the legacy adapter with `import { callback } from "vibelang-runtime"` while migrating. That import keeps the adapter's existing type and behavior.

A bare `: infer _` return annotation on a plain callback has no TypeScript meaning. Remove it from native `callback` and `Effect.callback` registration functions too; native completion still passes an Effect to `resume`, such as `resume(Effect.succeed(value))`.

## Legacy return-slot inference

For a plain function that returns an `Effect`, replace a retired `infer` return slot with the channels of the returned program: its real errors and the service requirements its callbacks introduce. A retired placeholder is not a requirement of a generic call or its handler. Keep the function's own type parameters when they describe those channels.

## Legacy service forms

`service class Users { … }` is retired and reports `EK0909`. Remove `class`, keeping the service key, shape and comments between the keywords.

The transitional `static readonly default = implementation` form reports the `EK4855` migration warning. For a local service, write the equivalent native `Context.Service` class and keep the cached static field, its key, its value and type reads, and the shape's mutable members. This keeps eager initialization and adds no missing-provider fallback. Exported keys, commented service bodies and keys that also declare `defaultValue` need the same native class. The legacy field needs an initializer: `static readonly default: Shape` without a value is `EK0902`.

Writing `static readonly defaultValue = () => implementation` instead chooses a `Context.Reference` fallback. Adding `readonly` to an old mutable `defaultValue` chooses that fallback too, so make that change as a deliberate migration. When upgrading a legacy service that used the old readonly default, write `readonly` on those fields and their nested type members to keep the earlier declarations.

Older compilers derived directory-prefixed keys for services in a package whose `package.json` has `"name": ""`. To keep those identities, write the old keys explicitly with `static readonly key` before upgrading consumers.

## Migration setup

The API check supports `exports` that point at generated declaration sidecars through `rootDirs`. A sidecar must match the selected project's emitted declaration and have one source owner; changed or ambiguous mirrors keep the batch under review.

Migration setup excludes generated declaration sidecars, including `x.vibe.platform.d.ts` and `x.vibex.platform.d.ts`, from Oxlint, ESLint, dprint and formatters that read `.prettierignore`. Authored `.platform.ts` implementations remain checked. Rerun setup to update an existing migration's configuration.

The migration's canonical API comparison uses freshly emitted declarations for native `module` bodies. Existing compatibility copies can spell imports differently; they do not replace the current emit. Handwritten neighbouring declarations remain checked.

In Vite+ projects, these generated-output exclusions also go in `vite.config.ts` under `fmt.ignorePatterns` and `lint.ignorePatterns`. Existing rules, test settings and authored implementation checks stay in place. Setup reports a warning when those sections are computed and require an explicit edit.

## Retaining validation evidence

Keep the original compiler-check reports as well. Losing a report or a checked package's entry cannot remove that package from verification. The run names the package and missing evidence and refuses to resume.

Keep the migration run directory until the migration finishes. A completed setup must retain its compiler diagnostics and exit receipts for every checked package. If both files are missing, resuming the run stops with the package named, even when an earlier admission record said it was accepted. Current setup records its compiler-receipt format, so losing those files or their directory cannot select an older successful result. Legacy-only runs remain readable when their package identities are unambiguous. Retain the remaining evidence and start a fresh setup from the original source.
