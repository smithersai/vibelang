# Installation

The fastest way to start is the starter project, which pins every package at a compatible version.

Create it with npm:

```sh
npm create vibelang@latest my-app
cd my-app
npm run start
```

With Bun (optional):

```sh
bun create vibelang@latest my-app
cd my-app
bun run start
```

The native `vibe` (alias `vibelang`) compiler compiles `.vibe` sources to JavaScript. Version 0.0.14 installs from npm.

> **For agents.** Give a coding agent:
>
> ```text
> Set up Vibe in this project: read https://vibelang.sh/setup and follow it.
> ```
>
> It detects the package manager, build tool, and editor and follows [Set up Vibe](/setup).

## Prerequisites

Install Node 22.22.3 (22.x) or Node 24.11.1 or later. Bun is optional. If you use it, install Bun 1.4.2 or later. See how to [run sources with Bun](/setup/vibelang-cli#run-sources-with-bun).

`vibelang` installs one platform binary via optional dependencies — keep optional dependencies enabled (avoid `--omit=optional`):

| Platform | Package | Rehearsed for 0.0.14 |
| --- | --- | --- |
| macOS on Apple silicon | `vibelang-darwin-arm64` | No |
| macOS on Intel | `vibelang-darwin-x64` | No |
| Linux on x64 | `vibelang-linux-x64` | Yes |
| Linux on arm64 | `vibelang-linux-arm64` | No |
| Windows on x64 | `@smthrs/cli-win32-x64` | No |
| Windows on arm64 | `@smthrs/cli-win32-arm64` | No |

Version 0.0.14 publishes six native packages; the release rehearsal creates, starts, and tests a starter with npm and Bun on Linux x64. The other five binaries are cross-built and not yet rehearsed on target hardware.

## Create a project

```sh
npm create vibelang@latest my-app
cd my-app
npm run start
npm run test
```

With Bun, use `bun create vibelang@latest my-app`, `bun run start`, and `bun run test`. Pass `--no-install` to skip dependency installation. `npm run start` builds and prints:

```text
Hello, VibeLang!
Recovered from EmptyName
```

See [Getting Started](/013-getting-started) for the starter files and [Running Effects](/getting-started/009-running-effects) for execution.

## Add VibeLang to an existing project

Pin the transitive `@effect/platform-node-shared` helper in the root `package.json` before installing so package managers do not select a mismatched patch.

For npm (or Bun when `overrides` exists or neither table exists):

```json
{
  "overrides": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

With Bun, if the root `package.json` uses only `resolutions`, add the pin there instead — when both fields exist, [Bun uses only `overrides`](https://bun.com/docs/pm/overrides#resolutions) and ignores `resolutions`:

```json
{
  "resolutions": {
    "@effect/platform-node-shared": "4.1.1"
  }
}
```

Then install the pinned packages (for pnpm and Yarn, see [existing project](/setup/existing-project#2-install-the-packages)):

```sh
bun add --exact vibelang-runtime@0.0.14 effect@4.1.1 @effect/platform-node@4.1.1
bun add -d --exact vibelang@0.0.14 vibelang-vite@0.0.14 vitest@5.1.0 @effect/vitest@4.1.1
```

With npm, use `npm install --save-exact` and `npm install --save-dev --save-exact`.

| Package | Install as | Purpose |
| --- | --- | --- |
| `vibelang-runtime` | Dependency | Small compiled-code helpers (e.g. `Symbol.customMatcher` polyfill); adds no runtime semantics |
| `effect`, `@effect/platform-node` | Dependency | Effect 4.1.1 and Node platform |
| `vibelang` | Dev dependency | Compiler, language server, native binary, and VS Code extension |
| `vibelang-vite` | Dev dependency | Compiles `.vibe` modules for Vite and Vitest |
| `vitest`, `@effect/vitest` | Dev dependency | Vitest 5.1.0 and `@effect/vitest` 4.1.1 |

**Version pinning:** `vibelang-runtime` requires `effect` 4.1.1 exactly — it depends on Effect internals and checks the exact version at load. The compiler reports `EK3201` if the resolved `effect` differs from `4.1.1`. VibeLang follows Effect 4.0.6's defect precedence, which 4.1.1 keeps: a failure whose cleanup crashes is a defect (see [release notes](/setup/release-notes)). Keep `effect`, `@effect/platform-node`, and `@effect/vitest` at `4.1.1`, and keep `vibelang`, `vibelang-runtime`, and `vibelang-vite` at one matching version.

Add `tsconfig.json` (VibeLang checks `vibe.config.json`, then `tsconfig.json`, then `jsconfig.json`; VibeLang-specific options go under a top-level `"vibe"` key, which plain `tsc` ignores):

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "sourceMap": true,
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true,
    "rewriteRelativeImportExtensions": true,
    "skipLibCheck": true,
    "types": []
  },
  "include": ["src"],
  "exclude": ["src/**/*.test.vibe"]
}
```

Add scripts to `package.json` (which must set `"type": "module"`):

```json
{
  "type": "module",
  "scripts": {
    "build": "vibelang",
    "start": "vibelang && node --enable-source-maps dist/main.js",
    "test": "vitest run"
  }
}
```

`src/main.vibe` invokes its runner explicitly at top level (`NodeRuntime.runMain(Effect.provide(main(), NodeServices.layer))`); the compiler does not auto-call `main`.

`node --enable-source-maps` maps JS locations back to `.vibe` lines, but VibeLang adds no spans of its own so a defect stack can show one frame. Name spans with `try withSpan(effect { ... }, "checkout")`, and see [Debug stack traces](/getting-started/012-devtools#debug-stack-traces) when a caller stack is missing.

Add `tsconfig.test.json` and `vitest.config.ts` so Vitest compiles `.test.vibe` files without emitting them into `dist/`:

```json
{
  "extends": "./tsconfig.json",
  "exclude": []
}
```

```ts
// TypeScript (.ts)
// vitest.config.ts
import { defineConfig } from "vitest/config"
import vibelang from "vibelang-vite"

export default defineConfig({
  plugins: [vibelang({ project: "tsconfig.test.json" })],
  test: { include: ["src/**/*.test.vibe"] }
})
```

Keep `"rewriteRelativeImportExtensions": true` so `.ts` files can import `.vibe` modules without TS5097. If your root `tsconfig.json` uses `"files": []` with `references`, pass the app config (`vibelang({ project: "tsconfig.app.json" })`). See [Vite and Vitest](/setup/vite).

To upgrade all three VibeLang packages together (read [release notes](/setup/release-notes) first, as v0 releases can break):

```sh
bun add vibelang-runtime@latest
bun add -d vibelang@latest vibelang-vite@latest
```

## Configure your editor

After installing dependencies, install the bundled extension:

```sh
code --install-extension node_modules/vibelang/editor/vibelang.vsix
# Or, for Cursor:
cursor --install-extension node_modules/vibelang/editor/vibelang.vsix
```

It is not yet on the VS Code Marketplace or Open VSX; reinstall from `node_modules` after updating `vibelang`. Other editors configure their LSP client to run `vibelang --lsp --stdio` for `.vibe` and `.ts` files ([Devtools](/getting-started/012-devtools)).

## Compiler commands

```sh
bun run build
bun run start
bun run test
bun x --no-install vibelang --noEmit
```

`vibelang` accepts TypeScript flags (`--noEmit`, `--watch`, `-b`) and emits compatibility declarations (`x.d.vibe.ts`) alongside each `.vibe` module (or in `vibe.sidecarDir`, such as the starter's `.vibe/declarations/`):

- **Stock TypeScript tools:** `tsc` and TypeDoc resolve `.vibe` imports via `allowArbitraryExtensions`. When a `check` script is declared, `bun check` runs the project's `check` script; a script invoking a TypeScript checker uses its sidecar resolution. (`bun check --no-script` selects Bun's native checker, which the runtime preload does not replace; use `vibelang -b` or `"check": "vibelang -b"` for native `.vibe` checking.)
- **Generated declarations:** Non-effectful exported callables carry `@throws` (or `@throws {never}`) in their `.d.vibe.ts` declarations; `effect` functions, `Stream`/`Layer`-returning callables, getters, and setters carry none. Set `"declaration": true` to also emit `.d.ts` files to `dist/` (the starter omits this option). Local source imports use `.vibe`; emitted JS and `.d.ts` files rewrite them to `.js`.
- **Workspace project references:** Leave `disableSourceOfProjectReferenceRedirect` absent or `false` so typed tools preserve sidecar resolution across namespace barrels ([Devtools](/getting-started/012-devtools)).

### TypeScript declaration consumers

Downstream projects checking emitted declarations with stock `tsc` require **TypeScript 5.7 or later** for `effect@4.1.1`, whose types use generic typed arrays like `Uint8Array<ArrayBuffer>` (introduced in TS 5.7). This consumer requirement is separate from VibeLang's TypeScript 7.1 checker; upgrade `typescript` rather than relying on `skipLibCheck`. Consumers also install `vibelang-runtime` beside `effect` ([Services and errors from TypeScript](/vibelang-features/114-vibelang-for-effect-users#services-and-errors-from-typescript)).

## Coming from Effect

Install `vibelang` and `vibelang-runtime` beside `effect@4.1.1`. Write application logic in `.vibe` and keep TypeScript integrations in `.ts`; the compiler checks both as one program.

## Last resort: keep TypeScript file names

Prefer the compiler, plugins, and editor setup above. Only if a project cannot rename files to `.vibe`/`.vibex`, see the experimental [TypeScript shim](/setup/typescript-shim) and its stock-tool limitations.
