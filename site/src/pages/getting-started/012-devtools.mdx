# Devtools

Compiler diagnostics show VibeLang contracts and catch failures or requirements that escape a function's promise. The `vibelang` compiler and its language server check `.vibe` and `.ts` files together.

## Install language tooling

```vibe
// example.vibe
effect function sample() {
  try sleep("5 millis")
  return "sample"
}
// string!!
// Output: sample
```

Install `vibelang` as a dev dependency. `vibelang --lsp --stdio` starts the language server from the project's compiler, one server for `.vibe` and `.ts` files.

For VS Code and Cursor, install the extension that ships in `vibelang`, then open the application directory:

```sh
code --install-extension node_modules/vibelang/editor/vibelang.vsix
# Or, for Cursor:
cursor --install-extension node_modules/vibelang/editor/vibelang.vsix
```

The extension is not on the VS Code Marketplace or Open VSX yet; reinstall it from `node_modules` after you update `vibelang`.

Other editors configure their LSP client to run `vibelang --lsp --stdio` for `*.vibe` and `*.ts`, with `vibe.config.json`, `tsconfig.json`, or `jsconfig.json` as a root marker. Turn off the other TypeScript server for this project to avoid duplicate diagnostics. JetBrains IDEs can use LSP4IJ.

For GitHub highlighting, add `*.vibe linguist-language=TypeScript` to `.gitattributes`; the starter's `.gitattributes` already has this line. Effect's type-aware lint rules, `@effect/tsgo`'s `effecttsgo/*` rules, are built into `vibelang`: see [Lint Effect code](/setup/vibelang-cli#lint-effect-code).

## Inspect inferred information

```vibe
error Rejected

effect function accepted(value: number) {
  if (value < 0) throw new Rejected()
  return value + 1
}
// number!Rejected
// Output: 3
```

Inspect `A`, `E`, and `R` when changing a function. A local call returns an unrun Effect. `try` returns its success value. The function's complete contract also records escaping failures and unmet services, and generated declarations expose it to TypeScript consumers.

Hover over an Effect-returning function to see its inferred `Effect<A, E, R>`. Language-server, formatter, and diagnostic support for the new forms arrives with the compiler's VIP implementation.

## Diagnostics, completions, and refactors

```vibe
// expect-error: EK9201
// Rejected escapes a contract promising no failures.
effect function promised(value: number): number!! {
  return try accepted(value)
}
```

This is `EK9201`, an interim code ([diagnostic code map](/vibelang-features/diagnostic-code-map)): handle `Rejected` inside the function or widen its contract. Unmet services are `EK9202`, also interim. A call returns an Effect that can be stored at module top level; run it with an explicit runner. A synchronous callback can return an Effect without running it.

Inside effect functions, wrap a call that may throw with `Effect.try`, or a Promise with `tryPromise`, then run the wrapper with `try`. A plain function known not to throw can be called directly. A Node.js or web I/O global, run or held as a value, and a Node.js module imported as a value are rejected with the Effect service that replaces them (`EK4402`). The web's `crypto` and `performance` are such globals. `Date.now()` and `Math.random()` stay allowed, though the current compiler still reports some clock and randomness reads as `EK4403`, an interim code. A runner inside code a fiber runs is `EK1005`. A `catch` expression whose Effect has E = `never` gets `EK9204`, an interim code (defects pass through), a warning by default.

Use a throw statement to fail an Effect: `if (value === undefined) throw new MissingValue()`. A handler that fails again uses `catch effect (e) => { throw e }`; a plain `catch (e) => value` returns a value.

The server exposes TypeScript completions through the VibeLang checker, service member types included. Catch-specific completions are not implemented. Other diagnostic messages suggest repairs as text. Use an effect function and `try` for VibeLang sequencing.

## Configure compiler checks

```vibe
effect function checked(value: number): number!Rejected {
  return try accepted(value)
}
// Output: 3
```

A contract gives the compiler a promise to check. Write all three channels, such as `Effect.Effect<number, Rejected, never>`, or omit the return annotation to infer all three. An omitted slot is `never`, so `Effect.Effect<number>` is `number!!`. VibeLang reads `vibe.config.json`, `tsconfig.json`, or `jsconfig.json`, in that order within a directory. `vibe.config.json` accepts every `tsconfig.json` field with its TypeScript meaning, except that every `.vibe` file is a module whatever `moduleDetection` says. Put VibeLang's settings under the top-level `"vibe"` key:

```json
{
  "compilerOptions": {
    "strict": true,
    "sourceMap": true
  },
  "vibe": {
    "severities": { "EK0801": "error", "EK4609": "warning", "EK3801": "off" }
  }
}
```

A config that `extends` another inherits its `vibe` settings key by key, and `severities` merges entry by diagnostic code. TypeScript, typescript-eslint, and editors' TypeScript servers ignore the top-level object. Plain `tsc` rejects unknown `compilerOptions` with TS5023, so keep VibeLang's settings at the top level.

Each `.vibe` file keeps the settings of the package that owns it. When a project reads another workspace package's `.vibe` source, the checker applies that package's config to its diagnostics. The importing project's settings apply to the files of its own package. Editor projects and imported packages use the nearest configuration directory, preferring `vibe.config.json`, then `tsconfig.json`, then `jsconfig.json` there. Creating `vibe.config.json` in an open project refreshes that selection.

Only a warning's code or an assigned imported `EK38xx` lint code may appear in `vibe.severities`. Set it to `"error"`, `"warning"`, `"suggestion"` or `"off"`. Warnings do not fail CI or prevent emission under `noEmitOnError`; use `"error"` to fail CI. Suggestions appear only in the language server. Invalid entries report `EK3006`; unknown or wrong-typed `vibe` options report `EK3007`. `extends` merges severity entries by code.

The legacy `vibelang.diagnostics` key reports `EK3009`. Run `vibelang --fix` to migrate configurable maps; remove obsolete nonconfigurable entries first. Other legacy options, including `vibelang.tracing` (`"none"`, `"exported"` or `"all"`), remain separate. See [Diagnostic severities](/setup/vibelang-cli#diagnostic-severities).

For example, a legacy `EK4406` policy entry cannot appear in `vibe.severities`; remove it before migrating the map. `EK9100` is editor-only and warns by default; it requests a written type for the text-only projection and is not reported by the CLI.

Unknown or retired warning codes cannot be configured. Remove an `EK1016` entry: the warning for an unused `main` was retired when `main` became an ordinary function (VIP-26).

### Effect.gen in direct style

An effect function expresses an `Effect.gen` program directly: each `yield* e` becomes `try e`, including an Effect value such as a service key or a `Config` descriptor:

```ts
// fragment
export const greet = (id: string) =>
  Effect.gen(function* () {
    const users = yield* Users
    return `Hello, ${yield* users.find(id)}`
  })
```

```vibe
// fragment
export const greet = effect (id: string) => {
  const users = try Users
  return `Hello, ${try users.find(id)}`
}
```

Use an effect function for a sequence with parameters, and `effect { … }` for an Effect argument, such as `Layer.effect`'s second argument. Keep unrun Effect values intact. A `throw` in effect code fails the Effect with a typed error; plain and `async` callbacks keep JavaScript's exception semantics.

Apply every fix in a project, then compile as the rest of the command says:

```sh
npx vibelang -p tsconfig.json --fix --noEmit
```

`--fix` writes what the prelude makes shorter: it removes an import of one of Effect's modules under its own name, as `import * as Console from "effect/Console"`, `import { HttpRouter } from "effect/http"`, or `import { FileSystem } from "effect/FileSystem"` are, writing a use the module's name cannot stand for as `FileSystem.FileSystem`. The report counts these as `prelude import` and `module export`. In a project that emits declarations, `--fix` keeps what the declaration file writes: an import that the file's declaration file keeps stays when it is spelled otherwise than `import { Schema } from "effect"`, so `import * as Schema from "effect/Schema"` stays beside `export const Value: Schema.Codec<unknown>`, and `import * as DateTime from "effect/DateTime"` beside a local `type NonNull<V> = V extends DateTime.Utc ? string : V` that an export names, and EK4833 keeps a `never` written in an exported statement, writing `Effect.Effect<void, never, never>` as `void!never!never`. The declaration file then matches the one the TypeScript emitted. It prints each file it changes, with its fixes by code, and writes the files only after it checks the fixed program: a fix that would add an error is listed as not fixed, and the file keeps its other fixes. Interrupted, it writes nothing. It fixes only what the project reports, so the `vibe.severities` setting and the legacy comments below choose what it touches; `// @vibelang-diagnostics-next-line EK4833:off` keeps one line as written. It rewrites only the project's own files: a workspace dependency's `.vibe` source that the project imports through its package keeps its text, and the compilation still reports its diagnostics. A second run finds nothing to fix. `--fix` cannot be combined with `--build` or `--watch`.

A service-class fix requires a literal key. A dynamic key stays as written, including its evaluation during class initialization.

When a fix removes the last value imported from another module, it keeps a side-effect import in the same position. Removing an unused binding must not remove that module's initialization.

Normalization continues until no accepted fix remains, even when nested edits overlap for more than sixteen rounds. If a rewrite repeats a source state, the command reports non-convergence and writes no files.

A direct `extends` or `implements` entry retains its named type, such as `Effect.Effect<number>`. Effect types inside another base's type arguments can still shorten, as in `Holder<number!!>`.

Fixes retain field comments and comments before unwrapped succeed/fail arguments. If a proposed rewrite cannot retain its comments, neither the editor nor --fix applies it.

## Effect language service rules

`@effect/language-service` 0.87.5 has 108 diagnostics and editor features. The table maps rules to VibeLang forms and existing EK diagnostics. Effect functions use `try` to run Effects, and `catch` expressions handle failures. The table also marks features not implemented.

EK4801-EK4825 are lint. Each has a default, error, warning, or off, and the historical port codes below remain available through legacy diagnostic comments. Configure assigned imported `EK38xx` codes through `vibe.severities`; core errors cannot be turned off. A later comment overrides an earlier one; within one comment, a code named on its own overrides `*`. Words after the codes are prose, and punctuation ends a category, so `// @vibelang-diagnostics-next-line EK4804:off: generic error` keeps its reason:

```vibe
effect function discard() {
  // @vibelang-diagnostics-next-line EK4804:off
  throw new Error("unused")
}
// Output: 0
```

`// @vibelang-diagnostics EK4818:warning` applies from its line to the end of the file; `*` names every adjustable code. Language diagnostics report in `.vibe` files, configuration diagnostics in config files; a `.ts` file keeps TypeScript's verdict. `vibelang` also runs Effect's own rules, copied from `@effect/tsgo`, on selected `.ts` and `.vibe` inputs, keeping the pinned upstream rule/file eligibility and declaration/library exclusions ([Lint Effect code](/setup/vibelang-cli#lint-effect-code)). In a `.vibe` file, a rule this table marks "Not needed" or "Covered" does not run, imported rules report their assigned `EK38xx` codes and rule names, at the configured severity. A rule's severity comes from its code's entry in `vibe.severities`, else the repository's existing Effect language-service configuration, else the rule's default.

## Debug stack traces

Build with `"sourceMap": true` in `compilerOptions`, then run `node --enable-source-maps dist/main.js`. Source maps translate JavaScript locations to `.vibe` locations. They do not record the logical caller chain.

VibeLang adds no spans of its own, so a defect can show only one frame, even with source maps enabled. Wrap work that needs a meaningful operation name in `try withSpan(effect { ... }, "checkout")`. More spans add runtime work.

The Node runner can exit with only `Error: message`. For a debugging run, call your application's exported `main` from a TypeScript entry and print the rejected error's stack:

```ts
// debug.ts
// fragment
import { Effect } from "effect"
import { main } from "./app.vibe"

Effect.runPromise(main()).catch((error: unknown) => {
  console.error(error instanceof Error ? error.stack : error)
  throw error
})
```

Include `debug.ts` in the project, compile it with `vibelang`, then run `node --enable-source-maps dist/debug.js`. Export the application Effect from `app.vibe` and call its runner from a separate entry module, so importing `app.vibe` does not start execution. This entry prints the underlying JavaScript stack and rethrows to preserve the failure exit status. Tracing and named spans add logical Effect call context.

## Lint and build integration

Type-check with `vibelang --noEmit`. The compiler owns type and language diagnostics in the terminal, editor, and Vite overlay. The local `vibelang-vite` package supports Vite 7 and 8 and Vitest 5. It runs one whole-project compiler subprocess on the first request and after edits, serves JavaScript and source maps, and invalidates loaded `.vibe` modules and their importers; it does not use `vibelang --api`.

```ts
// TypeScript (.ts)
// vitest.config.ts
import { defineConfig } from "vitest/config"
import vibelang from "vibelang-vite"

export default defineConfig({
  plugins: [vibelang()],
  test: { include: ["src/**/*.test.vibe"] }
})
```

The starter already includes this configuration. `bun run test` checks and compiles source tests without a prior build. See [TestClock](/testing/063-testclock) for tests with virtual time.

Lint `.vibe` files with ESLint through `vibelang/eslint`, the parser the `vibelang` package ships. The compiler parses each file, and ESLint gets the tree typescript-eslint gives it for TypeScript: typescript-eslint's rules and plugins such as `eslint-plugin-import`, `eslint-plugin-jsdoc`, and `eslint-plugin-unicorn` apply unchanged. Install `eslint` and `typescript-eslint` 8 beside `vibelang`; the parser uses typescript-eslint's scope analysis.

```js
// eslint.config.js
import tseslint from "typescript-eslint"
import vibelang from "vibelang/eslint"

export default tseslint.config({
  files: ["src/**/*.vibe"],
  extends: [tseslint.configs.recommended],
  languageOptions: { parser: vibelang }
})
```

Reports, fixes, and `// eslint-disable-next-line` comments land on the `.vibe` text. Rules that need type information, such as `@typescript-eslint/no-unnecessary-type-assertion`, cannot run on a `.vibe` file, since no TypeScript program loads one: enable them for `.ts` files only and check types with `vibelang --noEmit`. EK4801-EK4825 stay in the compiler and the language server. To see the tree a rule reads, run `vibelang --estree main.vibe < main.vibe`.

Find unused files, exports and dependencies in `.vibe` files with [Knip](https://knip.dev) through `vibelang/knip`, a Knip [compiler](https://knip.dev/features/compilers). It gives Knip each `.vibe` module's imports, re-exports, dynamic imports and exports, and the members it reads through a namespace import, from the compiler's ESTree. Knip takes compilers only from a configuration that is code:

```js
// knip.config.js
import vibelang from "vibelang/knip"

export default {
  compilers: { vibe: vibelang },
  // The declaration sidecars vibelang writes beside .vibe files are its output.
  ignore: ["**/*.d.vibe.ts"]
}
```

Knip then resolves `./x.vibe`, reports an unused export of a `.vibe` file at its line, and counts `vibelang-runtime`, which every compiled module imports, as used. The migrate flow writes this configuration, moving the settings of a `knip.json` into a `knip.config.ts`.

Typed lint of `.ts` files needs the types of the `.vibe` modules they import. typescript-eslint builds its program with the `typescript` it installs, which cannot read a `.vibe` file, so a type from one, imported directly or through a `.ts` barrel, is unresolved there, and type-aware rules report code that `vibelang -p` accepts, such as a non-null assertion the compiler needs. Give typescript-eslint the program `typedProgram` builds instead of `project` or `projectService`:

```js
// eslint.config.js
import tseslint from "typescript-eslint"
import vibelang, { typedProgram } from "vibelang/eslint"

export default tseslint.config(
  {
    files: ["src/**/*.ts"],
    extends: [tseslint.configs.recommendedTypeChecked],
    languageOptions: {
      parserOptions: { programs: [typedProgram({ project: "tsconfig.json", tsconfigRootDir: import.meta.dirname })] }
    }
  },
  {
    files: ["src/**/*.vibe"],
    extends: [tseslint.configs.recommended],
    languageOptions: { parser: vibelang }
  }
)
```

Without `project`, `typedProgram()` discovers the nearest config starting at `tsconfigRootDir` (the working directory by default). It checks `vibe.config.json`, `tsconfig.json`, then `jsconfig.json` in each directory before searching its parent. An explicit `project` selects that file.

`typedProgram` returns the project's TypeScript program, from the `typescript` the project resolves, in which each `.vibe` module reads as the declaration `vibelang` writes for it. A module of another workspace package compiles with that package's `tsconfig.json`, as the loaders compile it. It runs `vibelang` once per project, the first time the program reads one of its modules, and throws when a project does not compile, since typed lint would then have no types for its modules.

Forms whose TypeScript long form would mislead a rule have their own node types, which rules and `no-restricted-syntax` selectors can name:

| Form | ESTree node |
| --- | --- |
| `A!E!R` | `VibeEffectType` with `success`, `failure`, and `requirements` |
| `x \|> f(%)` | `VibePipeExpression` with `left` and `right`; `%` is `TopicReference` |
| `x catch () => fallback`, `x catch (e) => recover(e)` | `VibeCatchExpression` with `expression` and `handler` |
| `provide AppLive, Random.Random = seeded { ... }` | `VibeProvideStatement` with `providers` and `body`; `Random.Random = seeded` is `VibeServiceProvider` |
| `uninterruptible { ... }`, `restore { ... }`, `interruptible { ... }` | `VibeMaskStatement` with `kind` and `body` |

For example, `VibeCatchExpression > Literal.handler[value='']` selects a recovery to an empty string.

Node types for the VIP forms, such as effect functions, `effect { }` blocks, prefix `try`, `try.all` and its siblings, and the `fork` forms, are pending VIP-34's tooling implementation.

Declaration forms keep the TypeScript the checker reads: `error NotFound { id: string }` is a class with those fields, `service` declares a service key, and `schema User { ... }` is a `const User` typed by its fields. The parser leaves the names it writes for the checker, such as a `match`'s temporaries, out of scope analysis, so no rule reports a name the author did not write. A Vite Plus integration and a VibeLang Oxlint configuration are not shipped.

## Debugging in editors

```vibe
effect function tracedSample() {
  return try withSpan(sample(), "sample")
}
// Output: sample
```

Add spans where an execution boundary should appear in telemetry. VibeLang adds no spans of its own: name each one with `withSpan`. Effect's `DevTools` layer from `effect/devtools`, with its VS Code extension, shows fibers and logical span stacks across suspensions.

`vibelang` with `sourceMap` enabled, and the Vite plugin, map emitted JavaScript directly to `.vibe` positions. Debuggers that read standard source maps map breakpoints and paused frames to `.vibe`: VS Code's JavaScript debugger, Chrome and Edge DevTools, and JetBrains IDEs.

Compiled functions and producers keep their source names. The JavaScript stack shows the active frame above Effect's run loop. Stepping over a pausing `try` can enter the run loop; set a breakpoint on the next source line. Use spans for the logical call chain. When reporting a problem, include the Effect version, inferred contract, and diagnostic.
