# Managing Services

A service is a named capability a program uses without passing an implementation through every function. `service` declares its key and members' contracts; looking up its implementation with `try` adds the identifier to the `R` channel.


## Declaring typed service keys

```vibe
service Sequence {
  next(): number!!
}

service Reporter {
  write(message: string): void!!
}

effect function stringify(value: unknown) {
  return try Effect.try(() => JSON.stringify(value))
}
// Output: ticket-17
```

A service has no superclass or type parameters, and every instance member is abstract. Methods state full contracts, having no body to infer from; `readonly` value members are allowed. Static fields can hold layers or other helpers.

Services are nominal: the compiler derives the key from package, module path, and declaration name, so two services with identical members are different dependencies. To keep a key, such as one a `Context.Service` class wrote before migrating, write it in the body: `static readonly key = "app/Users"`. A `key` that is not `static readonly` with a string literal is `EK3008`. An `abstract class` is an ordinary TypeScript class; one written as a service draws `EK4854`, whose fix, which `vibelang --fix` applies, writes the `service` declaration with its members and key. Implement one with an object literal or a class that `implements` its `.Shape`; don't construct, extend, or use `instanceof` on it.

## Declaring a service of any shape

```vibe
interface SearchApi {
  find(query: string): string!!
}

class Search extends Context.Service<Search, SearchApi>()("app/Search") {}
class Prefix extends Context.Service<Prefix, string>()("app/Prefix") {}

effect function lookup(query: string) {
  const prefix = try Prefix
  const search = try Search
  return `${prefix}${try search.find(query)}`
}
// Output: > hit:vibe
```

Use Effect's `Context.Service` class for a service whose implementation has any type: an interface declared elsewhere, a primitive such as `string`, or a function type. `class Search extends Context.Service<Search, SearchApi>()("app/Search") {}` declares a key with an explicit identity. Its body can hold static members, such as `static readonly layer = Layer.succeed(Search, impl)`; declare implementation members in `SearchApi`. Read the implementation with `const search = try Search`, then run an Effect-returning member with `try search.find(q)`; `try Prefix` returns the string implementation. The type `Search` is the service's identifier, so type an implementation `SearchApi` or `Context.Service.Shape<typeof Search>`.

## Requesting and supplying implementations

```vibe
effect function nextLabel() {
  const sequence = try Sequence
  return `ticket-${try sequence.next()}`
}
// string!!Sequence

effect function fixedLabel() {
  return try provideService(nextLabel(), Sequence, {
    next: effect () => 17
  })
}
// string!!

effect function readImplementation() {
  const sequence = try Sequence
  return try sequence.next()
}
// number!!Sequence
// Output: ticket-17
// Output: ticket-23 23
```

A service can declare `static readonly defaultValue = () => implementation` to supply an implementation without a provider. It compiles to a `Context.Reference`. The returned implementation is checked against the service shape, as with `Layer.succeed`. For `Layer.succeed`, the compiler reports a shape mismatch as a TypeScript error, an excess member failure as `EK9201`, and an undeclared call-time requirement as `EK3101`. Support for the new `defaultValue` form arrives with the compiler's VIP implementation.

`try Sequence` looks up the implementation, to capture it or read value members; `try sequence.next()` runs its Effect-returning method. Supply every requirement before running the program.

```vibe
service Settings {
  baseUrl: string
}

effect function endpoint(path: string) {
  const settings = try Settings
  return `${settings.baseUrl}/${path}`
}
// string!!Settings
// Output: https://example.test/tickets
```

Read value members from the implementation, as `settings.baseUrl` after `const settings = try Settings`. Looking up a service adds it to `R` whatever its members return: `const path = try Path; path.join(a, b)` returns a plain string and still requires Effect's `Path` service. Wrap a synchronous member call that may throw with `Effect.try` and run it with `try`; wrap a Promise with `tryPromise` and run it with `try`. A member that is itself an Effect value runs with `try`, as in `try terminal.readLine`.

`provideService` removes the dependency only within its program. Nested overrides are local, a captured implementation stays the same object across later overrides or pauses, and forked fibers inherit the context present when they start.

## Service identifiers and shapes

```vibe
type SequenceImplementation = Sequence.Shape
type SameImplementation = Context.Service.Shape<typeof Sequence>
```

A service has two types, as an Effect `Context.Key` has, because it is Effect's own `Context.Service` class. As a type, `Sequence` is the service's identifier, which carries its key, so neither another service with the same members nor a structural type such as `{ next(): number!! }` can stand for it in `R`. `Sequence.Shape`, which Effect spells `Context.Service.Shape<typeof Sequence>`, is the members alone, the type of an implementation. `Layer.succeed`, `Layer.effect`, `provideService`, `provide Sequence = …`, and a `defaultValue` factory check an implementation against the shape, and `implements Sequence.Shape` in a `.vibe` file checks a class against it.

`try Sequence` returns the implementation typed as the shape, as `yield* Sequence` does. Type a parameter or a default implementation `Sequence.Shape`; a parameter typed `Sequence` takes the identifier, as in Effect TypeScript. A TypeScript class implements the emitted service with `implements Context.Service.Shape<typeof Sequence>`.

Providers infer and check the implementation from the key argument, so most layers don't need either name. At a TypeScript boundary, the shape describes the emitted implementation's Effect-returning methods.

## Combining multiple dependencies

```vibe
effect function announceTicket() {
  const label = try nextLabel()
  const reporter = try Reporter
  try reporter.write(`Created ${label}`)
  return label
}
// string!!Sequence | Reporter

const SequenceTest = Layer.succeed(Sequence, {
  effect next() { return 17 }
})
const ReporterTest = Layer.succeed(Reporter, {
  effect write(_message) {}
})

effect function testAnnouncement() {
  provide Layer.merge(SequenceTest, ReporterTest) { return try announceTicket() }
}
// Output: "ticket-17"
```

A union in `R` needs both capabilities. Layers supply the group together; `Layer.merge` combines independent layers, and `Layer.provide` feeds one layer's outputs into another's construction requirements. Inputs no argument provides stay requirements of the resulting layer, reported as missing where a runner or contract needs them satisfied. For a small local override, nest direct service provision.

```vibe
const testContext = Context.add(
  Context.make(Sequence, { next: effect () => 17 }),
  Reporter,
  { write: effect (_message) => {} }
)

effect function testWithContext() {
  provide testContext { return try announceTicket() }
}
// Output: ticket-17
```

A `Context` holds existing implementations; a `Layer` describes how to build them. A `provide` block, like `Effect.provide`, accepts either. `provide` is a statement: using it as an expression, as in `const ticket = provide testContext { … }`, is EK1017; return the value from inside its block. Keep resource-owning implementations within the lifetime that created them.

## Requesting optional services

```vibe
effect function optionalAnnouncement(message: string) {
  const reporter = try serviceOption(Reporter)
  if (Option.isNone(reporter)) return false
  try reporter.value.write(message)
  return true
}
// boolean!!
// Output: false
// Output: hello
// Output: true
```

`serviceOption` returns `None` when an application service is absent and `Some(implementation)` when present, without adding the service to `R`. Calling a found implementation still carries the method errors and call-time requirements the service declares.

## Handling dependencies between services

```vibe
service ReportSettings {
  prefix: string
}

const ReporterLive = Layer.effect(Reporter, effect {
  const settings = try ReportSettings
  return {
    effect write(message) {
      try Console.log(`${settings.prefix}: ${message}`)
    }
  }
})
// Layer<Reporter, never, ReportSettings>
// Output: audit: ready
```

Capture construction dependencies in the layer factory: `try reporter.write(...)` then requires only `Reporter`, because the implementation retains `settings`. Looking up `try ReportSettings` inside `write` would add a call-time requirement, which its declared `R = never` rejects.

## Coming from Effect

`service` declarations replace hand-written `Context.Service` declarations in `.vibe` files. A `Context.Service` class there draws EK4831, whose quick fix writes the `service` declaration, keeping the class's key as `static readonly key`, when its members are written in the class's type argument ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). Support for the new forms arrives with the compiler's VIP implementation. `try ServiceName` replaces yielding the key in a TypeScript generator to get its implementation; `try implementation.method()` runs an Effect-returning method.
