# Managing Services

Write the `service` keyword without Unicode escapes (`TS1260`). Escaped service names and ordinary identifiers keep working.

A service is a named capability a program uses without passing an implementation through every function. `service` declares its key and members' contracts; looking up its implementation with `try` adds the identifier to the `R` channel.


The transitional `static readonly default = implementation` form keeps its `EK4855` migration warning. For a local service, write the equivalent native `Context.Service` class and retain the cached static field, its key and its value/type reads. This preserves eager initialization and does not introduce a missing-provider fallback. The legacy field needs an initializer; `static readonly default: Shape` without a value is `EK0902`.

## Declaring typed service keys

```vibe
service Sequence {
  next(): number!!
}

service Reporter {
  write(message: string): void!!
}

effect function stringify(value: unknown) {
  return try Effect.try(() => JSON.stringify(value))
}
// Output: ticket-17
```

Export a service with `export service Counter { readonly value: number }`, or declare it and write `export { Counter as default }`. `export default service Counter { }` reports `EK0905`; an ordinary expression whose variable is named `service` can still follow `export default`.

An implementation retrieved with `try Service` or typed as `Service.Shape` can be spread into another object. The spread retains its method signatures; replacements must still satisfy the declared result types. Ordinary class prototype methods are not copied by object spread.

Separate service method and property signatures with `;`, a newline, or `,`, as in a TypeScript interface. A trailing comma is allowed.

A service has no superclass or type parameters, and every instance member is abstract. Methods and properties declare the service's shape as in a TypeScript `interface`; `readonly` value members are allowed. Write intended types; a default factory does not infer missing member types. Its only static members are `static readonly key` and `defaultValue`; keep layers and helpers in ordinary declarations beside it. Two members on one line with no separator are `EK0908`, which requires `;`. Value members are mutable unless declared `readonly`. When upgrading a legacy service that used the old readonly default, write `readonly` on those fields and their nested type members to preserve the earlier declarations. Other static fields, methods, accessors and initialization blocks report `EK0902`. An instance method body, a value initializer, or an accessor is `EK0902`; declare the member's contract and implement it in a layer.

Service contracts also work with `noUnusedLocals` and `noUnusedParameters`. Their bodyless signatures describe an implementation; unused checks still apply to actual private implementation members.

Service methods and properties accept semicolons, commas or line breaks between members. Formatting accepts these separators and preserves the member types and comments, including commas inside tuple, generic and function types.


Bodyless properties and methods use interface syntax. Class-only modifiers such as `public`, `private`, `protected`, `abstract`, `declare`, `accessor`, `override`, `async` and `effect`, private names such as `#count`, and definite assignment assertions such as `count!: number` are `EK0902`. `readonly` belongs only on a property, not a method. Remove a modifier or assertion while retaining comments and the written contract; a private name needs an explicit public name.

For an Effect-returning operation, write `read(): number!!`. A signature written as `effect read(): number!!` reports one `EK0902`; its manual change removes `effect` and preserves the return contract and comments. Supply the implementation in a layer.

`Users.Shape` names the written member object directly, so service contracts can refer to their own or another service's `.Shape`. A service cannot declare type parameters or capture an enclosing type parameter in a member contract (`EK3005`): different specializations would share one runtime key. A rejected member does not hide `EK3005` on the declaration's type parameters. Use a concrete contract or a member-local generic method independent of outer parameters. An unused argument does not capture a type parameter: `Phantom<T>` is allowed when `interface Phantom<U> { n: number }` never uses `U`. A foreign callable's written `@throws` contract also counts when checking captures. Explicit `this` parameter types count too, including in callable properties, nested types, aliases and whole-shape annotations; a member-local generic receiver remains allowed. Conditional branches count too: `U extends string ? T : number` captures an enclosing `T` even when `U` belongs to the member.

Type guards and assertion signatures also retain their result contract: `value is T` and `asserts value is T` capture an enclosing `T`, even though their ordinary return types are `boolean` or `void`.

A service declaration takes no `extends` or `implements` clause (`EK0904`): its identity is its key. Compose shapes with types instead, such as `find: Base.Shape["find"]`.

A call signature in a service body is rejected with one `EK0902`, including when the service has a written shape. Independent errors in its key or type parameters are still reported.

A service method may declare a plain return type, such as `lookup(): number`, or an Effect return type, such as `lookup(): number!!`, as a `Context.Service` shape can. An omitted member type follows TypeScript, as in an interface: under `noImplicitAny`, `read()` is `TS7010` and an untyped property is `TS7008`; with the option off they are `any`. Explicit `read(): any` is valid under strict checking. VibeLang adds no diagnostic of its own and infers no Effect contract; fix `TS7010` by writing the intended return type.

At module or namespace scope, `Users.Shape` names a service's implementation type. A function or block cannot declare that companion namespace: write `Context.Service.Shape<typeof Users>` for a local service instead. Within the service's own instance member type, `Users.Shape` remains a type-only self-reference. A member-local type parameter named `Users` shadows that service name, as in TypeScript.

Namespace services retain native key helpers such as `Tools.Users.of(implementation)`. Their emitted declarations also keep an explicit `Context` import when they use it.

Copying a service value into a `const` or an object property keeps the same service identity. The restrictions on `new`, `extends` and `instanceof` apply through those aliases and through parentheses too. An intersection type such as `typeof Users & { readonly extra?: number }` retains that identity: construction is `EK3003`, inheritance is `EK3002`, and `instanceof` or a class pattern is `EK3004`. Obtain the implementation with `try Users` and inspect its members instead. The identifier type `Users` in `R` is distinct from `typeof Users`; combining that identifier with an ordinary callable or constructor does not make the value an alias of the key.

A generic parameter constrained to a key's value type, such as `Key extends typeof Users`, retains that key identity. The same misuse diagnostics apply through chained constraints, intersection bounds and object properties. An indexed access such as `Box["key"]`, where `Box extends { key: typeof Users }`, also retains that identity, including tuple and array element constraints. A union whose alternatives are all service-key value types retains the same misuse checks. Conditional aliases, including a conditional with the same key in both branches and `Extract<…>`, preserve these checks when every possible value is a service key. Narrowing away `null` and `undefined`, a non-null assertion, or `NonNullable<Key>` retains the same checks and any unique key identity. A union containing an ordinary constructor keeps TypeScript's own checks. A constraint on the identifier type `Users` in `R` does not turn an ordinary function or constructor into a service key.

A `service` body cannot contain constructors or index signatures, such as `[name: string]: Value`; each reports `EK0902`. Declare named properties and methods instead. For a dictionary implementation, declare its type separately and use an explicit `Context.Service` class, as below.

Construct signatures directly in a service body, such as `new(): T!!` and `new<T>(value: T): T!!` are `EK0902`: declare a named factory method or a property whose value is a constructor instead. A method literally named `new` can use a quoted name, `"new"(): T!!`.

A call signature directly in a service body, such as `(value: string): string`, is `EK0902`: declare a named method, or a property whose type is a function, such as `format: (value: string) => string`.

A `get` or `set` accessor without a body, such as `get value(): number`, is `EK0902`, with or without a modifier such as `abstract`: declare a property, such as `readonly value: number`, or a method.

A service needs its body, even an empty one: `service Users` alone is `EK0906`. A whole-shape declaration also needs braces: write `service Prefix: string {}` or `service Format: (value: string) => string!! {}` in a named package. A service creates a run-time key, so it cannot be ambient: `declare service Users { … }`, or a service inside a `declare namespace` or `declare module`, is `EK0907`. Two members on one line need a separator, `;` or a line break: `a: number b: string` is `EK0908`, so write `;`.

For `EK0908`, insert `;` before the following member's comments and JSDoc, retaining its `@throws` contract.

Services are nominal: the compiler derives the key from package, module path, and declaration name, so two services with identical members are different dependencies. To keep a key, such as one a `Context.Service` class wrote before migrating, write it in the body: `static readonly key = "app/Users"`. Without a type annotation, `Users.key` retains its string literal type when returned from a plain or `effect` function, as the native `Context.Service` key does. If a local `let value = Users.key` is reassigned to another string, write `let value: string = Users.key` to keep the mutable binding. A written key type and a `defaultValue` reference keep their existing types. A `key` that is not `static readonly` with a quoted string literal is `EK0901`. A type annotation is allowed, as in `static readonly key: string = "app/Users"`; a template literal or computed initializer is not. A malformed key reports `EK0901` without a redundant error about the generated class’s static side; independent type and name errors remain. An `abstract class` is an ordinary TypeScript class; one written as a service draws `EK4854`, write a `service` declaration with its members and key. Implement one with an object literal or a class that `implements` its `.Shape`; don't construct, extend, or use `instanceof` on it. A rejected key still reports independent TypeScript errors in its initializer and type annotation.

When migrating, preserve every original explicit key; deriving a new key can break providers across package boundaries or persisted identities.

A derived key concatenates the string package name, `/`, the package-relative file path without its final extension, `#`, and the service name. An empty package name is still a string: `service Users` in `src/users.vibe` derives `/src/users#Users` when `package.json` contains `"name": ""`. To preserve the directory-prefixed identities produced by older compilers for those packages, write the old keys explicitly before upgrading consumers.

An explicit string-literal key keeps its value, including `""`. It is used for runtime lookup, the emitted key type, and duplicate-key checks; an empty literal does not request a derived key.

Derived keys require a module-scope declaration in a package whose `package.json` has a string `name`. A local or block-scoped service, or one outside a named package, reports `EK0903` when it omits `static readonly key`. Insert an explicit key while preserving the declaration's current runtime identity. A namespace at module scope can still derive its services' keys. A function-local service still needs an explicit key when `noEmit` is enabled or `declaration` is disabled. An explicit key works in each scope, including outside every package; `EK0901` instead diagnoses a malformed written key.

The special `key` and `defaultValue` property headers allow only `static readonly`, without `public`, `private`, `protected`, `declare`, optional `?` or definite `!` markers. `defaultValue` also needs an initializer. Malformed headers report `EK0902`; invalid key literals or a missing `readonly` on `key` use the key-validation diagnostic instead. These rules also apply to a written whole shape, `service Name: Type { … }`. Remove extra header modifiers and `?` or `!`, preserving an existing `readonly` initializer and type. A missing factory needs an explicit implementation. Adding `readonly` to an old mutable `defaultValue` chooses `Context.Reference` fallback behavior, so that change requires an explicit migration.

A `defaultValue` initializer has ordinary class-field context, even when its service is declared inside an effect function. A `try` expression there is `EK0501`. Compute an effectful input before the service declaration, then capture the resulting value in its `() => Shape` default factory.

A service's shape may have properties named `key` or `defaultValue`. They are ordinary implementation members and can coexist with the service's `static readonly key` and `static readonly defaultValue`. Read them from the implementation returned by `try Effect.service(ServiceName)`.

Service members form an object type, so a written `this` type there gets TypeScript's `TS2526` rather than referring to a service instance. For recursive members, name the implementation type; a separately declared interface can use its ordinary polymorphic `this` type and become a service's shape. Ordinary classes keep their `this` types.

A custom `service` has one key across every instantiation of its enclosing function or class. Its implementation contract must therefore use concrete types: capturing an enclosing type parameter reports `EK3005`, including in a whole-shape annotation such as `service S: { value: T } { ... }`. For generic operations, give individual members their own generic parameters. A rejected member does not create a service contract; capture checks continue on the other valid contracts.

Declaration output gives generated `Context` imports a free local name when a nested namespace or type shadows `Context`. Authored namespace members keep their names.

## Declaring a service of any shape

Only the written shape participates in generic-capture checking; rejected body members add no contract.

Write `service Database: DatabaseService { static readonly key = "app/Database" }` to use an existing type directly. The annotation can name any TypeScript type. Its body contains only `key` and `defaultValue`. Index signatures and constructors in that body report `EK0902`. Each member is checked independently: an invalid member does not hide `EK0901` on a separate malformed key. Write an index signature in the supplied shape type and put initialization in the layer that creates its implementation; a constructor has no automatic relocation. This form emits the written type directly, without a private shape helper or public `Database.Shape` namespace. Outside the declaration, write the type or `Context.Service.Shape<typeof Database>`. Within its own body, `Database.Shape` denotes the annotation. Body-only services retain their public `Shape` namespace.

```vibe
interface SearchApi {
  find(query: string): string!!
}

service Search: SearchApi { static readonly key = "app/Search" }
service Prefix: string { static readonly key = "app/Prefix" }

effect function lookup(query: string) {
  const prefix = try Prefix
  const search = try Search
  return `${prefix}${try search.find(query)}`
}
// Output: > hit:vibe
```

Write `service Name: Type { … }` when the implementation has a type declared elsewhere, a primitive such as `string`, a function, or another TypeScript type. The annotation supplies the whole shape, preserving its name and modifiers. The required body admits only `static readonly key` and `static readonly defaultValue`; keep layers and helpers beside the declaration. The written type passes directly to `Context.Service<Name, Type>`, or `Context.Reference<Type>` for a default, without an extra shape helper or namespace.

Read the implementation with `const search = try Search`, then run an Effect-returning member with `try search.find(q)`; `try Prefix` returns the string implementation. The type `Search` is the service's identifier; use `SearchApi` or `Context.Service.Shape<typeof Search>` for its implementation. Existing key, default, ambient and generic-capture rules apply.
The Effect TypeScript counterpart, `class Search extends Context.Service<Search, SearchApi>()("app/Search") {}`, has the same explicit key.


## Requesting and supplying implementations

```vibe
effect function nextLabel() {
  const sequence = try Sequence
  return `ticket-${try sequence.next()}`
}
// string!!Sequence

effect function fixedLabel() {
  return try provideService(nextLabel(), Sequence, {
    next: effect () => 17
  })
}
// string!!

effect function readImplementation() {
  const sequence = try Sequence
  return try sequence.next()
}
// number!!Sequence
// Output: ticket-17
// Output: ticket-23 23
```

A service can declare `static readonly defaultValue = () => implementation` to supply an implementation without a provider. It compiles to a `Context.Reference`. The returned implementation is checked against the service shape, as with `Layer.succeed`. For `Layer.succeed`, the compiler reports a shape mismatch as a TypeScript error, an excess member failure as `EK9201`, and an undeclared call-time requirement as `EK3101`. For a local key with an old `static readonly default`, the `EK4855` repair writes a native `Context.Service` class that retains the cached field, its reads and the shape's mutable members. Exported keys, commented service bodies and keys that also declare `defaultValue` require a manual native class migration.

A reference declared with a member body has `Flags.Shape` for its implementation and `typeof Flags` for its key value, but no `Flags` identifier type. Writing `let value: Flags` reports `TS2749`, as for Effect's `Context.Reference`; references do not appear in `R`. An import type such as `import("./flags.vibe").Flags` reports `TS2694`; use `typeof import("./flags.vibe").Flags` for the key value.

A service key has its native TypeScript properties. `Users.find(id)` does not look up an implementation and reports TypeScript's missing-property error; `Users.name` and `Users.key` still read the key. Write `(try Users).find(id)` to build a member's Effect, and `try (try Users).find(id)` to run it. The member program can also be the operand of `catch` or `|>`; the service lookup still happens explicitly. The old `EK4503` is retired; native property diagnostics apply.

`try Sequence` looks up the implementation, to capture it or read value members; `try sequence.next()` runs its Effect-returning method. Supply every requirement before running the program.

```vibe
service Settings {
  baseUrl: string
}

effect function endpoint(path: string) {
  const settings = try Settings
  return `${settings.baseUrl}/${path}`
}
// string!!Settings
// Output: https://example.test/tickets
```

Read value members from the implementation, as `settings.baseUrl` after `const settings = try Settings`. Looking up a service adds it to `R` whatever its members return, including when a `catch` handles a member's typed failure or a pipe transforms its Effect: `const path = try Path.Path; path.join(a, b)` returns a plain string and still requires Effect's `Path` service. Wrap a synchronous member call that may throw with `Effect.try` and run it with `try`; wrap a Promise with `tryPromise` and run it with `try`. A member that is itself an Effect value runs with `try`, as in `try terminal.readLine`.

`provideService` removes the dependency only within its program. Nested overrides are local, a captured implementation stays the same object across later overrides or pauses, and forked fibers inherit the context present when they start.

## Service identifiers and shapes

```vibe
type SequenceImplementation = Sequence.Shape
type SameImplementation = Context.Service.Shape<typeof Sequence>
```

A service has two types, as an Effect `Context.Key` has, because it is Effect's own `Context.Service` class. As a type, `Sequence` is the service's identifier, which carries its key, so neither another service with the same members nor a structural type such as `{ next(): number!! }` can stand for it in `R`. `Sequence.Shape`, which Effect spells `Context.Service.Shape<typeof Sequence>`, is the members alone, the type of an implementation. `Layer.succeed`, `Layer.effect`, `provideService`, `provide Sequence = …`, and a `defaultValue` factory check an implementation against the shape, and `implements Sequence.Shape` in a `.vibe` file checks a class against it.

`try Sequence` returns the implementation typed as the shape, as `yield* Sequence` does. The same lookup works for imported keys and inside exported `effect` functions. Type a parameter or a default implementation `Sequence.Shape`; a parameter typed `Sequence` takes the identifier, as in Effect TypeScript. A TypeScript class implements the emitted service with `implements Context.Service.Shape<typeof Sequence>`. The emitted declarations also export `Sequence.Shape`, so TypeScript callers can use that name directly. The key and public alias share a private named member type, preserving recursive shapes and their `readonly` members.

Providers infer and check the implementation from the key argument, so most layers don't need either name. At a TypeScript boundary, the shape describes the emitted implementation's Effect-returning methods.

## Combining multiple dependencies

```vibe
effect function announceTicket() {
  const label = try nextLabel()
  const reporter = try Reporter
  try reporter.write(`Created ${label}`)
  return label
}
// string!!(Sequence | Reporter)

const SequenceTest = Layer.succeed(Sequence, {
  effect next() { return 17 }
})
const ReporterTest = Layer.succeed(Reporter, {
  effect write(_message) {}
})

effect function testAnnouncement() {
  provide Layer.merge(SequenceTest, ReporterTest) { return try announceTicket() }
}
// Output: "ticket-17"
```

A union in `R` needs both capabilities. Layers supply the group together; `Layer.merge` combines independent layers, and `Layer.provide` feeds one layer's outputs into another's construction requirements. Inputs no argument provides stay requirements of the resulting layer, reported as missing where a runner or contract needs them satisfied. For a small local override, nest direct service provision.

```vibe
const testContext = Context.add(
  Context.make(Sequence, { next: effect () => 17 }),
  Reporter,
  { write: effect (_message) => {} }
)

effect function testWithContext() {
  return try Effect.provide(announceTicket(), testContext)
}
// Output: ticket-17
```

A `Context` holds existing implementations; a `Layer` describes how to build them. A `provide` block takes layers and `Key = value` entries, or a single `Context`. `testWithContext` passes its `Context` to `Effect.provide` directly, which works too. `provide` is a statement, not an expression: return the value from inside its block. Keep resource-owning implementations within the lifetime that created them.

## Requesting optional services

```vibe
effect function optionalAnnouncement(message: string) {
  const reporter = try serviceOption(Reporter)
  if (Option.isNone(reporter)) return false
  try reporter.value.write(message)
  return true
}
// boolean!!
// Output: false
// Output: hello
// Output: true
```

`serviceOption` returns `None` when an application service is absent and `Some(implementation)` when present, without adding the service to `R`. Calling a found implementation still carries the method errors and call-time requirements the service declares.

## Handling dependencies between services

```vibe
service ReportSettings {
  prefix: string
}

const ReporterLive = Layer.effect(Reporter, effect {
  const settings = try ReportSettings
  return {
    effect write(message) {
      try Console.log(`${settings.prefix}: ${message}`)
    }
  }
})
// Layer<Reporter, never, ReportSettings>
// Output: audit: ready
```

Capture construction dependencies in the layer factory: `try reporter.write(...)` then requires only `Reporter`, because the implementation retains `settings`. Looking up `try ReportSettings` inside `write` would add a call-time requirement, which its declared `R = never` rejects.

## Coming from Effect

`service` declarations replace hand-written `Context.Service` declarations in `.vibe` files. A `Context.Service` class there draws `EK4831`, which suggests the `service` declaration, keeping the class's key as `static readonly key`, when its members are written in the class's type argument ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). For a class the module exports, it writes `service Name: { … } { static readonly key = … }` with the type argument unchanged, so the package's declarations stay what they were; a class the module keeps to itself becomes `service Name { … }`. `try ServiceName` replaces yielding the key in a TypeScript generator to get its implementation; `try implementation.method()` runs an Effect-returning method.

Service members follow TypeScript interface typing. Omitting a method's return type gives `TS7010` under `noImplicitAny`; an untyped property gives `TS7008`. With that option disabled both are `any`, and an explicit `read(): any` works under strict checking. Write the intended type; no Effect return is required.

A service declaration keeps a written namespace import for `effect/Context` in its declaration file, including aliases such as `import * as Ctx from "effect/Context"`. Its generated base type then uses `Ctx.ServiceClass`. A locally shadowed alias uses a visible binding instead.

The public `Sequence.Shape` alias described above belongs to a member-body declaration. With a written whole-shape annotation, use its type or `Context.Service.Shape<typeof Sequence>` outside the declaration; the implicit `Sequence.Shape` name is confined to its own body. The same distinction applies to a reference declared with `defaultValue`.

The same declaration-import checks run with `noEmit` or `declaration: false`, because every VibeLang module has a sidecar. With `noUnusedLocals`, source checking takes priority: a binding left unread by the repair is removed.

For a class written as `class Database extends Context.Service<Database, DatabaseService>()("BetterAuth.Database") {}`, write the whole shape: `service Database: DatabaseService { static readonly key = "BetterAuth.Database" }`. It keeps the existing shape type and runtime key, without adding a shape helper or namespace.

An ordinary native `class Key extends Context.Service<…>` declares no `Key.Shape` namespace. Extract its implementation with `Context.Service.Shape<typeof Key>`, or use an explicitly declared TypeScript namespace. A member-body `service` declaration supplies its public `Shape` alias. The editor replaces an invalid non-generic native-key shape reference with a type import of Effect's extractor, preserving local bindings and foreign source files. An explicit namespace or type arguments are left for the owner to check.

Retired `service class Users { … }` declarations fail with `EK0909`. Remove only `class`, retaining the service key, shape and comments between the keywords.
