# Appendices

## Appendix A. Grammar

VibeLang's grammar is TypeScript's, plus three TC39 proposals and the productions below. This appendix is the only place a VibeLang production is written; chapters show examples and link here by production name. Pattern matching is pinned to commit `ba73ffe42f30f0cf56ece28bebdc28f955f2a52e` with its reconciliations ([Pattern matching](/spec/004-match)). Do expressions are pinned to `tc39/proposal-do-expressions` commit `3ef6d463b8163cbf222846b40d17178cca36e9e1` and the Hack pipe operator to `tc39/proposal-pipeline-operator` commit `5ac4dfd624e68b649e6f947885bf5ef67bac19f4`, each repository's head on 2026-10-28 (UTC), vendored in `vips/tc39-do-expressions/` and `vips/tc39-pipeline-operator/`. Names not defined here (`Block`, `Type`, `UnaryExpression`, `ConciseBody`, …) are TypeScript's or ECMAScript's. `"x"` is a token; `X?` is optional; `X*` repeats; `[no LineTerminator here]` and `[lookahead ∉ …]` are ECMAScript's restrictions.

### The `[Effect]` parameter

VibeLang adds one grammar parameter, `[Effect]`, with the contextual boundaries below, following [TypeScript’s parser](https://github.com/microsoft/TypeScript/blob/v5.9.3/src/compiler/parser.ts). The parameters and body of an `effect` function, arrow, method or producer, and the body of an `effect` block, parse with `[+Effect]`. The body of any source callable without an `effect` modifier parses with `[~Effect]`, retaining TypeScript’s own `[Await]` and `[Yield]` rules; an `async match` parses with `[~Effect, +Await]`, as a nested `async` function. Class heritage and computed class element names keep their enclosing source context. Class field and enum member initializers parse with `[~Effect]`, even inside an effect function. Ordinary TypeScript checks on computed field names still apply. Static blocks inherit `[?Effect]` for keyword reservation, but cannot execute Effects. A nested explicit Effect callable or block starts its own normal context.

The grammar parameter determines reservation; permission to execute additionally excludes parameter lists and `static` blocks. “Effect code” ([Running Effects](/spec/002-running)) is code parsed with `[+Effect]` that has that permission. A computed class key and an `extends` clause are effect code when their enclosing context is: `effect function f() { class C { [try key()]() { } } }` permits the `try`.

Under `[+Effect]`:

- `fork` and `join` are reserved words, as `await` is under `[+Await]` (VIP-17, amended). No next-token test applies. An `IdentifierReference`, `BindingIdentifier` or `LabelIdentifier` can't be `fork` or `join`, so `join(parts)` is always a [JoinExpression](/spec/900-appendices#joinexpression), `join - 1` joins `-1`, and a parameter or local named `join` is a syntax error (`EK1702`). A plain or `async` arrow head inherits the enclosing `fork`/`join` reservation, including in an Effect callable's parameter list, through its binding names, defaults and destructuring; the `async` prefix does not reset the head. This follows ECMAScript's [arrow](https://tc39.es/ecma262/#sec-arrow-function-definitions) and [async-arrow head](https://tc39.es/ecma262/#sec-async-arrow-function-definitions) context rules. Both `const g = (join) => 1` and `const g = async (join) => 1` are `EK1702` there. Each arrow body then has its own source context: a plain body is `[~Effect, ~Await]`, an ordinary `async` body `[~Effect, +Await]`. A nested `function h(join) { }` resets the head as well as its body. Outside an enclosing Effect reservation, `fork` and `join` remain ordinary identifiers even in an ordinary `async` arrow's head and body: native async's own `await` reservation does not reserve these two names. They stay ordinary `IdentifierName`s, as `await` does: `parts.join(",")`, `o?.fork`, `{ join: 1 }` and `class { join() { } }` are names. After the keyword, `/` begins a regular expression, and the operand may follow a line break, as after `await`: `join` then `f` on the next line joins `f`.
- [TryExpression](/spec/900-appendices#tryexpression), [CatchExpression](/spec/900-appendices#catchexpression), [ForkExpression](/spec/900-appendices#forkexpression), [JoinExpression](/spec/900-appendices#joinexpression), [TryAll](/spec/900-appendices#tryall), [ForConcurrent](/spec/900-appendices#forconcurrent), [ForTry](/spec/900-appendices#fortry), the interruption blocks and [ProvideStatement](/spec/900-appendices#providestatement) parse in this context. In a parameter list or `static` block, a recognized execution form receives its applicable placement diagnostic ([Running Effects](/spec/002-running#static-rules)). Initializers parsed with `[~Effect]` follow the recovery rule below.

Under `[~Effect]` those productions don't exist, and `fork` and `join` are identifiers. As TypeScript parses `await x` in a plain function to report "only allowed in async functions", a parser recovers by parsing these productions under `[~Effect]` and reports the construct's "outside effect code" rule, except where the tokens are also valid TypeScript, which keep their TypeScript meaning. A [ProvideStatement](/spec/900-appendices#providestatement) head is the exception: it wins in any code (decided detail 34), so the statement `provide / a / { }` in `function f(provide: number, a: number) { provide / a / { } }` is `EK1201`; after `return` no statement can start, so `return provide / a / { }` divides.


VIP-17’s outside-code identifier promise is contextual: a plain class’s static block keeps ordinary `fork`/`join` identifiers. This deliberately differs from ECMAScript’s unconditional `[+Await]` for static blocks; VibeLang reserves these two words only in the inherited Effect context, so module classification adds no global reservation. The same call syntax in an Effect-reserved static block is a recognized operation and receives `EK1701`.

The field and enum calls below are ordinary helper calls; the class head keeps the enclosing Effect context, and the nested block establishes its own. The Effect gives `Success([2, 3, 7])`:

```vibe [VibeLang]
// compiler-gap: pending VIP-1, VIP-2, VIP-5, VIP-17
import { Effect } from "effect"
function join(n: number): number { return n + 1 }
function fork(n: number): number { return n + 2 }
effect function contextBoundaries() {
  class Base {}
  class C extends (try Effect.succeed(Base)) {
    [try Effect.succeed("read")]() { return 1 }
    value = join(1)
    program = effect { return try Effect.succeed(7) }
  }
  enum E { A = fork(1) }
  const c = new C()
  return [c.value, E.A, try c.program] as const
}
class Plain { static { join(9); fork(9) } }
```

```ts [Effect]
import { Effect } from "effect"

function join(n: number): number { return n + 1 }
function fork(n: number): number { return n + 2 }
const contextBoundaries = Effect.gen(function* () {
  class Base {}
  class C extends (yield* Effect.succeed(Base)) {
    [yield* Effect.succeed("read")]() { return 1 }
    value = join(1)
    program = Effect.gen(function* () { return yield* Effect.succeed(7) })
  }
  enum E { A = fork(1) }
  const c = new C()
  return [c.value, E.A, yield* c.program] as const
})
class Plain { static { join(9); fork(9) } }
```

Execution stays forbidden in the initializer or static block itself:


### Contextual keywords

<a id="declaration-keywords"></a>**Declaration keywords.** `service`, `error`, `schema` and `data` follow TypeScript's contextual keyword `type`, whose alias declaration is `type` [no LineTerminator here] `BindingIdentifier`. This is the one rule for all four, written once as the production [DeclarationStart](/spec/900-appendices#declarationstart) and its five start productions under [Productions](/spec/900-appendices#productions).

Where a TypeScript declaration can start (a `StatementListItem`, or after `export`), a `DeclarationStart` begins that declaration, longest alternative first. Anything else is ordinary TypeScript, where the word is an identifier: `const error = …`, `catch (error)`, `const e = error as Error`, `return data as User[]`, `const ok = schema satisfies Schema.Top` and `error instanceof NotFound;` (a reserved word is not a `BindingIdentifier`). After the name, the declaration's production decides the rest, and line breaks may separate its tokens as in a TypeScript `class` or `type` declaration: a body's `{` and a `schema` alias's `=` may follow line breaks. The one production-specific rule is the bodyless `error` and `schema error` form, under [ErrorDeclaration](/spec/900-appendices#errordeclaration). No other line-break or disambiguation rule applies to these four words.

```text
service Users                 one service: the body follows the name, as a class body does
{ find(): User }
error Timeout                 one error declaration with the field id
{ id: string }
schema Code                   one alias, as `type Code` then `= …` is
= "a" | "b"
service as { a: string };     a service named as
service as T;  error as T;    syntax errors: `T` can't follow the declaration of `as`;
schema as T;  data as T;      write (service as T); for the TypeScript assertion
schema satisfies T;           a syntax error, as for `as`: write (schema satisfies T);
schema error = T              a schema named error: `=` is not a BindingIdentifier
schema error E { }            a schema error E
const e = error as Error      an assertion: not where a declaration starts
error instanceof NotFound;    an expression: `instanceof` is not a BindingIdentifier
error                         an expression statement: no name on the line
Timeout                       then another
```

**Other contextual keywords.** Each word below is a keyword only before the tokens listed, on the same line, and an ordinary identifier everywhere else. Each is tested wherever its production can appear.

`try` and `catch` are reserved words already; VibeLang gives them expression forms under `[+Effect]`. At the start of a statement, `try` followed by `{`, on the same line or not, is TypeScript's `try` statement, as in JavaScript.

#### EffectModifier

```text
EffectModifier = "effect"
               | "effect" [no LineTerminator here] "async"   (parses, then EK0105 rejects it)
               | "async" [no LineTerminator here] "effect"   (parses, then EK0105 rejects it)
```

Each two-word form needs a function, a method name, arrow parameters or an expression-position block after it, so TypeScript's forms keep their meaning: `async effect => 1` is an `async` arrow whose parameter is `effect`, `async effect() { }` is an `async` method named `effect`, and `effect async() { }` is an `effect` method named `async`.

A recognized `effect` modifier follows TypeScript’s `async` diagnostic recovery positions too. An `abstract` declaration, ambient `declare` context, or an `interface` or type literal member with that modifier is rejected with `EK0108` ([Functions](/spec/001-functions#static-rules)). Recognition is syntactic: identifiers named `effect` retain their ordinary member reading. Function/class overload signatures follow TypeScript’s ordinary admission and compatibility; generator overloads retain their native rejection.

#### EffectFunction

```text
EffectFunction = EffectModifier [no LineTerminator here] "function" Name? TypeParameters? Params ReturnType? Block
```

#### EffectFunctionOverload

```text
EffectFunctionOverload = EffectModifier [no LineTerminator here] "function" Name? TypeParameters? Params ReturnType? ";"   (function declarations only; TypeScript overload signatures and semicolon insertion)
```

Bodyless signatures follow TypeScript overload ordering, adjacent-implementation and compatibility checks, with the same name requirements as the corresponding `async` declaration. Function expressions, object-literal methods and arrows still require bodies. TypeScript rejects starred overload signatures, `abstract async` methods and ambient `async` declarations; the corresponding `effect` forms are rejected too.

#### EffectAccessor

```text
EffectAccessor = DecoratorList? Modifiers? EffectModifier [no LineTerminator here] ("get" | "set") ClassElementName Params ReturnType? Block   (parses, then the getter/setter rule rejects it)
```

`DecoratorList` is TypeScript's class decorator list and is admitted only on class elements, with TypeScript placement checks; an object-literal method has none. This applies to producer methods and rejected accessor recovery too.

`effect get x() { }` is an `EffectAccessor`; `effect get() { }` is an `EffectMethod` named `get`. `async effect get x() { }` gets both `EK0104` and `EK0105`.

#### EffectShorthand

```text
EffectShorthand = ("effect" | "async") [no LineTerminator here] [lookahead ∉ { as, satisfies, is }] BindingIdentifier TypeParameters? Params ReturnType? Block   (at a statement start or after export; parses, then the top-level-shorthand rule rejects it)
```

The identifier-spelled expression operators `as`, `satisfies` and `is` retain their expression reading after a value named `effect` or `async`; they cannot select recovery for an invalid function shorthand. In particular, both statements below are VIP-7 `is` expressions, and the Effect succeeds with `2`:

```vibe [VibeLang]
// compiler-gap: pending VIP-1, VIP-7
class Point {}
effect function operatorHeads() {
  const effect: unknown = new Point()
  const async = 3
  let hits = 0
  effect is (Point) && (hits += 1)
  async is < 5 && (hits += 1)
  return hits
}
```

```ts [Effect]
import { Effect } from "effect"

class Point {}
const operatorHeads = Effect.gen(function* () {
  const effect: unknown = new Point()
  const async = 3
  let hits = 0
  effect instanceof Point && (hits += 1)
  async < 5 && (hits += 1)
  return hits
})
```


`effect load() { }` and `async load() { }` outside a class or object literal are `EffectShorthand`s; the quick fix inserts `function`. Neither token sequence is valid TypeScript there, so no program changes meaning; `effect as (Handler);` stays a TypeScript type assertion.

#### EffectOperand

```text
EffectOperand = an ordinary TypeScript source type at the type-operator level (a primary type with postfix [] and [K], optionally after keyof, unique, readonly or infer), never an unparenthesized EffectType
```

At the optional `R` boundary after `!!`, prefer the present `R` among complete source parses when the following tokens on that line start a valid ordinary TypeScript source operand, except the existing unparenthesized `{` exclusion. A negative literal type is such an operand: `x as A!! - 1` consumes `-1` as `R`. This choice uses syntax, with no symbol lookup or whitespace distinction; parenthesize the whole omitted-`R` assertion before a following subtraction.

Only ordinary TypeScript source types are operands. The parser-only JSDoc forms `?T`, `T?`, `!T` and `*` are excluded, including inside parentheses; explicitly writing one gives the ordinary invalid-type diagnostic. At the optional-slot boundary, `?` and `*` instead remain expression operators where the surrounding expression admits them. An additional `!` follows the existing bang and non-null rules, rather than starting a JSDoc requirement. All existing line-break and union, intersection, function-type and conditional-type restrictions still apply.

```vibe
// compiler-gap: pending VIP-3
declare const x: unknown
type NegativeRequirement = number!!-1
const chosen = x as number!! ? 1 : 2 // omitted R, then conditional
const slot = x as number!! - 1      // R is -1
// @ts-expect-error: ordinary TypeScript arithmetic operand error
const product = x as number!! * 2   // omitted R, then multiplication
// @ts-expect-error: ordinary TypeScript arithmetic operand error
const subtract = (x as number!!) - 1 // omitted R, then subtraction
```

```ts [Effect]
import type { Effect } from "effect"

declare const x: unknown
type NegativeRequirement = Effect.Effect<number, never, -1>
const chosen = x as Effect.Effect<number> ? 1 : 2
const slot = x as Effect.Effect<number, never, -1>
// @ts-expect-error: Effect values are not arithmetic operands
const product = (x as Effect.Effect<number>) * 2
// @ts-expect-error: Effect values are not arithmetic operands
const subtract = (x as Effect.Effect<number>) - 1
```

The unparenthesized `{` exclusion applies only to the optional `R` after `!!`, leaving a following function body available. A required error or requirement slot admits an ordinary object type: `A!{ reason: string }!{ service: number }` means `Effect.Effect<A, { reason: string }, { service: number }>`. The omitted-error spelling still needs `A!!({ service: number })` for that requirement.

An enclosing TypeScript tuple can mark the completed Effect type as an optional tuple element: `[A!E?]` means `[(Effect.Effect<A, E>)?]`, `[A!!?]` means `[(Effect.Effect<A>)?]`, and `[A!!-1?]` means `[(Effect.Effect<A, never, -1>)?]`. This allows omission and contributes `undefined` on indexed access, as in TypeScript; the `?` is not a JSDoc suffix inside a slot. A stray postfix `?` outside an independently admitted TypeScript punctuation context remains invalid.

A leading `<` does not start a type at the type-operator level: `x as A!! < 3` omits `R` and continues with a comparison, subject to ordinary operand checking. A generic function requirement needs parentheses, `A!!(<T>() => T)`. A leading `[` does start a tuple type, so `x as A!![0]` consumes `[0]` as `R`; `(x as A!!)[0]` requests a later element access, subject to ordinary type checking.

In an expression, `x as A!! as B` and `x as A!! satisfies B` retain the ordinary chained assertion or check when consuming the keyword as `R` would strand `B`. Priority is between complete source parses, not parser-recovery trees. This is not a token ban: TypeScript allows type aliases named `as` and `satisfies`, so a pure type `A!!as`, a required or parenthesized slot using those aliases, and `x as A!!as satisfies unknown` retain their valid present-`R` parse. When both complete source parses survive, prefer the present `R`, with no symbol lookup.

```vibe
// compiler-gap: pending VIP-3
type RequiredObjects = number!{ reason: string }!{ service: number }
type OptionalError = [number!string?]
type OptionalSuccess = [number!!?]
type OptionalNegative = [number!!-1?]
type GenericRequirement = number!!(<T>() => T)
type as = { service: number }
type satisfies = { other: string }
type NamedRequirement = number!!as
type OtherRequirement = number!string!satisfies

function assertions(x: unknown) {
  const asserted = x as number!! as unknown
  const checked = x as number!! satisfies unknown
  const named = x as number!!as satisfies unknown
  const tuple = x as number!![0]
  // @ts-expect-error: Effect values are not comparison operands
  const comparison = x as number!! < 3
  // @ts-expect-error: an Effect has no numeric index
  const indexed = (x as number!!)[0]
}

effect function slotBoundaryWitness() {
  const empty: OptionalError = []
  const noError: OptionalSuccess = []
  return [empty.length, noError.length, empty[0] === undefined] as const
}
```

```ts [Effect]
  const checked = x as Effect.Effect<number> satisfies unknown
  const named = x as Effect.Effect<number, never, as> satisfies unknown
  const tuple = x as Effect.Effect<number, never, [0]>
  // @ts-expect-error: Effect values are not comparison operands

  // @ts-expect-error: an Effect has no numeric index

```

```ts [Effect]
import { Effect } from "effect"

type OptionalError = [(Effect.Effect<number, string>)?]
type OptionalSuccess = [(Effect.Effect<number>)?]
```

`slotBoundaryWitness()` succeeds with `[0, 0, true]`. These type boundaries change neither execution nor the Effect's error or requirement channels.

Recovery for a parameter list followed directly by a block after `catch`, as in `try x catch (e) { B }`, reports `EK0509` without an additional `EK0505` for that same malformed handler. It admits no block-handler production. A well-formed function literal restores the ordinary head check; independent source-context and separate syntax diagnostics remain. The [handler repair rule](/spec/002-running#catch) preserves source jump targets and the selected plain or Effect handler kind.

### Notes on the productions

**Pipe snapshot reconciliations.** The missing-topic early error checks the `AssignmentExpression` child with `ContainsOuterTopic`; the `PipeBody` boundary still returns `false`. Evaluation uses the actual `ShortCircuitExpression` input once, with `GetValue`, rather than the stale `ConditionalExpression` reference. `GetPrimaryTopicValue` reads `topicEnv.[[TopicValues]]`, not the unbound `envRec`. Binary XOR `^` and XOR assignment `^=` remain ordinary TypeScript operators despite the duplicated `%` in the token table. The snapshot receipt records these corrections without changing the upstream HTML; [Running Effects](/spec/002-running#the-pipe-operator) gives the examples.

**`catch`.** [CatchExpression](/spec/900-appendices#catchexpression) sits in ECMAScript's precedence chain beside `CoalesceExpression`, and its head mirrors `CoalesceExpressionHead`: it binds like `??`, is left-associative, and can't be mixed with `??`, `||` or `&&` without parentheses, for the same structural reason `a ?? b || c` is a syntax error. The handler is a plain or `effect` arrow or function expression, possibly parenthesized, so its kind is decided by its syntax alone; any other handler is `EK0509` ([Running Effects](/spec/002-running#catch)). An unparenthesized arrow handler ends the chain: its `ConciseBody` is the longest `AssignmentExpression`, as in an ECMAScript arrow, so a later `catch` belongs to the body. Any other handler is a closed expression, after which only another `catch` or a lower-precedence operator can follow.

```text
a catch (() => b) catch (() => c)    (a catch (() => b)) catch (() => c); type-checks only when the inner catch gives an Effect: a's success (never, if a only fails) and b are both Effects
a catch () => b ? c : d              a catch (() => (b ? c : d))
a catch (e) => b catch () => c       error: under [~Effect] the arrow body is b catch () => c, parsed by recovery and reported as `catch` outside effect code (EK0504)
a catch effect (e) => b catch () => c
                                     a catch (effect (e) => (b catch (() => c)))
a catch function (e) { … }           a plain function handler
a catch (effect function (e) { … })  an effect function handler
a catch b                            syntax error: not a function literal; write a catch () => b
a catch effect { b }                 syntax error: an effect block is not a function literal
a catch class { }                    syntax error: a class is not a function literal
a catch async (e) => b               syntax error: remove async (decided detail 85)
a catch function* (e) { }            syntax error: remove *
```

**`for concurrent`.** A line break between `for` and `concurrent` is allowed, as in ECMAScript’s [`for await` grammar](https://tc39.es/ecma262/2025/multipage/ecmascript-language-statements-and-declarations.html#sec-for-in-and-for-of-statements) and TypeScript. After `for concurrent`, the first parenthesized group is the limit only when it parses as an `AssignmentExpression` and the next group is the for…of head. A group that holds `ForDeclaration of …` is the head, whatever follows it:

```text
for concurrent (4) (const x of xs) f(x)        limit 4
for concurrent (const x of xs) (try g(x));     no limit; the body is a parenthesized expression
```

Both loop layouts have the same Effect counterpart and give `Success(3)` here:

```vibe [VibeLang]
// compiler-gap: pending VIP-19
effect function multilineTotal() {
  let total = 0
  for
  concurrent (const x of [1, 2]) { total += x }
  return total
}
```

```ts [Effect]
import { Effect } from "effect"

const multilineTotal = Effect.gen(function* () {
  let total = 0
  yield* Effect.forEach([1, 2], x => Effect.sync(() => { total += x }), {
    concurrency: "unbounded", discard: true
  })
  return total
})
```

**`!` in types.** `A!B!C` is always the three-slot form; write `(A!B)!C` to nest, and `A!!B!C` is a syntax error (`EK0302`). One rule explains every `[no LineTerminator here]` in the productions: a line break ends an Effect type. TypeScript stops its postfix type operators (`!`, `?`, `[]`) at a preceding line break, so in `x as User` followed by a line `!flag && fail()`, the type ends at `User`. A `[]` has a closing token and a slot doesn't, so the slot starts on the line of its `!`, which keeps `now(): number!!` and `later(): number!!` two members. A slot in parentheses may span lines. `R` after `!!` never starts with `{`; write `A!!({ … })` for a type-literal requirement. In a type, the scanner splits `!=` or `!==` only directly after `A!`, where the `!` completes `A!!`, as TypeScript rescans `>=` after type arguments only on demand; anywhere else they stay equality operators. `EffectType` is an alternative of TypeScript's `Type`, beside a function type and a conditional type. A function or constructor type's return is a `Type`, so `() => A!E` is `() => (A!E)`, as `() => A | B` is `() => (A | B)` (decided detail 80). `!` does not mix with `|`, `&` or conditional types without parentheses (decided detail 47): an `EffectType` can't be an operand of `|` or `&` or a part of a conditional type unless parenthesized, and a function or constructor type in a slot needs its own parentheses (`A!(() => B)`, not `A!() => B`). Each is a syntax error with a quick fix that parenthesizes (`EK0301`). `A!!B!C` is `EK0302`. Each operand sits at the type-operator level, so prefix and postfix operators bind tighter than `!`.

A `!` after a type with no slot and no second `!` after it on its line is a syntax error, as in TypeScript (TS17019); the quick fix parenthesizes: `(x as Foo)!`. `T!!` is always an `EffectType`.

```text
service S {                       two members: R can't start on the next line
  now(): number!!
  later(): number!! }
effect function f(): number!! {   "{" begins the body, not R
const e: User!                    syntax error: NotFound starts a new line, so this ! has no slot
  NotFound = load()
const e: User!(                   one type: the slot starts on the line of its !
  NotFound | Timeout) = load()
const e: User!!= load()           const e: User!! = load()
x as number !== 0                 (x as number) !== 0, as in TypeScript
type T = A | B!E                  syntax error; write (A | B)!E or A | (B!E)
keyof A!E                         (keyof A)!E
A!E[]                             A!(E[]); write (A!E)[] for an array of Effects
User!![]                          Effect.Effect<User, never, []>; write (User!!)[] for an array
type Find = (id: string) => User!NotFound      (id: string) => Effect.Effect<User, NotFound>
type New = new () => User!NotFound             a constructor type returning an Effect
type G = () => A!E | B                         syntax error: ! mixed with |
A!(() => B)                       Effect.Effect<A, () => B>
X extends Y ? A!E : B             syntax error; write X extends Y ? (A!E) : B
A!E extends X ? 1 : 2             syntax error; write (A!E) extends X ? 1 : 2
x as Foo!;                        syntax error, as in TypeScript; write (x as Foo)!
x as Foo!!;                       x as Effect.Effect<Foo>
```

`(A | B)!E` is `Effect.Effect<A | B, E>`; `A | (B!E)` is `A | Effect.Effect<B, E>`.

**Fields.** A field's `Type` is parsed greedily, as in a TypeScript type member; then the field ends at `;`, `,`, a line break or `}`, so `{ a: string b: number }` is a syntax error and a union may continue on the next line:

```text
schema User { role:             one field, role: "admin" | "user"
  | "admin"
  | "user" }
```

A variant's `{` may follow a line break, as an error body's may; a line break before `{` is not a separator, so `data D { A` then `{ x: string } }` gives `A` the field `x`. `readonly` is allowed on any field; `error` and `data` fields are readonly either way. `data Empty {}` has no variants; it is an empty `Data.TaggedEnum`.

**Declarations.** `ClassHeritage` is TypeScript's class heritage, `extends` and `implements` clauses. `ServiceDeclaration`, `ErrorDeclaration` and `SchemaErrorDeclaration` are deliberately wider than the language, so `service Repo<T> { }`, `service S extends Base { }`, `error E<T> { }` and `error E { static x = 1 }` reach the coded static rules of [Failures](/spec/003-failures#error-declarations) and [Services](/spec/005-services#static-rules) instead of a generic syntax error. The alternatives don't overlap: a member that parses as a `Field`, `PropertySignature`, `MethodSignature`, `KeyMember` or `DefaultMember` is that member, never a rejected one, so `service S { a: number, b: string }` uses interface separators. `ClassMethod` includes ordinary TypeScript method overloads, getters and setters, with their class modifiers and decorator checks. A getter is accepted and the setter rule rejects a setter; a constructor parses as `RejectedElement` but gets the specific constructor diagnostic before the catch-all row. `EffectMethod` and `ProducerMethod` start with `effect` and a name, which no ordinary `ClassMethod` does (`effect() { }` is a method named `effect`). A `ClassMethod`, `EffectMethod` or `ProducerMethod` in an error body follows TypeScript's class-method checks (`private m()`, `protected`, `override`), as any class can (VIP-13); a `static` one is rejected by the `static` rule. A member gets one diagnostic: the first row of its chapter's table that names it; the `RejectedElement` or `RejectedMember` row applies only when no other row does, and a member that a [Functions](/spec/001-functions) `effect` rule rejects (`effect get`, `effect set`, `effect constructor`) gets the applicable Functions diagnostics, with no extra error-body category diagnostic.

```text
error E { id: string }            a Field
error E { id = "init" }           RejectedElement: an initializer
error E { private id: string }    RejectedElement: a modifier other than readonly
error E { get message() { } }     a ClassMethod (a getter)
error E { effect again() { } }    an EffectMethod
error E { m() { }; id: string }   a ClassMethod, the empty element ";", a Field
error E { effect get x() { } }    an EffectAccessor: the getter/setter rule alone
service S { a: number b: string } syntax error: no separator, as in an interface
error E implements I { }          parses; an implements clause is rejected
service S { static readonly key = "k" }   a KeyMember
service S { static readonly key: string = "k" }   a KeyMember
service S { static readonly key = `k` }   RejectedMember: not a string literal
service S { (x: number): string }   RejectedMember: a call signature
service S { static key = "k" }    RejectedMember: not a KeyMember
service S { x: number = 1 }       RejectedMember: an initializer
```

**Match arms.** [MatchArm](/spec/900-appendices#matcharm) is the pinned draft's clause with VIP-7's `when` prefix and VIP-5's `throw` arm body. `default` is last, guards belong to `MatchPattern`, and every arm ends with `;`, the last one included; a newline is not a separator.

## Appendix B. Diagnostics

Every diagnostic has an `EK` code and a message that says how to fix it (VIP-34). VibeLang's own rules take one hundred-block per VIP, `EK` then the two-digit VIP number then two digits, so VIP-19's rules are `EK19xx` (decided detail 60). Imported lint rules use the growing `EK38` decimal suffix below (decided detail 142). A code assigned before that scheme is kept where its rule is unchanged, or only widened or downgraded: `EK2109`, `EK2111`, `EK2117`, `EK2126`, `EK3001` to `EK3005`, `EK4402`, `EK4609`, `EK4610` and `EK4701`. Codes are unique across the table, so a kept code may sit inside another VIP's block. Each rule's chapter links to its definition. A row whose rule starts "warning" or "lint warning" is a warning; every other code is an error. Only a warning's code, or an `EK38xx` code, may appear in `vibe.severities` (VIP-30, amended): `{ "EK0801": "off" }` is valid, `{ "EK4701": "off" }` is `EK3006`. Reused numbers: `EK2003` and `EK2102` previously named the deleted rules that VIP-4 and VIP-1 cite; in this table they mean only the rows below. `EK3008` is not reused: the current compiler prints it for the static-key rule, which this table numbers `EK0901`. VibeLang's own syntax errors have codes too, each in its VIP's block (`EK0509`, `EK1906`, `EK2005`, …). TypeScript's own diagnostics keep their `TS` codes. Diagnostic ownership follows the source rule, not the parser helper: new VibeLang productions, placement rules, adopted proposal early errors and explicit reconciliations use their owning VIP's `EK` code. Imported proposal syntax is not ordinary native TypeScript syntax. Independent errors in native embedded expressions and types keep their native diagnostics. Each Effect language-service rule that VIP-38 imports (`effecttsgo/*`) gets one stable `EK38xx` code, listed in a table generated from the pinned effect-tsgo version; the CLI prints the code and the rule name (`EK3801 floatingEffect: …`), a VIP-32 bump regenerates the table, and a code never changes once assigned. Every `EK38xx` code is a lint code that `vibe.severities` may set to any value, `"off"` included (decided detail 77). The [Imported lint codes](/spec/900-appendices#imported-lint-codes) table below is generated from that pin.

The TypeScript-form lint warnings also retain their existing `EK4830`–`EK4837`, `EK4839`, `EK4841` and `EK4842` assignments. ### Transitional compiler diagnostics

A transitional compiler may still print compatibility diagnostics from the old language. The following inventory covers the `EK92xx` codes in its registry, separately from the normative rules above: an interim code does not establish a language rule or reserve a new VIP block. Their retirement follows the named VIPs; a compiler renumbering must update this inventory with the registry.

| Emitted code | Rule | Retirement VIP | Replacement |
| --- | --- | --- | --- |
| interim `EK9201` | error: an expected failure escapes the written error contract | 1, 3 | Ordinary checked Effect return types and assignability |
| interim `EK9202` | error: a requirement escapes the written requirement contract | 1, 3 | Ordinary checked Effect return types and assignability |
| interim `EK9203` | error: a plain return annotation is on a function or native generator whose body runs an Effect or can fail | 1, 4 | Keywords decide function kind; ordinary JavaScript throws follow the accepted thrown-type rules |
| interim `EK9204` | warning: an old Effect `try`/`catch` statement has no expected errors | 5 | Effect code has no `try` statement; an infallible Effect is still run with `try e` |
| interim `EK9205` | error: a declaration without a body has a return type that is not an Effect | 1, 9 | Ordinary TypeScript declarations and service members may have non-Effect return types |
| interim `EK9206` | error: a recursive function has a success type that depends on its own result, or the legacy partial-contract inference cannot break its call cycle | 1, 3 | Ordinary TypeScript inference and its own recursion diagnostics; no VibeLang recursion diagnostic |
| interim `EK9207` | error: a service or control contract member has a body or initializer, or an instance member is placed in a legacy shape-only service body | 9 | Accepted service-member restrictions use `EK0902`; control syntax remains historical, not an accepted construct |
| interim `EK9208` | error: a static service member has the same name as an instance service member | 9 | Accepted service shapes and their restricted static members follow the ordinary `Context.Service` counterpart |

For example, `effect function bad(): number!! { throw new Bad() }`, with `error Bad`, fails ordinary Effect return-type checking: its error type is `Bad`, rather than `never`. `effect function run() { return try succeed(1) }` is valid and gives `Success(1)`. Removing the old statement warning never permits skipping an infallible Effect.

The existing migration warnings retain their emitted codes until the compiler and documentation move together. They select repairs; they do not change the omitted-slot or service rules.

| Code | Rule | VIP | Chapter |
| --- | --- | --- | --- |
| `EK4853` | warning: migration of an omitted requirement slot: write the previously inferred requirements explicitly, or omit the whole return annotation to infer the contract | 3 | [Functions](/spec/001-functions#the-aer-type-shorthand) |
| `EK4854` | warning: migration of the retired abstract-class service spelling to a `service` declaration, retaining its contract and key | 9 | [Services](/spec/005-services#service-declarations) |

## Appendix E. Shipped `@throws` and `@rethrows` annotations

These are the annotations [Thrown types](/spec/003-failures#thrown-types) refers to. VibeLang ships them for JavaScript's globals and for Effect's non-effectful exports, plus the thunk annotations of VIP-4's two wrappers. Every other callback parameter of any function, Effect's and the globals' alike, `LazyArg` included, is a function type with no `@throws`, so it admits only non-throwing functions: `sync(() => parse(s))` is an error; use `Effect.try`.

| Function | Annotation |
| --- | --- |
| `JSON.parse` | `@throws {SyntaxError}` |
| `Math.max`, `Date.now`, `Option.some` | `@throws {never}` |
| `Schema.decodeUnknownSync`, `Schema.decodeSync` | `@throws {never}`: they only build a decoder |
| the constructors of `Data.TaggedError` and `Data.taggedEnum` variants: `new NotFound({ id })`, `Delivery.Sent({ … })` | `@throws {never}` |
| the constructor of `Schema.TaggedError`: `new Invalid({ … })` for a `schema error` | `@throws {never}`, as for `error` and `data`: a bad field at construction throws a plain `Error`, a defect: `effect { throw new Invalid({ name: "" }) }` dies |
| the decoder that `Schema.decodeUnknownSync(schema)` or `Schema.decodeSync(schema)` returns | `@throws {SchemaError}` |
| the thunk of `Effect.try` and `tryPromise`, in either form: the function argument, or the `try` property of the options argument | `@throws {unknown}`: the wrapper makes a throw a failure. The options form's `catch` callback has no `@throws`. `promise`'s thunk has no `@throws`, so it admits only a thunk that throws `never` |
| `Array.prototype.map`, `.forEach`, `.filter`, `.find`, `.some`, `.every`, `.sort` | `@throws {never} @rethrows callbackfn` (`sort`: `@rethrows compareFn`) |
| `Array.prototype.reduce` | without `initialValue`: `@throws {TypeError} @rethrows callbackfn` (`[].reduce(f)` throws); with `initialValue`: `@throws {never} @rethrows callbackfn` |
| `Array.from` | `@throws {never} @rethrows mapfn` |
| the data-last overload of every dual export of effect 4.1.0: `map(f)`, `retry(p)`, `catchTag(t, h)` | `@throws {never}`: it only builds a function |
| `new Promise(executor)` | `@throws {never}`, no `@rethrows`: a throw in the executor rejects the Promise, as in JavaScript; it never throws at the construction site |
| the `executor` parameter's call signature | `@throws {unknown}`: it admits a throwing executor, whose throw becomes the rejection, not part of the constructor's thrown type |

In a `.ts` file, `setTimeout` does not rethrow, because it stores the callback; in a `.vibe` file it is a banned platform global ([Services](/spec/005-services#the-platform-standard-library)). A shipped annotation always carries `@throws`, so step 2 of [Thrown types](/spec/003-failures#thrown-types) always finds a type. The array annotations attach to every `lib.d.ts` call signature of the named method, on `Array<T>` and `ReadonlyArray<T>` alike; a tuple uses `Array<T>`'s. An Effect function's data-first overload returns an Effect and is effectful; its data-last overload returns a function and is non-effectful with `@throws {never}`, so `fetchUser(id).pipe(Effect.map(toDto), Effect.retry(policy))` is accepted. Their callbacks have no `@throws`. A library declares the same tags in its own declarations:

```ts
/** @throws {never} @rethrows f */
export declare function each<T>(xs: readonly T[], f: (x: T) => void): void
```

Apply the three-step procedure in [Thrown types](/spec/003-failures#thrown-types) to these shipped signature contracts. It composes own throws with `@rethrows` and preserves the effectful exemption (decided detail 66).

```vibe [VibeLang]
// compiler-gap: pending VIP-4
/** @throws {never} @rethrows f */
function each<T>(xs: readonly T[], f: (x: T) => void): void {
  xs.forEach(f)
}

effect function direct() {
  each([1], () => { throw "callback" }) // EK0403: wrap the call
}

effect function wrapped() {
  return try Effect.try({
    try: () => each([1], () => { throw "callback" }),
    catch: (e) => e
  })
}
```

The same contracts apply when `each` is imported through the declaration above. Its ordinary JavaScript call throws; `Effect.try` turns that throw into a typed failure:

```ts [Effect]
import { Effect } from "effect"

/** @throws {never} @rethrows f */
function each<T>(xs: readonly T[], f: (x: T) => void): void {
  xs.forEach(f)
}

function wrapped() {
  return Effect.gen(function* () {
    return yield* Effect.try({
      try: () => each([1], () => { throw "callback" }),
      catch: (e) => e
    })
  })
}
```

`Schema.decodeUnknownSync(User)` and `Schema.decodeSync(User)` only build decoders and throw nothing; calling either decoder throws `SchemaError` on invalid input.

Every remaining global and effect 4.1.0 non-Effect export is annotated by a generator, not by hand: `@throws {never}` only when its source has no `throw` reachable from well-typed input, a named class when one is known (`SchemaError`), otherwise `@throws {unknown}`. The normative [`throws.json`](https://github.com/smithersai/vibelang/blob/main/docs/design/inventory/throws.json) is generated by `node docs/tools/throws-inventory.mjs --write`. It records the bundled TypeScript lib version and every input file's hash, the exact Effect package version and hashes of its declarations and shipped `dist` sources. Every entry is keyed by `module`, `declaration`, `kind` and `signature`, with `ownThrows`, `rethrows`, `callbacks` and `returns` contracts; non-callable values have `ownThrows: null`. Native argument-validation contracts follow [Implicit and tracked built-in throws](/spec/003-failures#implicit-throws) (detail 81); source analysis follows imported helpers and constructors, separates returned function bodies and treats incomplete proofs as `unknown`. Function-type callbacks admit `never` by default, while the explicit wrapper thunks, Promise executor and rethrowing parameters carry their admitted thrown type. Native proofs use finite sets of known methods; unmodeled APIs remain `unknown`. Iterable protocol hooks are implicit for `Array.from(it)`, `new Map(it)` and `new Set(it)` (detail 202). Numeric `dual` arities distinguish a data-last factory, whose own thrown type is `never`, from a full invocation of its body; the returned callable keeps that body's contract. Dynamic arity predicates need a separate proof and stay conservative. Detail 202 separately settles `Effect.catchTag`'s data-last factory as `never`; its shipped selector only tests `isEffect`. The JavaScript `dist` files erase parameter types, so scalar-call proofs require known safe arguments or an intrinsic that accepts every value. Unresolved iterator protocols, disposal, tagged-template calls and computed method keys remain `unknown` rather than a guessed `never`. A TypeScript or Effect bump regenerates this artifact; `node --test docs/tools/throws-inventory.test.mjs` rejects stale output. Written contracts still take precedence over shipped annotations, then inference or defaults, as the three-step procedure requires. `@throws` and `@rethrows` attach to a call signature, as TypeScript attaches JSDoc to each overload, so a returned function's contract sits on its own signature:

```ts
import type { Schema } from "effect"

export declare function decodeUnknownSync<T>(s: Schema.Decoder<T>): {
  /** @throws {Schema.SchemaError} */ (input: unknown): T
}
```
