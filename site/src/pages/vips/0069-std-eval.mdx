## Summary

THESIS 8 also applies: "Agentic behavior is probabilistic, so evals become as basic as tests."

**One sentence.** `Experimental.Eval` runs a fixed set of cases against a target, `Experimental.Scorer` grades each answer from 0 to 1, and a gate compares the scores with a committed baseline and returns an exit code.

**One paragraph.** A test asserts that an answer equals something. An answer from a model rarely equals anything; it is better or worse than the last one. Smithers' `@smthrs/evals` and `@smthrs/scorers` score the answer, compare the score with a committed baseline, and turn the comparison into a CI result. This VIP ports both behind two namespaces. [eval-declarations](/vips/0059-eval-declarations) says where an eval lives and how it is run. This VIP says what runs: the suite, the scorers, model-graded rubrics, baselines, regression comparison, the gate, and scoring of live runs. Five outcomes stay distinct all the way to the exit code: a target that failed, a scorer that could not decide, a score that regressed, a score that moved for no stated reason, and a score that is missing.

```text
 cases ──► target ──► output ──► scorers ──► scores in [0, 1] ──► compare with baseline ──► gate
                                  │ exact, contains, checks                │ regressed?       │ 0  pass
                                  │ rubric: a model grades                 │ moved? missing?  │ 1  regressed
                                  │ yours: Scorer.make                     │ only noise?      │ 5  could not decide
```

## Decision

```ts
// proposed
effect function greet(name: string) {
  return `Hello, ${name}`
}

const polite = Experimental.Scorer.make({
  name: "polite",
  version: "1",
  score: (run: { output: string; expected: string }) => run.output === run.expected ? 1 : 0
})

export default Experimental.Eval.suite("greet", {
  target: greet,
  cases: [{ name: "ada", input: ["Ada"], expected: "Hello, Ada" }],
  scorers: [polite],
  gate: { min: 1, tolerance: 0 }
})
```

### Module

`Experimental.Eval` and `Experimental.Scorer`, in scope with no import, as [VIP-33](/vips/0033-platform-stdlib) rules. Their code is `vibelang-runtime/experimental/Eval` and `…/Scorer`. They port `@smthrs/evals` and `@smthrs/scorers`.

| Call | Meaning | Smithers |
| --- | --- | --- |
| `Eval.suite(name, { target, cases, scorers, trials?, concurrency?, gate? })` | Declare a suite. Runs nothing | `Suite.make`, `Binding.make` |
| `Eval.run(suite, { runId? })` | Run every case, score every output | `Runner.run`, with a `CaseExecutor` built from `target` |
| `Eval.baseline(run)`, `Eval.write`, `Eval.load` | A baseline from a run, as text to commit, and back | `Baseline.fromRun`, `Baseline.write`, `Baseline.load` |
| `Eval.compare(baseline, run, tolerances?)` | Regressions, nondeterminism and missing observations, as a value | `Regression.compare` |
| `Eval.gate(report, { mean?, min? })` | A verdict and a CI grade | `Gate.check`, `Gate.ciGrade`, `ScoreGate` |
| `Eval.fromJsonLines(text, options)` | Cases from a JSONL file | `Suite.fromJsonLines` |
| `Eval.passAtK(n, c, k)` | The chance at least one of `k` trials passes, from `c` passes in `n` | `Trials.passAtK` |

| Scorer | Grades | Smithers |
| --- | --- | --- |
| `Scorer.exact` | Normalized equality with `expected` | `Scorers` |
| `Scorer.contains(text)` | Containment | `Scorers` |
| `Scorer.checks([...])` | A list of pure text and action checks | `Checks` |
| `Scorer.rubric(criteria, { model })` | A model grades the output against written criteria | `Rubric` |

| `Scorer.bind(scorer, W, { sampling })` | Score a workflow's live runs | `Binding.make`, `Sampling` |

### Rules

1. **A score is a finite number in `[0, 1]`.** Anything else is refused.
2. **A scorer has an identity.** Its name, version and configuration hash into a `scorerKey` that is written on every score it produces. A score recorded a month ago still names the exact grader. Change the grader, bump `version`.
3. **A scorer that fails does not fail the suite.** It records an inconclusive observation with a reason and a code. A target that fails is a failed case. Neither becomes a score of zero.
4. **Regression and noise are different facts.** The comparison separates a score that dropped from a case whose step key changed, which means the target took a different path. `trials` runs a case several times to measure the spread. A trial is a new call: replaying one recorded answer measures the recording.
5. **A baseline never updates itself.** `Eval.baseline` records successful scores only, and writing one is a separate act with a diff to review.
6. **A gate is pure.** It takes a report and options and returns a verdict. `min` is the lowest passing score, `mean` the lowest passing average, and `tolerance` how far a score may fall below its baseline.
7. **Three exit codes.** `0` when every case cleared the gate, `1` when a score regressed or an observation went missing, `5` when the gate could not decide. A `5` is a broken harness, not a result. A partial pass never exits `0`.
8. **Rubric judges are models.** `Scorer.rubric` names its judge, `{ model: seat }`, and records it in the scorer's identity. It does not default to the model under test, which would grade itself. A judge that cannot be reached is inconclusive; it never passes. Judge calibration, grading known answers to measure the judge, is part of `Rubric`.
9. **Live runs can be scored.** Sampling is `"all"`, `"none"`, or a ratio strictly between 0 and 1 with a seed, so a replay samples the same runs. Scores persist as observations (`SqlScoreStore`).
10. **Limits.** A suite holds at most 10,000 cases and runs at most 1,024 at once (`Suite.limits`).

### Host needs

None for scoring. A rubric needs a model ([std-model](/vips/0062-std-model)). Persisted observations need the SQL store [std-durable](/vips/0060-std-durable) provides.

### Decisions made while building it

- `Experimental.Eval.suite` and `Experimental.Scorer.make` never throw, because a plain VibeLang function may not throw: a scorer with no stable identity keeps the reason as `scorer.problem`, and `Eval.run` refuses a malformed suite with `invalid_suite` and the offending path before running anything. Author: vip-std-eval (Claude Opus 5.5).
- A scorer's identity is SHA-256 of the RFC 8785 canonical JSON of `{ id: name, version, config }`, so the VIP's `name` takes the place of Smithers' separate `id`. Two scorers with one identity in a suite are refused. Author: vip-std-eval (Claude Opus 5.5).
- A case's step key is the first 16 hex digits of SHA-256 of the output's canonical JSON, sets and maps sorted. A score that dropped at a changed step key is a regression; a score that moved at the same step key is nondeterminism (Smithers' rule). Output that is not JSON gets one step key per type. Author: vip-std-eval (Claude Opus 5.5).
- Exit codes: a missing score on either side and a failed target exit `1`, as rules 3 and 7 say (Smithers reports both as unresolved, exit `5`). A gate with no score at all, an inconclusive scorer, or an invalid threshold exits `5`. Author: vip-std-eval (Claude Opus 5.5).
- `Eval.gate(report, options)` returns `{ verdict, exitCode, summary }` with no Effect, and also takes `perCase` and `tolerance`; `tolerance` ignores a regression or nondeterminism no larger than it. `Eval.compare` keeps Smithers' `{ absolute, relative }` tolerances. Author: vip-std-eval (Claude Opus 5.5).
- `Eval.write` keeps Smithers' baseline JSON (version 1, keys and records sorted) but puts each record on its own line, so a review sees one changed line per changed score; Smithers' `Baseline.load` reads it, and `Eval.load` reads Smithers' files. Author: vip-std-eval (Claude Opus 5.5).
- A scorer grades `{ input, output, expected }`, with `expected` typed as the target's output; a case with no `expected` passes `undefined`. `Scorer.exact` compares text after collapsing whitespace and other values by canonical JSON; `Scorer.contains(text?)` falls back to the case's `expected`. Author: vip-std-eval (Claude Opus 5.5).
- `Scorer.checks` takes data records, `includes`, `excludes`, `words`, `excludesOpener` and `complete`, ported from Smithers' `Checks`, so the list is the scorer's configuration and identity. Smithers' link and action checks are not ported. Author: vip-std-eval (Claude Opus 5.5).
- `Eval.run`'s `runId` defaults to the suite name and the start time read from Effect's `Clock`; `trials` and `k` may be overridden per run. `Eval.passAtK` returns `NaN` for impossible counts instead of throwing. Author: vip-std-eval (Claude Opus 5.5).
- `Scorer.bind(scorer, W, { sampling, timeout })` is a layer over the `WorkflowEngine` it is given. It wraps `W`'s registered body, so a run is scored when its body returns a result; a failed run is not scored. The observation's identity is the workflow, run id and `scorerKey`, so re-executing, joining or resuming a run records it once. Scoring adds at most `timeout` (one minute by default) to the run, and any scorer outcome, a timeout or self-interruption included, is an inconclusive observation that never changes the run's result. Author: vip-std-eval (Claude Opus 5.5).
- The score store is the `Scorer.ScoreStore` service with `recordOnce`, `observations`, `aggregate` and `prune`; `Scorer.memory` and `Scorer.layerSql` (one table, `score_observations`, over Effect's `SqlClient`) provide it. Ratio sampling is Smithers' FNV-1a over the run id, `scorerKey` and seed, exposed as `Scorer.sampled`. Author: vip-std-eval (Claude Opus 5.5).
- `Scorer.rubric(criteria, { model, layer })`: `model` is the judge's seat and part of the identity with the criteria, examples, rule and instructions; `layer` is the Effect `LanguageModel` that answers for the seat, so a test passes a scripted model. Until VIP-62's `Experimental.Model.use` lands, `layer` is required; it then defaults to `Experimental.Model.use(model)`. In a suite, a single argument is the judge's subject. Author: vip-std-eval (Claude Opus 5.5).
- `Scorer.calibrate(scorer, labelled)` grades answers with known verdicts and returns agreement counts; a judgement passes by its `meta.pass`, or by a score at least a threshold (default 1), and an inconclusive judgement agrees with nothing. Author: vip-std-eval (Claude Opus 5.5).
- An inconclusive observation accounts for one baseline record of its case and scorer, so a judge outage is undecided (exit `5`), not missing (exit `1`). Scores left over at changed step keys pair by score rank. A case's scorers run one after another, so at most `concurrency` targets or scorers run at once. A target or scorer that interrupts itself fails only its case or score. Author: vip-std-eval (Claude Opus 5.5).
- Every scorer configuration, check list and rubric declaration is copied and frozen when it is declared, so mutating the caller's object cannot change grading under the same `scorerKey`. Author: vip-std-eval (Claude Opus 5.5).
- `Scorer.decide(decision, { model, layer, pass? })` answers follow-up question 2: it grades with one `Decision.probability`, `Decision.rate` or `Decision.classify` on Effect's `DecisionModel`, and the judge reads `{ context, focus?, output }`. The score is the probability, the rating from 0 at the lowest level to 1 at the highest, or the probability of the `pass` labels, which a classify decision requires; `meta.pass` says whether the chosen label passes. The seat, the decision and `pass` are the scorer's identity. A refused, missing or invalid answer is inconclusive, and a locate decision is refused. As with `rubric`, `layer` is required until VIP-62's `Experimental.Model` lands. Author: vip-std-eval (Claude Opus 5.5).
- Follow-up question 3 has no default tolerance. A suite whose `rubric` or `decide` scorer meets a gate with no `tolerance` lists a warning in `suite.warnings`, and `Eval.run` logs each one with `Effect.logWarning` before it runs. A scorer's `judge` is the seat of the model that grades it. Author: vip-std-eval (Claude Opus 5.5).
- Follow-up question 4 keeps scores apart from run history. `Durable.sweep({ olderThan })` deletes finished runs and leaves their scores, so a score trend outlives the runs it graded; `ScoreStore.prune({ olderThan })` deletes the observations older than the duration and answers how many. Nothing prunes scores on a schedule the program did not set. Author: vip-std-eval (Claude Opus 5.5).

## Compared

A suite, a custom scorer, a baseline comparison and a gate in Smithers 1.x. It type-checks against `@smthrs/evals` and `@smthrs/scorers` 1.0.0-rc.16.

```ts
import { Baseline, CaseExecutor, Gate, Regression, Runner, Suite } from "@smthrs/evals"
import { Binding, Scorer } from "@smthrs/scorers"
import { Effect, Layer } from "effect"

const greet = (name: string) => Effect.succeed(`Hello, ${name}`)

const exactMatch = Scorer.make({
  id: "example/exact-match",
  version: "1",
  name: "exact-match",
  score: ({ groundTruth, output }) => Effect.succeed({ score: output === groundTruth ? 1 : 0 })
})

const executor = CaseExecutor.make((suiteCase) =>
  Effect.map(greet((suiteCase.input as { readonly name: string }).name), (output) => ({
    output,
    stepKey: suiteCase.name,
    latencyMs: 0,
    target: { name: "greet" }
  }))
)

export const gate = (committed: string) =>
  Effect.gen(function*() {
    const suite = yield* Suite.make({
      name: "greet",
      cases: [{ name: "ada", input: { name: "Ada" }, expected: "Hello, Ada" }],
      bindings: [Binding.make({ scorer: exactMatch, appliesTo: { name: "greet" }, groundTruth: "Hello, Ada" })],
      concurrency: 1
    })
    const run = yield* Runner.run(suite, { runId: "nightly-2026-11-09", at: "2026-11-09T00:00:00.000Z" })
    const report = yield* Regression.compare(yield* Baseline.load(committed), run)
    return Gate.ciGrade(yield* Gate.check(report))
  }).pipe(Effect.provide(Layer.succeed(CaseExecutor.CaseExecutor)(executor)))
```

## Principles

- **TypeScript-first.** A call with a record, the shape Evalite and Vitest set.
- **Effect-second.** A target, a scorer and a run are Effects. Effect has no eval module to reuse.
- **Optimized for agentic programs.** GOAL measures Vibe itself by evals. The same module measures a user's agent.
- **Highly forkable.** A scorer is a function. A gate is a pure function. A fork replaces either.
- **Factory-first.** Each release's eval baseline is a committed file, and the comparison that passed it is reproducible.

## What this changes

- `Experimental.Eval` and `Experimental.Scorer` are new. No grammar changes.

## Alternatives

- **Evalite or another npm framework.** One import away, and it stays available. It has no step keys, so it cannot tell a regression from a different path, and it does not score a durable run.
- **Evals as tests with a threshold**, `expect(score).toBeGreaterThan(0.8)`. A fixed threshold fails on noise and hides a slow decline. A baseline comparison does neither.
- **Smithers' names as they are**: `Suite`, `Runner`, `Baseline`, `Regression`, `Gate`, `CaseExecutor`. Six namespaces and an executor service for what one call declares. The port keeps their behavior and their file formats.
- **One namespace, `Eval.scorer`.** A scorer is used outside eval files, on live runs. It earns its own name.
- **Scores in the journal.** Smithers keeps them in their own tables with their own identity, because nothing in a run reads a score back.

## Follow-up questions

1. **Baseline format.** Smithers' baseline is versioned JSON (`Baseline.version` is 1). Vibe commits it beside the eval file. Keep the format as it is, so Smithers tools read Vibe baselines? Recommendation: yes.
2. **Decision models as judges.** Smithers' agent checks completions with Jev, not a rubric. Should `Scorer.decide(decision)` exist, over `DecisionModel`? Recommendation: yes; it is cheaper and typed.
3. **A default tolerance.** With `tolerance: 0`, any lower score on a model-graded case is a regression, and model scores move. Recommendation: no default; a suite with a rubric scorer and no `tolerance` is a warning.
4. **Retention.** Nothing prunes Smithers' score tables. Decide with [std-durable](/vips/0060-std-durable)'s `Durable.sweep`.
