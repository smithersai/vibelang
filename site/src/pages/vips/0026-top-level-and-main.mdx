# VIP-26: top-level `await`, and no magic `main`

**Status:** accepted, 2026-10-29, under Will's standing approval of recommendations ("assume I accept now. I will interrupt you if I need to").

## Decision

```ts
import { NodeRuntime } from "@effect/platform-node"
export effect function main() { … }
NodeRuntime.runMain(main())     // exactly as in Effect TS
await runPromise(main())        // or ES top-level await of a Promise (VIP-5); runPromise is a VIP-6 global
```

- A module's top level is ordinary JavaScript. `await` there is ES top-level await of a Promise (VIP-5), and `try` is not allowed, because a top level is not an `effect` function.
- There is no magic entry point. A function named `main` is an ordinary function, and you call a runner yourself, exactly as in Effect TS.

*Corrected 2026-11-02: the Decision example imports `NodeRuntime` from `@effect/platform-node`, which is not in scope (VIP-14), as chapter 1 does (found by the round-6 review).*

## Amendment: source file kind

Every source `.vibe` compilation unit is an external module before binding and checking, independently of written imports and exports, required prelude imports, `vibe.effectGlobals` and `vibe.effectModules`. Preserve that classification in emitted JavaScript and declaration sidecars with an effective empty module marker when needed. Ordinary TypeScript module emission and host rules, including incompatible-option diagnostics, apply. Top-level `await` therefore requires supported module and target options. This adds no implicit runner or special `main`. The `moduleDetection` exception is explicit in VIP-30.

## What was not adopted

Old VibeLang (D135, D517, EK4843) had the compiler emit `runMain(main())` for an exported `main`. That needed the platform, the entry file and rules for `const main`, which is behavior Effect doesn't have.

The old findings were contradictions about `main` (EK4843 versus chapter 28). They are moot.

### Detail 253

**Synchronous source `throw` has no module-body exception.** (Loop r5 Opus OPUS-1 top-level question; Will's 2026-10-31 no-local-throws ruling, accepted VIP-26 and principle 8.) Reject an explicit source `throw` in the ordinary top-level body of a `.vibe` module, including its directly evaluated blocks, `do` expressions and plain `try`/`catch` statements. A top-level `await`, an ES-module host or asynchronous module evaluation does not put that body inside an `async` VibeLang function and does not create an implicit Effect. VIP-39 applies the same VibeLang rule to `.vibex`. Will's rule is about synchronous source `throw`, so catching that same explicit source statement locally does not legalize it. A native `try`/`catch` that handles an actual foreign-call exception is a different case and keeps its admitted foreign-boundary rule.

    Classify nested callable/Effect bodies by their own existing owner: `throw` in `effect` code is `Effect.fail`; admitted async function/arrow/method throws reject their Promise under detail251; a nested synchronous callable or initializer remains synchronous. A plain generator body is not made async by returning an iterator. This decision adds no generator protocol, inline TypeScript module, implicit runner, local throws metadata or new diagnostic identity. Native top-level Promise `await` and its option checks stay unchanged. The restriction on the explicit `throw` statement is the deliberate Will-ordered difference from TypeScript, not a difference in where Effects may run.

    ```vibe
    throw new Error("stop") // error: ordinary module body
    try { throw new Error("stop") } catch {} // error: source throw stays forbidden
    const p = effect { throw new Error("stop") } // allowed: cold typed failure
    async function rejected() { throw new Error("stop") } // allowed: Promise rejection, detail251
    ```

    Effect TS:

    ```ts
    const p = Effect.gen(function* () {
      return yield* Effect.fail(new Error("stop"))
    })
    async function rejected() { throw new Error("stop") }
    // Native TypeScript also permits top-level throw; VibeLang deliberately rejects it under Will's ruling.
    ```

    No Will confirmation is needed: the ruling already rejects source `throw` outside the admitted Effect/async owners, and principle8 supplies the conservative scope where the wording names functions as examples. `nothrow-spec` and `nothrow-impl` retain source/compiler ownership. Cover ordinary module blocks, caught and uncaught source throws, `do`, top-level-await presence and module/target options, `.vibe`/`.vibex`, nested plain/async/Effect boundaries and initializers in their regression/spec-quoted keyed fuzz work. Preserve foreign-call handling, unknown native implicit exceptions and the separately accepted Promise behavior; do not widen this into whole-program exception proof. This policy lane ran no VibeLang compiler test for this clarification.
