# VIP-64: `Experimental.Tools`: the standard tools for files, search, HTTP, the web, the shell and language servers

**Status:** open, 2026-11-11. Not part of the language: Will limited the alpha to the core VIPs and reopened this one as a proposal ([VIPs](/vips/#the-built-in-set)). It was accepted optimistically on 2026-11-09 under his pre-alpha standing approval, since superseded; Will has not reviewed this VIP's decisions. No implementation exists.

## Will's words

> Ok so give me a list of [the reference engine's] features. We need to figure out what the VIP should look like. Some of the features outside of durable execution likely should simply be in the standard library I'm guessing but we should enumerate all of them

## Summary

**One sentence.** `Experimental.Tools` is a module of ready-made tools, each one both a function a program calls and an Effect `Tool` a model calls, with bounded output and a declared permission.

**One paragraph.** An agent needs the same dozen tools everywhere: read a file, edit it, search, run a command, fetch a page. The reference engine (an existing Effect durable-execution framework these built-ins are modelled on) ships them in its std package, each with a schema for its input and output, a declared capability, a display limit that is disclosed and never silent, and a handler that runs on whatever `FileSystem`, `ChildProcessSpawner` and `HttpClient` the host provides. This VIP ports them as Effect tools. A program calls `Experimental.Tools.read({ path })` directly. A model gets `Experimental.Tools.filesystem`, a `Toolkit`, through `LanguageModel.generateText` or `Experimental.Agent.run`. Because the handlers use injected services, the same tools run on the local disk, in a container, or on another machine.

```text
                      ┌─ a program:  try Experimental.Tools.grep({ pattern: "TODO", root: "src" })
 Tools.grep ──────────┤
 input schema         └─ a model:    LanguageModel.generateText({ prompt, toolkit: Experimental.Tools.filesystem })
 output schema                       Experimental.Agent.run({ prompt, tools: Experimental.Tools.filesystem, output })
 capability: fs:read
 limit: a match cap, then `truncated: true`       runs on: FileSystem + Path from context (disk, container, remote)
```

## Decision

```ts
// proposed
export effect function todos() {
  const hits = try Experimental.Tools.grep({ pattern: "TODO", root: "/workspace/src" })
  const first = try Experimental.Tools.read({ path: "/workspace/src/index.ts" })
  return { hits, content: first.content }
}
```

### Module

`Experimental.Tools`, in scope with no import, as [VIP-33](/vips/0033-platform-stdlib) rules. Its code is `vibelang-runtime/experimental/Tools`. Effect's `Tool` and `Toolkit` keep their names: `Tool` defines one, `Tools` is the standard set.

| Toolkit | Tools | Needs | Capability | Reference engine std package modules |
| --- | --- | --- | --- | --- |
| `Tools.filesystem` | `read`, `write`, `edit`, `applyPatch`, `ls`, `glob`, `grep` | `FileSystem`, `Path` | `fs:read`, `fs:write` | `Read`, `Write`, `Edit`, `ApplyPatch`, `Ls`, `Glob`, `Grep`, `Search` |
| `Tools.shell` | `bash`, `test` | `ChildProcessSpawner` | `proc:spawn` | `Bash`, `TestRun`, `TestRunner` |
| `Tools.http` | `fetch`, `post` | `HttpClient` | `net:get`, `net:post` | `Fetch`, `HttpPost` |
| `Tools.web` | `webfetch`, `websearch` | `HttpClient`, a search provider | `net:get` | `WebFetch`, `WebSearch`, `ExaWebSearch` |
| `Tools.lsp` | The language-server queries | A language-server service | `fs:read` | `Lsp`, `LanguageServer` |
| `Tools.readOnly` | Every tool above that changes nothing | As above | Read actions only | `Manifest.readOnly` |

Each tool is also a function: `Tools.read(input)`, `Tools.grep(input)`, `Tools.bash(input)` and so on. There is no `Tools.all`: a tool set that can run a shell is chosen by name.

### Rules

1. **One declaration, two uses.** A tool is an Effect `Tool` with a handler. `Tools.read` called directly is the same handler a model's call reaches.
2. **Ordinary outcomes are values.** A non-zero exit code, an empty match set and an HTTP 500 are successes with data. `Tools.ToolError` is for failures a model must see as failures. Its `code` is a closed list, with the `path` where one exists.
3. **Limits are disclosed.** A capped result says so: `truncated`, `stdoutTruncated`, or a notice line naming what was shown and what there was.
4. **Capture is bounded where it is read.** A command that prints gigabytes costs the bound.
5. **Child processes get a small environment**: `PATH`, `HOME`, `USER`, `LANG`, `LC_*`, `TERM`, `TMPDIR`, `SHELL`, and what the caller declares. `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `GH_TOKEN` are withheld unless named.
6. **Each tool declares its capability**, so [capabilities](/vips/0058-capabilities) checks every call, and a plan can list what a tool set may touch. A tool's arguments come from a model, so the kernel checks the resolved resource again at the call.
7. **Each tool carries Effect's annotations.** `Tool.Readonly`, `Tool.Destructive` and `Tool.Idempotent` are set from the declared capability, so an MCP host that lists these tools sees the same facts ([std-mcp](/vips/0065-std-mcp)).
8. **`read` preserves bytes.** It keeps a trailing `\r` in CRLF files, so its text is a valid edit anchor. `edit` fails on an anchor that no longer matches; it never overwrites a concurrent change.
9. **Search has three implementations behind one service**: ripgrep (`NativeSearch`), an in-process walk (`PortableSearch`) and a remote machine (`RemoteSearch`). The host picks.
10. **`Tools.readOnly` is a tool set, not a confinement.** A program that also hands over `Tools.shell` has handed over writes.
11. **Inside a task, each call is a recorded step**, as every durable call is. A direct call outside a task is an ordinary live Effect.
12. **A custom tool is Effect's.** `Tool.make` and `Toolkit.make` work in Vibe 0.0.13, and `Toolkit.merge` joins one to the standard set.

### What must be built

The reference engine's std package declares each tool as a reference engine flow (`Read.flow`, `Read.run`, `Read.capabilities`, `Read.effects`). Effect's `LanguageModel` takes `Tool`s. No adapter exists at `main@origin` `bcf8076a4ff4`. This VIP needs one function in each direction: a flow declaration with a handler as a `Tool`, and a `Tool` as a `FlowBinding.Binding` for the cell loop. [std-agent](/vips/0063-std-agent) needs the second.

### Host needs

`Tools.filesystem` and `Tools.shell` need a machine: Node, Bun or a sandbox. `Tools.http` and `Tools.web` run anywhere `HttpClient` does, including a browser and a Worker. The root of the reference engine's std package "reaches no `node:*` module".

## Compared

The same program in the reference engine 1.x. It type-checks against the reference engine's std package 1.0.0-rc.16.

```ts
import { Grep, Read } from "@smthrs/std"
import { Effect } from "effect"

export const program = Effect.gen(function*() {
  const hits = yield* Grep.run({ pattern: "TODO", root: "/workspace/src" })
  const first = yield* Read.run({ path: "/workspace/src/index.ts" })
  return { hits, content: first.content }
})
```

| Program | Tokens (o200k_base) | Lines |
| --- | --- | --- |
| Vibe, proposed | 57 | 5 |
| Reference engine 1.x | 83 | 8 |

A direct call is nearly the same in both. The gap opens when a model uses the tools: the reference engine registers flows with the host's catalog, and Vibe passes `Experimental.Tools.filesystem`.

**Checked.** The Vibe example uses only existing syntax and compiles under `vibelang` 0.0.13 against a declaration of `Tools.grep` and `Tools.read`. The reference engine program type-checks as shown. `Tool.make`, `Toolkit.make` and the `Tool.Readonly` annotation resolve in 0.0.13 with no import.

## Principles

- **TypeScript-first.** Functions and values.
- **Effect-second.** `Tool` and `Toolkit` are Effect's. This module is a set of them. No second tool type.
- **Optimized for agentic programs.** THESIS 7: tool calls are "as basic as HTTP and files". The standard set is in scope.
- **Highly forkable.** A fork adds or removes a tool in one list. The search service already has three implementations behind one seam.
- **Factory-first.** The factory's agents use these tools and no private ones.

## What this changes

- `Experimental.Tools` is new. No grammar changes.
- One adapter pair is built, as listed.

## Alternatives

- **Keep them as reference engine flows**, `Read.run` and `Read.flow`. Then a model reached through Effect's `LanguageModel` cannot use them, and Vibe has two tool types.
- **Derive a tool from an `effect function`**, so any function is a tool: `Tool.from(grep)`. The compiler would derive the parameter schema from the signature, as it does for `task`. It is a real token saving and a language feature. See open question 1.
- **Ship no tools; let each project write its own.** Every agent then rewrites file reading with different truncation, and none of them match what a model was trained to expect.
- **Everything the reference engine's std package exports.** It also has `Checkpoints`, `Container`, `Relocate`, `TreeFingerprint`, `Probe`, `Explore` and `UpdatePlan`, which serve the reference engine's own run model and products. A language's tools do not need a repository to read a file.

## Follow-up questions

1. **Tools from functions.** Should `Tool.from(effectFunction)` derive a tool's schemas from a signature? It needs the compiler, as VIP-44's derivation does. Recommendation: yes, as its own language VIP after this set; it removes the last place a Vibe program writes a schema by hand for a model.
2. **Which shell shape?** The reference engine ships `Bash` and a `ShellCommand` shaped like OpenAI's coding-agent CLI tools, because models trained on different tool sets call different shapes. Recommendation: `Tools.shell` is `Bash`; ship the OpenAI CLI shapes (`ShellCommand`, `ApplyPatch`) as `Tools.codex`.
3. **A default web search provider.** The reference engine implements `WebSearch` with Exa. A standard library naming one vendor is a decision. Recommendation: ship the `WebSearch` service and the Exa layer, and make no layer the default.

## Depends on

- [capabilities](/vips/0058-capabilities): each tool's declared permission.
- [std-durable](/vips/0060-std-durable): recorded calls inside a task. A direct call needs nothing in this set.

[std-sandbox](/vips/0067-std-sandbox) runs the same tools on another machine and needs no change here.
