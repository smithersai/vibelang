# Simplifying Excessive Nesting

Dependent computations often need several intermediate values at once. VibeLang gives them ordinary local names, so sequencing needs no nested callbacks or record of named bindings. In TypeScript Effect code, do notation and generators express the same dependency order.

## Recognizing nesting in dependent pipelines

```vibe
// pending: VIP-1, VIP-2, VIP-3, VIP-5, VIP-6, VIP-12, VIP-14, VIP-17
// run: provide TestClock.layer() { try TestClock.setTime(0); const worker = fork example(); try TestClock.adjust("40 millis"); try Console.log(join worker) }
effect function elapsed<A, E, R>(program: A!E!R) {
  const started = try Clock.currentTimeMillis
  const value = try program
  const finished = try Clock.currentTimeMillis
  try Console.log(`completed in ${finished - started} ms`)
  return value
}

effect function example() {
  return try elapsed(effect {
    try sleep("40 millis")
    return "complete"
  })
}
```

```output
completed in 40 ms
complete
```

Later statements still see `started` and `value`, with no nested callback to keep each in scope. The Effect parameter preserves its success, error, and requirement types, so errors and services from `program` pass through `elapsed`.

## Named bindings with do notation

```vibe
// pending: VIP-1, VIP-2, VIP-5, VIP-6, VIP-12, VIP-14, VIP-17
// run: provide TestClock.layer() { try TestClock.setTime(0); const worker = fork readInterval(); try TestClock.adjust("40 millis"); try Console.log(try Effect.try(() => JSON.stringify(join worker))) }
effect function readInterval() {
  return try Effect.Do.pipe(
    Effect.bind("started", () => Clock.currentTimeMillis),
    Effect.bind("value", () => effect {
      try sleep("40 millis")
      return "complete"
    }),
    Effect.bind("finished", () => Clock.currentTimeMillis)
  )
}
// Returns { started, value, finished }.
```

```output
{"started":0,"value":"complete","finished":40}
```

`Effect.Do` is an Effect value holding an empty record, and its `.pipe` method applies Effect's data-last `Effect.bind` to it, as in TypeScript; `try` runs the pipeline and returns the record. Each `Effect.bind` runs the Effect its callback returns and adds the result under a new, unique field name; later callbacks see earlier fields. The style suits maintaining an existing pipeline; local variables are the usual VibeLang spelling.

## Introducing derived values

```vibe
// pending: VIP-1, VIP-2, VIP-5, VIP-6, VIP-12, VIP-14, VIP-17
// run: provide TestClock.layer() { try TestClock.setTime(0); const worker = fork intervalRecord(); try TestClock.adjust("40 millis"); try Console.log(try Effect.try(() => JSON.stringify(join worker))) }
effect function intervalRecord() {
  return try Effect.Do.pipe(
    Effect.bind("started", () => Clock.currentTimeMillis),
    Effect.bind("finished", () => effect {
      try sleep("40 millis")
      return try Clock.currentTimeMillis
    }),
    Effect.let("millis", ({ started, finished }) => finished - started)
  )
}
```

```output
{"started":0,"finished":40,"millis":40}
```

`Effect.let` adds a field computed by a synchronous, non-failing callback; use `bind` when the field needs Effect work. In an effect function both become `const` declarations, and the compiler infers each expression's contract.

## The sequence as ordinary statements

```vibe
// pending: VIP-1, VIP-5, VIP-6, VIP-12, VIP-14, VIP-17
// run: provide TestClock.layer() { try TestClock.setTime(0); const worker = fork intervalRecord(); try TestClock.adjust("40 millis"); try Console.log(try Effect.try(() => JSON.stringify(join worker))) }
effect function intervalRecord() {
  const started = try Clock.currentTimeMillis
  try sleep("40 millis")
  const finished = try Clock.currentTimeMillis
  const millis = finished - started
  return { started, finished, millis }
}
```

```output
{"started":0,"finished":40,"millis":40}
```

This is the VibeLang form of the same sequence. In a TypeScript file, `Effect.gen(function* () { ... })` binds each Effect result with `yield*` to a local name; in a `.vibe` file, an effect function sequences those operations with `try`. Use `effect { ... }` when a combinator needs an Effect built from several statements. `do { ... }` is a TC39 do expression: it runs immediately and gives the block's normal completion value. Operands to its left are evaluated first. In a derived constructor, a `this` read before a later `do` that calls `super()` still reads an uninitialized receiver; moving `super()` into the `do` does not make that earlier read valid.

A `do` in a dynamic `import()` specifier or options runs where that argument is evaluated. The import keeps JavaScript's native syntax and Promise behavior, and evaluates the specifier before the options. Computed `super` references keep their native syntax too; `import.meta.url`, `new.target`, template tags, optional chains and `delete` retain their ordinary JavaScript meaning.

A `do` on the right of a `super` assignment currently retains a function boundary so the assignment keeps its native receiver and base. An outward `return`, `var`, `break`, `continue`, `await` or `yield` in that position is `EK0204`; move that work into a preceding statement.

`do` keeps ordinary expression typing: `const exact = do { 1 }` has type `1`, while `let ordinary = do { 1 }` widens to `number`. A written type where the `do` stands, such as a function's return type, reaches the alternatives that produce the value, so `(flag: boolean): 'a' | 'b' => do { flag ? 'a' : 'b' }` compiles as the conditional would in place. `do { 7; {} }` retains `7`, because the empty block inherits the preceding value; an entirely empty `do` gives `undefined`. `provide` and interruption blocks preserve these completion values too, including values carried through a locally consumed `break`.

In plain code, a `try`/`finally` inside `do` keeps the `try` or `catch` value when `finally` finishes normally. A jump from `finally` replaces that completion: `do { label: { try { 1 } finally { 2; break label } } }` gives `2`; omitting `2;` gives `undefined`.

A `do` block cannot end with a declaration, including `var` (`EK0201`). Write `do { var value = 1; value }` to supply a value; its `var` still hoists to the enclosing function. Empty statements or blocks after the declaration do not make a final declaration valid.

A `do` on the right of `&&`, `||` or `??` runs only in that operator’s selected branch and keeps its TypeScript narrowing. For example, `x !== undefined && do { x.length }` accepts `x: string | undefined`; assigning `undefined` to `x` before reading `x.length` still reports an error. The left operand runs once.

An `effect function*` produces a Stream with `yield`. A plain `function*` is a JavaScript generator. Consume a Stream with `for try`.

## Coming from Effect

- `Effect.Do` and named `bind` fields usually become local `const` bindings.
- A derived `Effect.let` field becomes an ordinary expression.
- An `Effect.gen` body becomes an effect function body, with `try` replacing `yield*`.

Region finalizers see the ordinary generator result: `undefined` for normal completion or an outward `break`/`continue`, and the returned value for `return`. The source block can still supply a different completion value to `do`; compiler control records stay private.
