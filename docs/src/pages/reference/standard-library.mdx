# Standard Library [What ships on each package subpath, and what does not yet]

This page is a map of the `vibelang` package as it ships, measured on
2026-09-05 against the package's own export list. Module names below are real
import specifiers. Where a name is a design intent rather than an export, the
page says so.

## Design Contract

The standard library:

- operates on ordinary VibeLang values and functions
- returns `Result<A, E>` for recoverable errors
- defines platform services as abstract classes extending `Context`
- works across JavaScript hosts where applicable
- derives schemas and codecs from ordinary types
- includes structured concurrency without a fiber runtime

TypeScript-compatible built-ins remain available. There is no `Array` module —
ordinary `Array.prototype` is the array API. Collection misses use `T |
undefined`.

## One caveat before the map

:::warning Importable from TypeScript today, not yet from `.vibe` — measured 2026-09-05
Every subpath below resolves from ordinary TypeScript and JavaScript. From a
`.vibe` file, only `vibelang/context` and `vibelang/provider` are recognized by
the compiler. Importing any other subpath from `.vibe` is refused with
`VIBE1510`, "foreign module initialization can panic before a checked call
boundary", because the compiler treats the package's other modules as untrusted
foreign code, and a capability class declared there (`Console`, `Clock`,
`FileSystem`) is not recognized as a capability: `Console.context()` from
`vibelang/platform` is an ordinary foreign call, not a requirement.

The consequence is visible in [Getting Started](/introduction/getting-started):
the scaffold declares its own `Console` instead of importing the shipped one.

Closing this is a compiler change, not a library change, and it is small:
extend the trusted-specifier registry (the reference's `vibelang/context` and
`vibelang/provider` entries, and the Go bridge's matching list) to the
subpaths on this page, and let capability-base recognition accept the runtime's
`Context` declaration as well as the prelude's. Until it lands, declare
capabilities in `.vibe` and implement them behind a `.ts` adapter carrying
`@module` and `@throws {never}`.
:::

## Configuration and Time

`Duration`, `Instant`, and `Schedule` are pure values. Reading the wall clock
needs `Clock`; waiting is explicit through a `Sleeper`; configuration reads use
`Environment` and never ambient process state.

## Platform Services

Services use the same library-shaped declaration and access model as
application capabilities:

```ts
import { Context } from "vibelang/context"

abstract class Clock extends Context {
  abstract now(): Instant
}

function timestamp(): Instant {
  const clock = Clock.context()
  return clock.now()
}
```

The inherited `Clock.context()` method is compiler-aware: it adds `Clock` to
`timestamp`'s inferred requirement row, while callers continue to use
`timestamp()` with no explicit context argument. Layers from
`vibelang/provider` supply the host-specific implementation.

## Concurrency and Streams

The library uses static concurrency combinators, cancellation, and workers
rather than Effect-style fibers or parser-level Promise syntax. Helpers contain
and join the work they start; Queue and Stream runners preserve typed
cancellation and failure Results. Inside a durable Flow, arrival-order
combinators (`Promise.race`, `Promise.any`) are reachable only through the
deterministic `Scheduler`.

## Durable Runtime

`Action` and `Flow` are the two authoring names. `Artifact`, `Signal`,
`Journal`, and `Deployment` are design names, not exports; the shipped
spellings are `PlanArtifact`, `SignedDeployment`, and `DeploymentManifest` on
`vibelang/durable`, `SignalNode` as a durable IR type, and `TurnJournal` in the
agent library.

## Agent Library

The agent library provides MDX prompt rendering, model adapters, TypeScript
compilation, sandbox execution, and optional Action and Flow durability
adapters. It ships as `vibelang/agent`; the constructor names on the
[Agent Library](/guide/agent-library) page are directional except where that
page says otherwise.

## Implementation Strategy

Compute-heavy components may call into Wasm modules, including implementations
written in Zig, imported through the asset loaders — a design intent, not a
shipped path: no `zig`, `rust`, or `wasm` loader is registered, and such an
import is refused with `VIBE5213`. JavaScript/Wasm boundaries should be chosen
by measurement. Host-specific implementations remain behind capabilities.
