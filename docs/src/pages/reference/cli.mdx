# CLI [Target compiler, tooling, and deployment commands]

The `vibe` command operates on one checked project graph. Project commands
resolve `.vibe`, TypeScript, JavaScript, generated asset modules, compiler-known
inputs, and package declarations before they emit or execute anything.

Users do not select a compiler implementation or lowering backend. The command
contract is defined by VibeLang semantics and the selected JavaScript host.

This page includes target commands; not every command below is shipped. The
`plan` section documents the current native Go-backed inspection command.
Existing `--backend js|go` flags select SDK or direct-native delivery profiles,
not different compiler libraries: both use the same pinned Go TypeScript engine.

## Commands

```bash
vibe check src/index.vibe
vibe compile src/index.vibe --outDir build
vibe run src/index.vibe
vibe test
vibe inspect src/index.vibe --format json
vibe plan src/build.vibe --input preview.json --providers providers.json --planId build/preview
vibe build --outDir dist
vibe format . --check
vibe lsp
vibe doctor --format json
```

| Command | Contract |
| --- | --- |
| `check` | Checks the complete project graph, including failure and requirement rows, without writing output. |
| `compile` | Emits JavaScript, declarations, source maps, generated asset modules, and emitted Flow bodies with their Effect Manifests as requested. |
| `run` | Checks and executes one application entry on the selected JavaScript host. |
| `test` | Discovers, checks, and runs the project's tests with deterministic reporting and configured resource limits. |
| `inspect` | Reports types, failure and requirement rows, compiler-known inputs, generated modules, and Flow metadata without executing the program. |
| `plan` | Derives and publishes a keyed node graph from checked source, explicit input and provider declarations, without executing the Flow or dispatching Actions. Historical Manifest inspection requires explicit compatibility mode. |
| `build` | Resolves deployment providers and emits coordinator, worker, manifest, codec, and signature inputs for selected Flows. |
| `format` | Formats supported source files or checks whether they are formatted. |
| `lsp` | Runs the VibeLang language server over stdio. |
| `doctor` | Reports whether the configured compiler, JavaScript host, foreign toolchains, signing setup, and sandbox providers satisfy the project contract. |

## Project Selection

Commands load project configuration from the nearest VibeLang configuration
file unless `--project` selects one explicitly. An entry path is resolved inside
that project. Source identity uses canonical project-relative paths; aliases
that make one file appear under multiple identities are rejected.

One invocation is atomic. If discovery, loading, checking, lowering, validation,
or output collision detection fails, no part of the new output set is
committed.

:::note Direction
The configuration filename and schema, workspace behavior, default entry
selection, and exact project-root flags remain to be specified.
:::

## Check

```bash
vibe check src/index.vibe
vibe check --project vibelang.json --format json
```

`check` performs the same graph discovery, asset loading, comptime evaluation,
Flow body and Effect Manifest derivation, declaration-boundary validation, and
semantic checks as `compile`, but never emits project artifacts.

## Compile

```bash
vibe compile src/index.vibe \
  --outDir build \
  --declaration \
  --sourceMap
```

`compile` emits the complete reachable graph. Output paths are deterministic
and contained by `--outDir`. Relative runtime edges are rewritten to emitted
artifacts; package and host-module imports remain external unless the project
selects a bundling integration.

Declarations preserve public Result failures and compiler-inferred requirement
rows for downstream VibeLang consumers. Source maps trace generated JavaScript
back through VibeLang and comptime lowering to authored source. Compiler-created
text with no authored location remains explicitly unmapped.

## Run

```bash
vibe run src/index.vibe -- arg1 arg2
```

`run` checks the same graph as `compile`, creates an isolated temporary output
set, and executes the selected entry on the configured JavaScript host. Text
after `--` is passed to the program. Runtime code receives the host authority of
that process; `run` is not a security sandbox.

When structured output is selected, program stdout and stderr are captured in
separate result fields and never corrupt the command envelope.

## Test

```bash
vibe test
vibe test test/account.vibe --timeout 30s --format json
```

The test runner discovers tests according to project configuration, checks all
selected modules before starting execution, applies per-test time and resource
limits, and reports nominal Results and unexpected defects separately. Test
processes receive only the capabilities and host authority configured for the
test target.

:::note Direction
Test declaration syntax, discovery conventions, isolation granularity,
fixtures, watch mode, and coverage integration remain open.
:::

## Inspect

```bash
vibe inspect src/index.vibe
vibe inspect src/index.vibe --format json
```

`inspect` is a read-only semantic query. Its structured output includes the
resolved project graph, public function channels, capability paths, tracked
comptime and loader inputs, generated module identities, and compiled Flow and
Action contracts. It does not classify code for withdrawn non-TypeScript
targets.

## Plan

```bash
vibe plan src/build.vibe \
  --input preview.json \
  --providers providers.json \
  --planId build/preview \
  --outFile build/preview.plan.json \
  --format json
```

`plan` defaults to `--profile keyed`. It accepts exactly one `.vibe` source entry
and requires the three explicit options above. The input file contains the JSON
encoding of the Flow's input, including for a Flow that performs no Actions. The
providers file contains an array; each referenced Action needs an explicit
declaration of this shape (use `[]` when no provider is needed):

```json
[
  {
    "actionId": "build.vibe#Compile",
    "implementationId": "compile/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

These are inspection declarations, not verified provider bytes or execution
authority. The example digest is a placeholder, not an authenticated bundle.
The compiler does not infer missing providers, tiers or effects. A graph digest
does not constitute approval: execution separately requires authenticated
source/provider/runtime artifacts and approval of the complete invocation,
including its input, authority envelope and deployment identity.

The Go compiler checks the source and input contract and emits canonical Plan
bytes containing all nodes in the supported graph, dependency edges, keys,
declared effects, `baseDigest`, and `digest`. It never invokes the authored Flow,
module initializers or callbacks to discover work. Static child Flows, bounded
static fan-out and checked pure value computations are supported. Ordinary
loops, mutable/module captures, graph-dependent branch selection and bounded
runtime rounds still refuse; rejection never falls back to body replay or a
sets-only Manifest.

`--exportName` selects an exported Flow when needed. `--flowId` overrides its
declaration-derived identity; `--flowVersion` defaults to 1 and must be a positive
safe integer. `--rootDir` bounds source discovery and sets project-relative
identities; it defaults to the entry file's directory. Only deterministically
resolved `.vibe` dependencies inside that root are included. Ambiguous imports
and hard-link identity aliases refuse. The source closure is limited to 257
files and 2 MiB in total. Input and provider files are limited to 16 MiB each.
All files must be regular UTF-8 files. Original source bytes, including a source
BOM, contribute to identity; JSON BOMs, duplicate keys, negative zero and other
noncanonical durable values are rejected by Go before a host JSON parser can
discard that evidence.

The JSON report carries `profile: "keyed"`, `planId`, `digest`, and `plan`.
`--outFile` writes the compiler's canonical Plan bytes followed by a newline,
only after successful checking. It cannot name a source, dependency, input or
providers file, including a hard-link alias, or an output symlink (even a dangling
one). A refusal preserves the prior output. Native source/data refusals exit 1.
Command-handler misuse, unreadable files and output collisions exit 2. The CLI
argument parser's own schema errors (for example, an invalid `--flowVersion`)
exit 1 with `VALIDATION_ERROR` before the command handler runs.

Historical inspection remains available explicitly:

```bash
vibe plan src/build.vibe --profile manifest-compat \
  --bindings actions.json --outFile build/preview.manifest.json --format json
```

This mode preserves the old Effect Manifest and binding-file contract; it is
not a keyed Plan or execution approval. Supplying `--bindings` alone does not
select it. Mixing keyed options with this compatibility profile is refused.

## Build

:::note Target deployment command
Deployment-provider resolution, coordinator/worker packaging and signing policy
remain product-integration work. The shipped `vibe build` still forwards
TypeScript project-reference builds to the Go compiler; it is not yet a command
for deploying a durable Flow. The keyed `plan` command does not change the
historical `compile`/`run` body-emission path into the new durable runtime.
:::

## Format

```bash
vibe format src test
vibe format . --check
vibe format src/index.vibe --stdout
```

Formatting is deterministic and semantics-preserving. Files are written
atomically by default. `--check` performs no writes and exits nonzero when any
selected file would change; `--stdout` prints one explicitly selected file and
also performs no writes.

## Language Server

```bash
vibe lsp
```

The language server speaks Content-Length-framed JSON-RPC 2.0 over stdin and
stdout. Its target surface includes diagnostics, completion, hover for public
function channels, definition, references, rename, signature help, formatting,
code actions, and semantic navigation across the checked project graph.

Editor behavior must use the same project model and diagnostics as `check`.
Language-service recovery may return partial editor results, but it cannot make
invalid code appear valid.

The current alpha server supports full-document synchronization, diagnostics,
hover, definition and formatting; the other target methods above are not yet
implemented. Formatting, token lookup and static module-literal inspection use
the native Go compiler. Module navigation uses the literal's exact UTF-16 range,
excluding import-attribute strings. Semantic diagnostics and hover also use the
Go-backed language frontend; no TypeScript 5.x compiler-library fallback remains.

## TypeScript Compatibility Commands

VibeLang accepts ordinary `.ts`, `.tsx`, and JavaScript-family modules in the
same project. For scripts that require exact native TypeScript CLI behavior,
the distribution exposes a compatibility command:

```bash
vibec --project tsconfig.json --noEmit
vibec --build --verbose
```

`vibec` preserves TypeScript argument ordering, exit behavior, and output.
It does not enable `.vibe` semantics. A `tsc` alias may be installed only when the
user requests it; VibeLang must not unexpectedly replace an existing compiler.

## Structured Output

```bash
vibe check src/index.vibe --format json
vibe inspect src/index.vibe --format json
vibe test --format json
```

All commands support a versioned machine-readable result envelope. It contains
the command status, diagnostics, artifact inventory where relevant, and
captured program streams where execution occurs. Diagnostics identify authored
files and UTF-16 source spans and retain structured cause paths for requirements,
foreign panic, loader inputs, and durable contracts.

Human-readable text is the default on an interactive terminal. Automation
should select a structured format explicitly.

## Exit and Failure Rules

The CLI fails closed when:

- a source, loader, comptime, foreign-toolchain, or generated module cannot be
  resolved deterministically;
- a compiler-owned intrinsic is used through an unrecognized identity;
- an input escapes the declared project root or aliases another input;
- output paths collide or escape the destination;
- a resource budget is exceeded;
- an unsupported option would change semantic meaning; or
- any diagnostic prevents the requested artifact from being valid.

Warnings never silently downgrade a required check. Resource limits and
timeouts are configurable within implementation-enforced safety ceilings and
are included in cache or deployment identity when they affect semantics.
