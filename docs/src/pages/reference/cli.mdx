# CLI [Target compiler, tooling, and deployment commands]

The `smithers` command operates on one checked project graph. Project commands
resolve `.sm`, TypeScript, JavaScript, generated asset modules, compiler-known
inputs, and package declarations before they emit or execute anything.

Users do not select a compiler implementation or lowering backend. The command
contract is defined by Smithers semantics and the selected JavaScript host.

## Commands

```bash
smithers check src/index.sm
smithers compile src/index.sm --outDir build
smithers run src/index.sm
smithers test
smithers inspect src/index.sm --format json
smithers plan build/Build.flow.json --input preview.json
smithers build --outDir dist
smithers format . --check
smithers lsp
smithers doctor --format json
```

| Command | Contract |
| --- | --- |
| `check` | Checks the complete project graph, including failure and requirement rows, without writing output. |
| `compile` | Emits JavaScript, declarations, source maps, generated asset modules, and emitted Flow bodies with their Effect Manifests as requested. |
| `run` | Checks and executes one application entry on the selected JavaScript host. |
| `test` | Discovers, checks, and runs the project's tests with deterministic reporting and configured resource limits. |
| `inspect` | Reports types, failure and requirement rows, compiler-known inputs, generated modules, and Flow metadata without executing the program. |
| `plan` | Reads a compiled Flow's Effect Manifest, validates optional preview input, and prints the Flow's reachable Actions, requirement row, external-input contracts, and failure row without loading the Flow body or dispatching Actions. |
| `build` | Resolves deployment providers and emits coordinator, worker, manifest, codec, and signature inputs for selected Flows. |
| `format` | Formats supported source files or checks whether they are formatted. |
| `lsp` | Runs the Smithers language server over stdio. |
| `doctor` | Reports whether the configured compiler, JavaScript host, foreign toolchains, signing setup, and sandbox providers satisfy the project contract. |

## Project Selection

Commands load project configuration from the nearest Smithers configuration
file unless `--project` selects one explicitly. An entry path is resolved inside
that project. Source identity uses canonical project-relative paths; aliases
that make one file appear under multiple identities are rejected.

One invocation is atomic. If discovery, loading, checking, lowering, validation,
or output collision detection fails, no part of the new output set is
committed.

:::note Direction
The configuration filename and schema, workspace behavior, default entry
selection, and exact project-root flags remain to be specified.
:::

## Check

```bash
smithers check src/index.sm
smithers check --project smithers.json --format json
```

`check` performs the same graph discovery, asset loading, comptime evaluation,
Flow body and Effect Manifest derivation, declaration-boundary validation, and
semantic checks as `compile`, but never emits project artifacts.

## Compile

```bash
smithers compile src/index.sm \
  --outDir build \
  --declaration \
  --sourceMap
```

`compile` emits the complete reachable graph. Output paths are deterministic
and contained by `--outDir`. Relative runtime edges are rewritten to emitted
artifacts; package and host-module imports remain external unless the project
selects a bundling integration.

Declarations preserve public Result failures and compiler-inferred requirement
rows for downstream Smithers consumers. Source maps trace generated JavaScript
back through Smithers and comptime lowering to authored source. Compiler-created
text with no authored location remains explicitly unmapped.

## Run

```bash
smithers run src/index.sm -- arg1 arg2
```

`run` checks the same graph as `compile`, creates an isolated temporary output
set, and executes the selected entry on the configured JavaScript host. Text
after `--` is passed to the program. Runtime code receives the host authority of
that process; `run` is not a security sandbox.

When structured output is selected, program stdout and stderr are captured in
separate result fields and never corrupt the command envelope.

## Test

```bash
smithers test
smithers test test/account.sm --timeout 30s --format json
```

The test runner discovers tests according to project configuration, checks all
selected modules before starting execution, applies per-test time and resource
limits, and reports nominal Results and unexpected defects separately. Test
processes receive only the capabilities and host authority configured for the
test target.

:::note Direction
Test declaration syntax, discovery conventions, isolation granularity,
fixtures, watch mode, and coverage integration remain open.
:::

## Inspect

```bash
smithers inspect src/index.sm
smithers inspect src/index.sm --format json
```

`inspect` is a read-only semantic query. Its structured output includes the
resolved project graph, public function channels, capability paths, tracked
comptime and loader inputs, generated module identities, and compiled Flow and
Action contracts. It does not classify code for withdrawn non-TypeScript
targets.

## Plan and Build

```bash
smithers plan build/Build.flow.json --input preview.json
smithers build --flow Build --outDir dist
```

`plan` performs the **inspection** phase. It consumes a Flow's Effect Manifest
**(PR-1)**, verifies the Flow identity and schema, validates optional preview
input, and reports the Flow's reachable Actions, capability requirement row,
external-input contracts, and failure row. It never loads or invokes the emitted
Flow body and never dispatches an Action.

What it reports is a **bound on what the Flow may request**, not a prediction of
what a run will do. The Manifest carries no control-flow edges, no branch
structure, and no execution counts, so a branch whose condition is unknown is not
reported at all — the previous behavior of emitting an explicit conditional or a
parameterized fan-out template is withdrawn, not reworded.

`build` resolves the selected deployment Layers, validates every Action
provider and policy, partitions coordinator and worker artifacts, derives wire
codecs, and emits a canonical deployment manifest. The emitted Flow body must
survive tree-shaking into every artifact that can create or resume an execution
of that Flow. Signing is a separate explicit step or configured build policy; an
unsigned artifact cannot be silently treated as authenticated, and a signature
attests to what a Flow **is and may request**, not to what a run will do.

:::note Direction
The artifact extension, provider configuration, signing commands, deployment
profiles, and remote publication workflow remain open. The command is still
spelled `plan` although the artifact it reads is the Effect Manifest rather than
a plan; whether to rename it is a product decision no page has made, so it is
recorded here rather than pre-empted.
:::

## Format

```bash
smithers format src test
smithers format . --check
smithers format src/index.sm --stdout
```

Formatting is deterministic and semantics-preserving. Files are written
atomically by default. `--check` performs no writes and exits nonzero when any
selected file would change; `--stdout` prints one explicitly selected file and
also performs no writes.

## Language Server

```bash
smithers lsp
```

The language server speaks Content-Length-framed JSON-RPC 2.0 over stdin and
stdout. Its target surface includes diagnostics, completion, hover for public
function channels, definition, references, rename, signature help, formatting,
code actions, and semantic navigation across the checked project graph.

Editor behavior must use the same project model and diagnostics as `check`.
Language-service recovery may return partial editor results, but it cannot make
invalid code appear valid.

## TypeScript Compatibility Commands

Smithers accepts ordinary `.ts`, `.tsx`, and JavaScript-family modules in the
same project. For scripts that require exact native TypeScript CLI behavior,
the distribution exposes a compatibility command:

```bash
smithersc --project tsconfig.json --noEmit
smithersc --build --verbose
```

`smithersc` preserves TypeScript argument ordering, exit behavior, and output.
It does not enable `.sm` semantics. A `tsc` alias may be installed only when the
user requests it; Smithers must not unexpectedly replace an existing compiler.

## Structured Output

```bash
smithers check src/index.sm --format json
smithers inspect src/index.sm --format json
smithers test --format json
```

All commands support a versioned machine-readable result envelope. It contains
the command status, diagnostics, artifact inventory where relevant, and
captured program streams where execution occurs. Diagnostics identify authored
files and UTF-16 source spans and retain structured cause paths for requirements,
foreign panic, loader inputs, and durable contracts.

Human-readable text is the default on an interactive terminal. Automation
should select a structured format explicitly.

## Exit and Failure Rules

The CLI fails closed when:

- a source, loader, comptime, foreign-toolchain, or generated module cannot be
  resolved deterministically;
- a compiler-owned intrinsic is used through an unrecognized identity;
- an input escapes the declared project root or aliases another input;
- output paths collide or escape the destination;
- a resource budget is exceeded;
- an unsupported option would change semantic meaning; or
- any diagnostic prevents the requested artifact from being valid.

Warnings never silently downgrade a required check. Resource limits and
timeouts are configurable within implementation-enforced safety ceilings and
are included in cache or deployment identity when they affect semantics.
