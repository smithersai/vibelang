# Comptime [Reference for phases, targets, inputs, and evaluation]

:::warning Current bounded implementation
The project compiler currently lowers checker-resolved direct/aliased/namespace
`comptime(...)` calls over a bounded static value language. Immediately-called
or private-const compile-time functions support parameters, `const`/`let`,
assignment and compound assignment, `++`/`--`, blocks, `if`, `while`,
`do-while`, classic `for`, `for-of`, unlabeled `break`/`continue`, `return`,
project-local marked calls, interpreter-owned array/object mutation, and a
widened deterministic standard-library allowlist. Selected target branches are
erased, text `embed(...)` inputs are tracked, and retained runtime functions
have marked call sites replaced with evaluated values.

One call tree is bounded to 1,000,000 evaluation steps, 100,000 allocation
nodes, 64 nested calls, and 1,000,000 UTF-16 units per string. Any exhaustion
is VCT1012. A top-level single-declaration comptime const used in type position
also emits a same-named deep readonly literal alias; a non-exported binding
used only as a type erases its runtime const. VCT1013 rejects unsupported type
production. Cache identity, dependencies, source maps, and provenance remain
deterministic. General JavaScript, implicit evaluation, re-exported markers,
spread/destructuring, labeled control flow, closures as values, ambient state,
and non-value-derived computed/mapped/generic types remain design or fail
closed.

With `--backend go` on `smithers check`, `compile`, or `run`, the pinned fork
independently recognizes the same compiler-owned binding and lowers a bounded
comptime language through its checked AST. It supports canonical values, local helpers,
loops and interpreter-owned mutation, hard evaluation budgets,
`comptime.target`, and value-derived literal aliases. It deliberately refuses
`embed(...)` until tracked asset bytes exist in the Go request protocol, and it
does not claim the TypeScript instrument's schema reification, loader, or
persistent-cache surfaces.
:::

## Explicit Form

```ts
import { comptime } from "smithers:comptime"

const value = comptime(expression)
const buildFunction = comptime(functionValue)
```

`comptime(expression)` requires the expression to evaluate during compilation. When the argument is a function, the call marks and returns a compile-time function; it does not invoke the function. Calling the returned function requires that call to evaluate during compilation.

For an immediately evaluated block:

```ts
const value = comptime(() => {
  // deterministic compile-time work
  return result
})()
```

The compiler recognizes the resolved import identity. Import aliases retain these semantics; unrelated functions named `comptime` do not. `smithers:comptime` is a compiler-owned virtual module and has no ordinary uncompiled runtime fallback.

Valid result categories include:

- runtime-emittable values
- comptime-only values
- types
- typed module descriptions from loaders

The bounded implementation emits runtime-emittable canonical values and can
materialize their deep readonly literal shape as a same-named type alias. It
does not materialize arbitrary computed, mapped, conditional, or generic types
as compile-time results.

Durable Plan IR is produced separately through `durable(...)`, not by executing a Flow as a compile-time function.

## Implicit Evaluation

The compiler may evaluate code automatically when all inputs are known. Implicit evaluation must not change observable runtime semantics.

The current frontend performs ordinary TypeScript constant checking but only
executes work explicitly rooted at the imported `comptime` intrinsic.

## Target

```ts
import { comptime } from "smithers:comptime"

comptime.target
```

Current target vocabulary is direction and includes:

```text
node  bun  deno  browser  edge
```

A branch resolved from `comptime.target` is eliminated for other targets.

The bounded implementation supports this inside an erased compile-time function
and evaluates only the selected branch.

## Allowed Inputs

Comptime code may depend on:

- literals and other comptime values
- checked pure computation
- compiler configuration exposed through a typed API
- compiler-tracked imports and embedded assets
- loader-context dependencies

## Unavailable Ambient State

Comptime code cannot directly observe:

```text
filesystem  network  environment  process  clock  random  mutable host state
```

An equivalent input is valid only when supplied through a tracked compiler mechanism.

## Loader Contract

A loader conceptually receives:

```ts
type Loader = (
  asset: CompilerAsset,
  context: LoaderContext,
) => TypedModule
```

The context records transitive imports and reports structured diagnostics. A
programmatic source-asset POC provisionally recognizes a project file whose
default export is `comptime.loader("type", fn)` by checker identity and always
runs the function in its no-permission Deno loader process. Built-ins take
precedence and duplicate project registrations fail closed. Package-distributed
loaders, glob/extension selectors, configuration, the final typed-module
builder, and the production spelling remain open.

## Cache Identity

A comptime result is keyed by all semantically relevant inputs, including:

```text
compiler version
evaluated implementation graph
configuration
target
source bytes
transitive dependency hashes
```

Process-local function identity is insufficient for a portable cache key.

## Errors

Compilation fails when explicit `comptime(...)` code:

- depends on a runtime-only value
- requests an unavailable capability
- exceeds resource limits
- produces an invalid type or module
- attempts an untracked read
- uses an operation unsupported by the target-neutral evaluator

Loader diagnostics should retain source spans into the original asset.
