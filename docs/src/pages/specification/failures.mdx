# Failure Semantics [Normative model for Result values and nominal Error classes]

Status: the Result return model, ordinary `Error` subclasses, compiler lifting, and Promise restrictions are **locked**. The complete convenience-method set and declaration encoding are **direction**.

## Result Model

A function that can complete with a recoverable error MUST return:

```ts
Result<A, E>
```

`A` is the success value and `E` is an `Error` subtype or union of `Error` subtypes. A fallible async function MUST return:

```ts
Promise<Result<A, E>>
```

Failure MUST be represented in the ordinary return value. Smithers MUST NOT encode `E` as an erased `throws` annotation or a second Promise type parameter.

## Error Classes

Any named class extending `Error` MUST be usable as a nominal recoverable error:

```ts
class NotFound extends Error {
  constructor(readonly id: string) {
    super(`Not found: ${id}`)
  }
}
```

Authors MUST NOT need a `TaggedError("Name")` factory, `_tag` declaration, or separate error-declaration syntax. The compiler MUST provide stable nominal identity, matching metadata, serialization evidence, and cross-realm transport metadata while preserving ordinary `Error` behavior.

## Compiler Lifting

Inside a function inferred or declared to return `Result<A, E>`:

- `return value` MUST produce the success variant
- `throw error` MUST produce the error variant and exit the function
- returning an existing compatible Result MUST preserve it without nesting

Authors MUST NOT need to write `Result.ok(...)` or `Result.err(...)`. Those constructors MUST NOT be part of the ordinary Smithers authoring API.

A function with no fallible path MUST continue to return its ordinary success type rather than an unnecessary Result.

A `.sm` function with a reachable recoverable Error exit MUST return or infer a Result. An explicit non-Result return annotation on such a function MUST be a compile error. The distinguished `panic` case is tracked separately from ordinary recoverable Error variants.

## Inference and Public Contracts

When a function body has no explicit return annotation, the compiler MUST infer `A` from successful returns and `E` from:

- reachable `throw error` statements
- propagated `!` operators
- existing Results returned from the function
- foreign exception or rejection boundaries

Public, abstract, ambient, and declaration-only contracts MUST express fallibility directly with `Result<A, E>` or `Promise<Result<A, E>>`.

Smithers MUST NOT add a general `throws` clause, `!T` type marker, prefix `try` expression, or postfix Result-recovery expression. Panic MUST be explicitly catchable; the final catch spelling is not fixed by this page.

## Failure Propagation

The postfix `!` operator MUST yield the success value or propagate the error variant from the enclosing Result-returning function:

```ts
function displayName(id: string) {
  const user = findUser(id)!
  return user.displayName
}
```

This is the role Zig gives `try expr`, using an operator TypeScript already has, so it costs no grammar.

`!` MUST NOT retain TypeScript's non-null assertion meaning in `.sm`. The definite-assignment form `x!: T` MUST also be rejected. Removing the prior meaning entirely is what makes the reuse unambiguous.

`??` and `?.` MUST keep their ordinary nullish semantics and MUST NOT be reinterpreted for failures. Failure and absence are separate axes and MAY appear in one expression:

```ts
const name = findUser(id)!?.nickname ?? "anonymous"
```

Here `!` propagates `NotFound`, `?.` handles an absent nickname, and `??` supplies the absence fallback.

The compiler MUST include the propagated Result's error type in the enclosing function's inferred `E`. The emitted error path MUST complete the enclosing computation with its error variant rather than throw a recoverable JavaScript exception. Where the enclosing function is emitted in the resumable calling convention defined by [Effects](/specification/effects), "complete" means the computation's completion value, which the handler observes; it does not mean a JavaScript `throw`, and a Result error MUST NOT be delivered through the exception channel at any point.

At an explicit non-Result boundary, unsafe extraction MAY throw at runtime and MUST be visually distinct in API naming or diagnostics.

### Refusal Conditions

The lowering emits a delegated suspension, which is an expression in every position and therefore preserves the authored evaluation order everywhere. Placement is unrestricted **(SA-1)**. The conditions that remain on `!` are typing conditions and a control-flow-boundary condition, not lowering conditions.

`!` is accepted in any expression position **(SA-1)**:

```ts
r!.length        // accepted
r!.trim()        // accepted
r![0]            // accepted
r! ?? "fallback" // accepted
maybe ?? r!      // accepted
f(r!)            // accepted
```

The `!` operator MUST be rejected unless the enclosing function declares a Result channel or infers a non-empty failure set, and unless the operand's checker-derived provenance is a Result. Each refusal MUST carry its own diagnostic code.

The `!` MUST NOT be inside a `try` block that has a `catch` clause. The emitted failure exit unwinds the delimited computation: `finally` blocks and `using` disposals run, and `catch` clauses do not. The authored text would read as though the failure were catchable when it is not, so the placement MUST be refused rather than silently lowered. Delivering the failure as a thrown JavaScript exception so that `catch` observes it is prohibited by this section and MUST NOT be adopted as an alternative.

A rejected `!` MUST be a diagnostic, never a silent lowering. Three distinct conditions refuse a `!` and a reader MUST NOT expect one code to cover them: no enclosing Result channel, non-Result provenance, and presence of an enclosing `catch`.

Two further contracts disqualify the **enclosing member** from hosting any `!` rather than rejecting the placement: getters and constructors, and class static blocks. An **authored** `function*` MUST NOT declare or infer a non-empty effect row: the iterator protocol's `throw()` and `return()` injection points mean an authored generator's row is not a function of its own text. The resumable generator form is reserved for compiler emission; its resumption protocol is part of the compiler contract and MUST NOT be spellable in `.sm`.

## Compiler-Owned Modules

`smthrs/result` and the Smithers runtime are **compiler-owned** and MUST NOT be required to be authored in Smithers.

The reason is structural rather than a matter of convenience. `smthrs/result` is the lowering target: emitted code imports it, so authoring it in the language whose lowering depends on it is circular. The compiler links it directly, `!` and `expect` are rejected inside it, and its public API is instance methods — which `.sm` cannot author, because `this` is never a Result operand.

A standard library written in Smithers MAY therefore exclude these modules without being incomplete.

## Matching and Transformation

Result values MUST provide a quality-of-life API modelled on the
[better-result](https://github.com/dmmulroy/better-result) library, with
Smithers's own construction rules.

Inspection and matching:

```text
isOk  isError  match
```

Transformation and sequencing:

```text
map  mapError  andThen  andThenAsync  flatten
```

Recovery:

```text
recover  tryRecover  tryRecoverAsync
```

Observation, which MUST NOT change the Result:

```text
tap  tapAsync  tapError  tapErrorAsync  tapBoth  tapBothAsync
```

Extraction:

```text
unwrapOr  expect
```

Collection and adaptation, as statics:

```text
Result.all  Result.allAsync  Result.partition  Result.partitionAsync
Result.try  Result.tryPromise  Result.codec
```

### Authorability

The API above is the contract Smithers programs may *call*. It is not a claim that every member can be *authored* in Smithers.

Members that must inspect a failure value — `tryRecover`, `tapError`, `mapError`, and the error half of `partition` — are not authorable today, because the language has no form that extracts the error from a Result: `!` propagates it and `match` is a method `.sm` can call but not define. `flatten` is likewise unauthorable, because `!` marks its own output as a plain value without checking, so a `Result<Result<A, E>, E>` cannot be unwrapped one level.

**Open.** Whether Smithers gains an error-extraction form is undecided. It is a real language feature with a spelling to choose, not an oversight, and it is the root of most of the unauthorable members.

**(SA-7) — implementation status, measured 2026-08-28.** The sentence that stood here —
"until it is decided, these members are supplied by the compiler-owned runtime" —
was false, so record the gap rather than assert the fix. The list above is a
`direction` obligation on an implementation, and this one does not yet meet it.
Callable from authored `.sm` today: `isOk isError match map mapError andThen
recover tap tapError unwrapOr expect`, plus the statics `Result.all Result.try
Result.tryPromise`. The other twelve names above resolve nowhere, and the failure
is not the obvious one — a Result member outside the recognized set does not
report an unknown property, it fails the must-use walk and is refused as
`SMITHERS1301`. `flatten` and `tapBoth` exist on the runtime
(`poc/src/runtime/result.ts`) and are reachable from foreign TypeScript through
`smthrs/result`, but the checker's Result surface does not declare them, so
authored `.sm` cannot call them either. See
[Results and Errors](/reference/errors) §Deliberately absent for the per-member
reasoning, including why the async mirror is blocked on the must-use ownership
walk rather than on the runtime.

`match` MUST require both success and error branches. Transformations MUST preserve or correctly combine the Result error type. Async variants MUST return a Promise of the Result rather than a nested Result.

Smithers MUST NOT expose `Result.ok`, `Result.err`, or a `TaggedError` factory: ordinary `return`, `throw`, and `class ... extends Error` construct those. Smithers MUST NOT require `Result.gen`/`yield*` do-notation in authored source, because postfix `!` already provides propagation. This is a constraint on the authoring surface. The compiler MAY emit `yield*` in the lowered form of a function with a non-empty effect row; that form has no `.sm` spelling and MUST NOT appear in an authored type, a public declaration's value syntax, or a diagnostic.

A Result MUST be treated as a must-use value. A source program MUST NOT silently discard a Result without returning, matching, transforming, inspecting, or unwrapping it.

## Error Prototype

Every `Error` instance MUST provide compiler-aware quality-of-life methods:

```text
is  matches  match  matchPartial  rootCause
```

For a statically known error union, `error.match({...})` MUST be exhaustive and MUST narrow each handler argument to its nominal `Error` subclass:

```ts
error.match({
  NotFound: (error) => User.guest(error.id),
  Timeout: (error) => retryAfter(error.ms),
})
```

Handler selection MUST use compiler-stable nominal identity, not a forgeable user `_tag` or minifier-sensitive constructor name in compiled artifacts.

## Foreign Exceptions

Calling any TypeScript, JavaScript, or other foreign runtime implementation MUST add the distinguished checked `panic` case by default. This applies even when the foreign declaration omits throws, and it includes Promise rejection and a runtime implementation violating its declared signature.

A caller MUST propagate panic, explicitly catch it, or use a trusted adapter that catches and translates it. `panic` is imported from `smithers:exceptions` and accepts an optional message or underlying Error.

The compiler MUST recognize trusted JSDoc/declaration metadata at the boundary. `@throws {never}` removes the default panic case; `@throws {T}` declares the stated foreign error channel. These annotations are trust claims and MUST remain visible in declarations and tooling. Exact overload, declaration-merging, generic, and multiple-tag rules remain open.

`Reflect.panic` and compiler/runtime invariant failures enter the same distinguished panic channel. Ordinary Result recovery MUST NOT swallow panic implicitly.

### Panic Does Not Widen a Return Type

Calling `panic(...)` MUST NOT force a function's return type to widen into `Result<A, Panic>`.

This follows from the two rules above rather than being a new decision. Panic is *tracked separately from ordinary recoverable Error variants*, and ordinary Result recovery *MUST NOT swallow it*. `E` is the expected-error channel; a panic is by definition not an expected error. Requiring a panicking function to return `Result<A, Panic>` places the panic inside `E`, where `unwrapOr`, `recover`, and `match` consume it as an ordinary failure — which is precisely what this page forbids, and it silently removes the panic from the caller's channel.

A function that validates an argument, refuses a forgery, or asserts an invariant MUST therefore be able to abort with `panic(...)` while keeping a plain return type.

An author MAY still annotate `Result<A, Panic>` explicitly to materialize a panic as a value; that is how panic is made explicitly catchable. The prohibition is on the compiler *forcing* that widening, not on an author choosing it.

## Promise Semantics

Authored `.sm` code MUST consume Promise instances only through `await`.

Calls to Promise instance `.then()`, `.catch()`, or `.finally()` MUST be compile errors. Imported TypeScript and JavaScript modules retain ordinary Promise behavior internally. A Flow body therefore MUST NOT depend on the interleaving of work started inside an imported module: any such work MUST be consumed at the boundary through a single awaited value, and the runtime journals only that value.

Awaiting `Promise<Result<A, E>>` MUST produce `Result<A, E>`. `await` MUST NOT automatically unwrap, recover, or discard the Result.

Promise rejection at an unannotated Smithers foreign boundary MUST become the checked panic case rather than an untyped rejection escaping the declared contract.

## JavaScript `try/catch`

Ordinary statement-form JavaScript `try/catch` remains valid where JavaScript interoperability requires it. It is not the typed recovery surface for Smithers Results, and its presence MUST NOT change a function's Result contract implicitly.

## Cleanup

Smithers MUST NOT add `defer` or `errdefer`. Scope-exit cleanup uses TC39
explicit resource management (`using` and `await using`), inherited unchanged
from TypeScript.

Cleanup conditioned on the error variant MUST be written explicitly in the
failure path rather than registered by a dedicated statement form.

Disposal ordering relative to a compiler-generated failure exit, async
finalization, cancellation, and cleanup-error composition require further
normative specification.

The specification MUST additionally cover **abandonment**: a handler that
declines to resume a suspended computation MUST cause that computation's live
`using` and `await using` scopes to be disposed, in reverse acquisition order,
before the handler's own result is produced. A runtime MUST NOT allow an
abandoned computation to leave a resource undisposed. Whether a disposal error
raised during abandonment can be observed by the handler is **open**.

## Amendment Record — one-shot delimited continuations, 2026-08-27

The failure model on this page is unchanged. What changed is the *lowering* it is
written against: a failure exit is now a delimited-computation completion rather
than an emitted early `return`. Three sentences were withdrawn rather than
edited, and are recorded here so a reader who has quoted them can see what
replaced them.

**Withdrawn — the placement rule** (previously §Accepted Placements):

> "`!` is not accepted in every expression position. The lowering emits an early
> return, so a placement is sound only where that return preserves the authored
> evaluation order — the same constraint that governed the withdrawn
> expression-form grammar."

With it go the five-condition rule, the seven enclosing forms, the
repeated-loop-header condition, the statement-walk rationale, and the six worked
rejections (`r!.trim()`, `r![0]`, `maybe ?? r!`, `f(r!)`). Those forms are now
**accepted**, permanently. The 115-case placement measurement that supported the
rule is withdrawn with it and MUST NOT be cited. Two of the five conditions —
no enclosing Result channel and non-Result provenance — were typing conditions
rather than lowering conditions and survive verbatim under §Refusal Conditions,
as does the `catch` condition, whose *reason* is rewritten there.

**Withdrawn here, still enforced by the compiler.** The statement-walk rule is
what the shipped frontend implements: four of the six forms §Refusal Conditions
now accepts are refused today with `SMITHERS1204`, and five conformance cases
certify those refusals. That gap is recorded as **(SA-1)** at §Refusal Conditions
and in [Specification Status](/specification/index) §Specification–Implementation
Gaps. It is a gap, not a reason to restore the rule: the corpus cases stay green
and the specification stays as written until the frontend moves.

**Withdrawn — the count of refusals:**

> "Four distinct conditions refuse a `!` … placement, repeated loop header, no
> enclosing Result channel, presence of a `catch`, and non-Result provenance are
> separately diagnosed."

That sentence said four and listed five. It is replaced by three.

**Amended — the enclosing-member disqualification.** Generators were previously
disqualified alongside getters, constructors, and class static blocks. They still
are, but the rule is now stated as a constraint on an authored `function*`'s
effect row, because the compiler now emits generators of its own.

**Amended — the emitted error path.** "MUST return the enclosing error variant"
became "MUST complete the enclosing computation with its error variant". The
prohibition it carries — a Result error MUST NOT travel through the JavaScript
exception channel — is unchanged and was strengthened to hold at every point.
