# Type System [Result returns, requirements, absence, and boundary precision]

Status: the Result failure model and inferred requirements are **locked**. The emitted TypeScript representation of requirements remains **open**.

## Gradual Foundation

Smithers extends TypeScript's gradual type system. Existing TypeScript escape hatches remain available on the TypeScript target and MAY be restricted by lint policy rather than the language.

Recoverable errors and requirements add precision without requiring a separate globally strict mode or an Effect interpreter. This is a guarantee about authored functions and their observable behavior. The emitted form of a function with a non-empty effect row MAY be a generator, as defined by [Effects](/specification/effects).

## Function Type

A Smithers function has:

- an ordinary return type, which is `Result<A, E>` when the function can fail
- an inferred set `R` of nominal capability requirements

Functions MUST remain eager. A Result is an ordinary returned value used only by fallible functions; it is not a universal wrapper around all computation. This is a guarantee about authored functions and their observable behavior. The emitted form of a function with a non-empty effect row MAY be a generator, as defined by [Effects](/specification/effects).

## Fallibility Inference

For a function with a body and no return annotation, the compiler MUST infer:

- `A` from successful return paths
- `E` from reachable Error throws, Result propagation, returned Results, and foreign boundaries
- `R` from `Capability.context()` calls and transitive callees

A function with non-empty `E` MUST have inferred return type `Result<A, E>`. An async function with non-empty `E` MUST have inferred return type `Promise<Result<A, E>>`.

Plain success returns and Error throws MUST be compiler-lifted as defined by [Failure Semantics](/specification/failures).

If an explicit return annotation cannot represent a reachable recoverable Error, the compiler MUST reject the function rather than permit an untyped exception path.

## Public Boundaries

Public contracts MUST use ordinary generic type syntax:

```ts
declare function loadUser(id: string): Result<User, NotFound | Unavailable>

declare function fetchUser(
  id: string,
): Promise<Result<User, NotFound | Unavailable>>
```

Smithers MUST NOT add `throws E`, `!T`, or another failure-annotation grammar.

The `R` set MUST be inferred from compiler-recognized context access and preserved in exported declarations. Its emitted TypeScript representation remains open, and it MUST additionally carry whether the function is effectful, because a cross-module caller cannot lower its call site without that fact.

### Rows on Function Values

A function's **effect row** is the pair `(E, R)`. The row MUST be part of the function's static type, MUST be preserved in exported declarations, and MUST be carried by a function **value**, not only by a function declaration. Assigning a function with a non-empty row where a function with a smaller row is expected MUST be a type error.

An unannotated function type carries the empty row. A call whose callee the compiler cannot resolve, and whose callee type carries no row, MUST be rejected rather than lowered with an assumed calling convention.

## Result Composition

Result types MUST compose without nested `Result<Result<A, E1>, E2>` values when a compatible Result is returned or produced by `andThen`.

Transformations MUST union error types when they can introduce additional errors. Exhaustive recovery MAY remove handled members from `E`.

An ignored Result MUST be a compile error.

## Foreign Boundaries

Every unannotated foreign call MUST add the distinguished checked `panic` case, because JavaScript may throw, reject, or violate a declaration. Trusted `@throws {never}` metadata removes that default; `@throws {T}` or an adapter may supply a more precise channel.

There is no `TypeScript` requirement: TypeScript is the only target, so recording that a program depends on the JavaScript runtime would carry no information.

Type-only imports add neither runtime requirement.

## Async Values

An infallible async function returns `Promise<A>`. A fallible async function returns `Promise<Result<A, E>>`.

```ts
declare function loadUser(
  id: string,
): Promise<Result<User, Unavailable>>
```

Awaiting the call removes only the Promise layer. The resulting value remains `Result<User, Unavailable>` until it is matched, transformed, returned, or unwrapped.

Promise instance chaining is unavailable in authored `.sm`; `.then`, `.catch`, and `.finally` MUST be rejected.

## Absence

Smithers has no built-in `Optional<T>`. Absence MUST be modelled with TypeScript's existing `T | undefined` (or `T | null`) unions, narrowing, optional chaining, and nullish coalescing.

```ts
declare function findUser(id: string): User | undefined
```

TypeScript already expresses absence precisely and every JavaScript consumer already understands it, so a second representation would add a conversion boundary without adding safety.

Absence MUST remain distinct from failure. A function that can fail returns `Result<A, E>`; a function that can find nothing returns `T | undefined`; a function that can do both returns `Result<A | undefined, E>`.

The earlier `?T`, payload-capture, `orelse`, and `.?` grammar MUST NOT be part of the language.

An `Optional<T>` container MAY be reconsidered later as an ordinary standard-library type. It MUST NOT acquire compiler lifting, propagation, or nesting rules if it is.
## Reification

Ordinary types MAY be consumed as comptime values. Comptime code MAY derive validators, codecs, equality, hashing, schemas, and generated types.

There MUST NOT be a separate `runtime type` declaration modifier.

At durable boundaries, Result variants and all enclosed values MUST have compiler-known durable codecs or explicit user-supplied codecs.

The scope of that sentence widens under replay: every journaled effect-request answer is such a boundary, and codec representability is what decides whether a request is journaled at all. See [Effects](/specification/effects) §The Journaling Classifier.
