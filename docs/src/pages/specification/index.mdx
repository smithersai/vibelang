# Specification Status [How to read the Smithers design specification]

This specification records the target semantic model of Smithers. It is the
contract the language, toolchain, standard library, and runtime are designed to
satisfy. It does not describe repository progress or the behavior of a
particular implementation.

## Maturity Labels

Every design rule has one of three maturity levels:

| Label | Meaning |
| --- | --- |
| **Locked** | explicitly accepted by the language designer |
| **Direction** | accepted principle whose spelling or mechanics remain open |
| **Open** | discussed but not decided |

Unless a section says otherwise, statements in these specification pages summarize locked decisions. Syntax shown for a directional feature is informative.

## Normative Terms

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** describe intended conformance requirements. Because the grammar and compiler contract are incomplete, these terms apply only to behavior marked locked.

Examples are non-normative unless the surrounding text states otherwise.

## Conformance Targets

Smithers defines several distinct subjects of conformance:

- a **source implementation** parses and checks `.sm` programs
- the **TypeScript backend** preserves TypeScript-compatible source behavior and emits TypeScript/JavaScript artifacts
- a **durable runtime** executes compiler-emitted Flow bodies under a journaling handler, together with the Action protocols

## Source of Truth

The published specification pages are the readable target contract. The
[decision ledger](https://github.com/smithersai/smithers/blob/main/docs/DECISIONS.md)
records accepted design decisions, and the [durable execution
draft](https://github.com/smithersai/smithers/blob/main/docs/DURABLE_EXECUTION.md)
expands the distributed runtime model.

These documents are one specification set. A conflict between them is a
documentation defect and must be reconciled; implementation behavior does not
resolve it. Until reconciliation, the decision ledger is authoritative for the
specific decision it records.

## Specification Map

- [Compatibility](/specification/compatibility) defines the TypeScript interop boundary and target model.
- [Type System](/specification/type-system) defines function channels, absence, and boundary precision.
- [Failure Semantics](/specification/failures) defines failures, defects, propagation, and recovery.
- [Effects](/specification/effects) defines effect requests, one-shot delimited continuations, handlers, and effect rows — the shared substrate the failure, requirement, and durable pages are written against.
- [Requirements](/specification/requirements) defines `Context` capabilities, inferred requirement rows, and layer satisfaction.
- [Control Flow](/specification/control-flow) defines the statement model, cleanup, and the one accepted grammar addition.
- [Comptime](/specification/comptime) defines the imported compiler intrinsic, phase evaluation, and tracked compiler input.
- [Durable Execution](/specification/durable-execution) defines the imported durable intrinsic, Actions, the replay execution model, non-executing inspection, and runtime guarantees.

## Open Design Work

Rules marked **Direction** or **Open** identify design work that remains in the
target contract. They are not implementation status. A directional example
communicates the intended semantics but does not lock its exact syntax, names,
wire format, or operational mechanism.

TypeScript is the sole compilation target. Near-native, LLVM, and general Wasm
targets are outside the language contract. The checked `panic` channel on
foreign calls exists because JavaScript can throw; it is not a portability
classification.
