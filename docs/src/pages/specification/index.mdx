# Specification Status [How to read the Smithers design specification]

This specification records the target semantic model of Smithers. It is the
contract the language, toolchain, standard library, and runtime are designed to
satisfy. It does not describe repository progress or the behavior of a
particular implementation.

## Maturity Labels

Every design rule has one of three maturity levels:

| Label | Meaning |
| --- | --- |
| **Locked** | explicitly accepted by the language designer |
| **Direction** | accepted principle whose spelling or mechanics remain open |
| **Open** | discussed but not decided |

Unless a section says otherwise, statements in these specification pages summarize locked decisions. Syntax shown for a directional feature is informative.

## Normative Terms

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** describe intended conformance requirements. Because the grammar and compiler contract are incomplete, these terms apply only to behavior marked locked.

Examples are non-normative unless the surrounding text states otherwise.

## Conformance Targets

Smithers defines several distinct subjects of conformance:

- a **source implementation** parses and checks `.sm` programs
- the **TypeScript backend** preserves TypeScript-compatible source behavior and emits TypeScript/JavaScript artifacts
- a **durable runtime** executes compiler-emitted Flow bodies under a journaling handler, together with the Action protocols

## Source of Truth

The published specification pages are the readable target contract. The
[decision ledger](https://github.com/smithersai/smithers/blob/main/docs/DECISIONS.md)
records accepted design decisions, and the [durable execution
draft](https://github.com/smithersai/smithers/blob/main/docs/DURABLE_EXECUTION.md)
expands the distributed runtime model.

These documents are one specification set. A conflict between them is a
documentation defect and must be reconciled; implementation behavior does not
resolve it. Until reconciliation, the decision ledger is authoritative for the
specific decision it records.

## Specification–Implementation Gaps

A maturity label says how settled a rule is. It does not say whether the shipped
compiler implements it. Those are independent axes, and this page's opening
sentence — that the specification does not describe the behavior of a particular
implementation — is why they have to be.

Where a gap between this specification and the shipped compiler has actually been
**measured**, it is marked inline so a reader can find it, and marked with its
**direction**, because the two directions call for opposite responses. The
markers are greppable, in the same spirit as the decision ledger's `(PR-n)`
provisionality markers.

| Marker | Direction | Meaning |
| --- | --- | --- |
| **(SA-n)** | specification ahead | this specification promises behavior the shipped compiler refuses today. The marker names the diagnostic codes that refuse it and the conformance cases that certify the refusal. |
| **(IA-n)** | implementation ahead | the shipped compiler already does something this specification does not permit, or forbids. |

What a marker does and does not mean:

- A marker **records** a gap; it does not resolve one. Nothing carrying `(SA-n)` or `(IA-n)` is thereby weakened, and neither side may be quietly edited to match the other.
- An example carrying `(SA-n)` states the contract. It is **not** an example of what compiles today: copied into a `.sm` file it draws the diagnostics the marker names.
- A conformance case certifying the current refusal is evidence **for** the gap, not evidence against the rule. It MUST stay green and MUST NOT be weakened to fit this specification. It is retired when the implementation moves, and its retirement condition is named at the marker.
- A gap closes when one side is deliberately changed. Until then it is a recorded conflict rather than an unnoticed one.

### Current markers

| Marker | Where | Gap |
| --- | --- | --- |
| **(SA-1)** | [Failure Semantics](/specification/failures) §Refusal Conditions | placement of postfix `!` is unrestricted here. The shipped frontend still enforces the withdrawn statement-walk rule and refuses four of the six accepted forms with `SMITHERS1204`. |
| **(SA-2)** | [Durable Execution](/specification/durable-execution) §Compiler-Recognized API and §Flow | a Flow body is an ordinary function here. The shipped durable frontend is still the static-plan model: it refuses a runtime branch (`SMITHERS4106`) and a runtime loop (`SMITHERS4107`), types `Action.run` as `A \| undefined` rather than `Result<A, E>`, and does not lift a plain `return` to a Result inside a durable body. |
| **(SA-3)** | [Effects](/specification/effects) §Rows Are Types, §Propagation Is an Abort Request, §Layer Provision Installs a Handler | the resumable calling convention is **unwired**. `poc/src/runtime/effect.ts` implements the substrate — three request kinds, `Continuation`, `Handler`, `Resumable`, `handle`, `runHandled`, `capabilityHandler`, `__vsGet`/`__vsPerform`/`__vsPropagate` — but it is not re-exported from the runtime index and the compiler emits no call into it. A fallible function still lowers to an ordinary early `return __vsResultFailure(…)`. That substrate is **not** certified complete, and the page it marks no longer claims it is. Three defects were measured in it on 2026-08-28 and fixed: the declared failure row was keyed on `error.constructor`, a field the compiler-derived Error codec reconstructs from wire data, so the payload named its own failure identity; a handler could answer an `abort` with the ABI's `raise` arm and resume the aborted computation, swallowing a declared failure the page says MUST NOT be resumed; and a forwarding handler frame dropped `raise` inward, making recovery depend on handler nesting depth. All three were unwired and so never reachable. |
| **(SA-4)** | [Compatibility](/specification/compatibility) §Determinism-Sensitive Members | three of the five per-member walls remain unenforced. Rows one and two **closed on both backends on 2026-08-28**: `WeakRef`, `FinalizationRegistry`, `SharedArrayBuffer`, and `Atomics` were *listed* in the frontend's `UNIVERSAL_GLOBALS` and in the fork's byte-for-byte copy (`universalGlobals` in `compiler/forkbridge/hostrules.go.txt`), so the allowlist asserted the opposite of two `MUST NOT`s rather than merely failing to meet them; all four are now refused as `SMITHERS1605` — a new code, because `SMITHERS1601`'s message offers a Context capability and these rows say no capability can mediate them — and `20-host-globals/determinism-hostile-globals-are-refused` certifies it beside the positive control `20-host-globals/determinism-hostile-siblings-stay-available`, which keeps `WeakMap`, `WeakSet`, `ArrayBuffer`, `DataView` and the typed arrays available. Still open, and **not** the same shape of work: no `Scheduler` or `Locale` requirement exists — the ambient requirement type admits only `Clock`, `Random`, `Host`, so rows three and five have nothing to charge and adding one is a decision about the capability surface, not a list edit — and `Date` is analyzed at the root identifier only, so row four needs type-directed analysis of a value the walk never inspects. Measured against a `Date.now()` control that correctly reports `SMITHERS1602`. |
| **(SA-5)** | [Compatibility](/specification/compatibility) §Mandatory and §Forbidden | only `strict` is enforced. There is no tsconfig-validation gate at all, so the other five mandatory options are unchecked and none of the eleven forbidden options is rejected. |
| **(SA-6)** | [Requirements](/specification/requirements) §Amendment Record, [Capabilities](/reference/capabilities) §Withdrawn | the 2026-08-27 promise-settlement withdrawal is **not implemented**. `poc/src/runtime/layer.ts` still enforces all three withdrawn obligations using `v8.promiseHooks.createHook` and `AsyncLocalStorage`, and its refusal message quotes the withdrawn `async () => await promise` adapter as the required remedy. |
| **(SA-7)** | [Failure Semantics](/specification/failures) §Matching and Transformation | Ten of the twelve required Result members still do not exist anywhere: `andThenAsync`, `tryRecover`, `tryRecoverAsync`, `tapAsync`, `tapErrorAsync`, `tapBothAsync`, `Result.allAsync`, `Result.partition`, `Result.partitionAsync`, `Result.codec`, refused as `SMITHERS1301` (an unrecognized member fails the must-use walk rather than reporting an unknown property) on both backends. `flatten` and `tapBoth` closed on **both** backends on 2026-08-28: the reference's checker Result surface declares both, and the Go fork's independent copy of the discharge set (`resultConsumerMembers` in `compiler/forkbridge/lowering.go.txt`) and both of its prelude classes now do too, so `01-result-lifting/result-flatten-collapses-one-level-of-nesting` and `01-result-lifting/result-tap-both-observes-whichever-variant-is-active` pass everywhere and their `xfail(go)` markers are retired. The fork's copy cannot be folded into the reference's — it is Go source compiled into a foreign checkout — so `compiler/fork_result_member_surface_test.go` pins the two lists against each other instead. |
| **(SA-8)** | [Durable Execution](/specification/durable-execution) §Deployment Authentication | the signed envelope is `{artifactVersion, kind, plan, manifest, signer, signature, digest}` and still carries a `PlanTemplate`; `flowSourceDigest`, `journalSchemaVersion`, and `routingManifest` exist in no production source. The authentication half is implemented. Same pivot as `(SA-2)`. |
| **(IA-1)** | [Compatibility](/specification/compatibility) §Dynamic Features | `eval` remains permitted here. The shipped compiler already refuses dynamic code evaluation, and the conformance corpus deliberately certifies the refusal ahead of this page. Recorded there as contested and **open**; this marker labels the direction and decides nothing. |

`(SA-3)` through `(SA-8)` were measured on 2026-08-28 by a documentation-truth
sweep, each by running the construct rather than by reading source. They were
previously unmarked, which is why the register warns that a maturity label says
nothing about implementation status.

No document in this repository schedules the work that closes an `(SA-n)` gap.
The provisional decisions behind the 2026-08-27 revision are recorded in the
decision ledger under **Pending ratification**; there is no migration plan beside
them. That absence is recorded here rather than filled in with an invented one.

## Specification Map

- [Compatibility](/specification/compatibility) defines the TypeScript interop boundary and target model.
- [Type System](/specification/type-system) defines function channels, absence, and boundary precision.
- [Failure Semantics](/specification/failures) defines failures, defects, propagation, and recovery.
- [Effects](/specification/effects) defines effect requests, one-shot delimited continuations, handlers, and effect rows — the shared substrate the failure, requirement, and durable pages are written against.
- [Requirements](/specification/requirements) defines `Context` capabilities, inferred requirement rows, and layer satisfaction.
- [Control Flow](/specification/control-flow) defines the statement model, cleanup, and the one accepted grammar addition.
- [Comptime](/specification/comptime) defines the imported compiler intrinsic, phase evaluation, and tracked compiler input.
- [Durable Execution](/specification/durable-execution) defines the imported durable intrinsic, Actions, the replay execution model, non-executing inspection, and runtime guarantees.

## Open Design Work

Rules marked **Direction** or **Open** identify design work that remains in the
target contract. They are not implementation status. A directional example
communicates the intended semantics but does not lock its exact syntax, names,
wire format, or operational mechanism.

TypeScript is the sole compilation target. Near-native, LLVM, and general Wasm
targets are outside the language contract. The checked `panic` channel on
foreign calls exists because JavaScript can throw; it is not a portability
classification.
