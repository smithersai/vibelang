# Compatibility [Normative contract for TypeScript source and JavaScript hosts]

Status: **Locked**, except where marked.

## Source Relationship

1. `.sm` MUST use a TypeScript-derived grammar with only explicitly documented differences.
2. `.ts`, `.tsx`, and JavaScript modules MUST retain their own complete syntax and behavior when imported by Smithers.
3. Shared syntax MUST retain TypeScript behavior unless the Smithers specification explicitly assigns different semantics.
4. Smithers MUST NOT impose a globally sound type system that invalidates TypeScript escape hatches.

Smithers MUST NOT be described or tested as a syntactic superset of TypeScript. Smithers source uses the `.sm` extension. The JSX-capable extension is **open**; `.smx` is a candidate only.

## TypeScript Target

The TypeScript target MUST interoperate with the complete TypeScript language in `.ts` and `.tsx` modules. Smithers constructs SHOULD lower into ordinary TypeScript before the stock pipeline finishes checking and emission where feasible. Constructs whose lowering depends on a whole-program row MUST be lowered after inference completes.

Requirement metadata SHOULD erase where it does not require runtime machinery. Result values have an intentional runtime representation; infallible functions MUST NOT be wrapped. That last obligation is now the rule that a function whose effect row is empty MUST NOT be emitted in the resumable calling convention defined by [Effects](/specification/effects).

Requirement metadata does not erase completely. Whatever representation is chosen MUST additionally carry whether a function is effectful, because a cross-module caller cannot lower its call site without that fact.

## Foreign Boundary

Calling an unannotated foreign runtime value MUST add the checked `panic` case, because JavaScript and TypeScript may throw, reject, or violate a declaration. Trusted `@throws {never}` metadata opts out; `@throws {T}` declares a more precise channel. The caller must propagate, explicitly catch, or safely adapt that channel.

This is a property of JavaScript, not of a second compilation target, and it is retained independently of everything else on this page.

Smithers has no `TypeScript` requirement. TypeScript is the only target, so every program depends on the JavaScript runtime and a requirement recording that fact would carry no information.

## Dynamic Features

`.sm` inherits TypeScript's runtime semantics. There is no portable / `TypeScript`-required / forbidden classification, because there is no second target to be portable to.

`any` and `eval` remain usable. General Smithers guidance may lint against them; the language does not forbid them.

**Open — contested, and shipped behavior already diverges from the sentence above (IA-1).** That sentence is Locked and has not been withdrawn. The `(IA-1)` marker records the *direction* of the divergence — the implementation is ahead of this page, the opposite of the `(SA-n)` gaps elsewhere in this specification — and decides nothing; see [Specification Status](/specification/index) §Specification–Implementation Gaps. It is nevertheless not what the compiler does: dynamic code evaluation is refused today, and the conformance corpus deliberately certifies the refusal ahead of this page. Until the conflict is ratified one way or the other, it is a recorded conflict rather than an unnoticed one, and neither side may be quietly changed to match. The proposal on the table is:

> Dynamic code evaluation is unavailable in `.sm`. `eval`, the `Function`
> constructor, and any selection of `constructor` on a callable receiver MUST be
> refused: a runtime string lies outside every static analysis, so the compiler
> can neither describe what it requires nor prove that it replays. This holds
> even for an expression that reads nothing from the host, because purity of a
> runtime string is not decidable. `any` remains usable, but a receiver typed
> `any` in a position where the analysis must decide callability MUST be treated
> as callable — matching the fail-closed default already applied to a dynamically
> selected member.

Both directions cost something. Adopting the proposal converts a locked permission into a prohibition. Declining it leaves a hole that matters more under replay than it did before: an `eval`'d string produces no journal entry, so it produces no divergence to detect. The full evidence is recorded in the decision ledger.

## Host Globals

Platform-specific globals such as `process`, `window`, `document`, filesystem, and network MUST NOT be unconditional globals in authored `.sm` code. Host functionality MUST be represented by typed capabilities, normally accessed through the inherited `Capability.context()` method from `smthrs/context`.

Facilities truly present in every supported JavaScript environment MAY be unconditional globals. Host-sensitive operations such as clock and random access MUST still use capabilities.

Because a Flow body re-executes on every resumption, an operation whose result can differ between two executions of the same code on the same inputs MUST be reachable only through a capability whose answer the runtime journals.

That sentence is unchanged and stays Locked. What was *settled* on 2026-08-28 is the verb it is read with, because two Locked pages had read it two ways — see §Determinism-Sensitive Members and the Amendment Record. "Reachable only through a capability" is discharged by a **requirement row**, not by refusing the name.

### Determinism-Sensitive Members

"Present in every JavaScript environment" is not sufficient on its own. The following are per-member obligations on the rule above, because each names an operation whose result is a function of host state that no journal entry can describe:

| Operation | Obligation |
| --- | --- |
| `WeakRef`, `FinalizationRegistry` | MUST NOT be unconditional globals. `deref()` returning `undefined` is a pure function of garbage-collection timing: no capability can mediate it and no journal entry can describe it. |
| `SharedArrayBuffer`, `Atomics` | MUST NOT be unconditional globals. Cross-agent shared-memory reads and `Atomics.wait` observe another agent's schedule. That ECMA-262 publishes them is true and irrelevant to replay. |
| `Promise.race`, `Promise.any` | MUST charge a `Scheduler` requirement, because their value *is* arrival order. Every other `Promise` member stays free. |
| `Date.prototype.getHours`, `getDay`, `getTimezoneOffset`, `toLocaleString`, `toLocaleDateString`, `toLocaleTimeString`, `toString` | MUST charge `Clock` even when an explicit instant is supplied, because they read the host time zone. `getTime()` stays free. This is the hazard `Intl.DateTimeFormat` construction is already refused for, as `SMITHERS1602`. |
| Every ICU-backed operation: `Intl` other than `DateTimeFormat` — `NumberFormat`, `Collator`, `PluralRules`, `ListFormat`, `RelativeTimeFormat`, `Segmenter`, `DisplayNames`, `Locale`, `supportedValuesOf`, `getCanonicalLocales` — together with `String.prototype.localeCompare`, `toLocaleUpperCase`, `toLocaleLowerCase`, and `normalize`, and `toLocaleString` on `Number`, `BigInt`, `Array`, `Object`, and each of the twelve typed arrays | MUST charge a `Locale` requirement. They are functions of the host ICU version and locale data, and `Collator.compare` used as a sort comparator makes the resulting **ordering** host-dependent. The obligation is the criterion, not the list: any later member whose result is a function of the host's locale or Unicode data joins the row without amending it. `normalize` is in the row by that criterion and is the one member whose variance is the host's **Unicode** version rather than its locale. |

**"Charge", in this table, means the site publishes the named capability's
requirement into the enclosing function's row**, which a caller discharges by
providing a layer. Where the capability has a source-language surface the author
can write instead — `Clock.context()`, `Random.context()` — the *ambient*
spelling is additionally refused, so the row is charged by the capability call
rather than by the ambient one; that refusal is `SMITHERS1602`/`SMITHERS1603`,
and it is why `Date.now()` reports a diagnostic rather than merely publishing a
requirement. Where the capability deliberately has **no** source-language
surface, a refusal would name a remedy that cannot be written, and the
obligation is the row charge alone. Rows one and two are neither: they say in as
many words that no capability could mediate them, so they are refused with no
remedy offered (`SMITHERS1605`).

## Host Modules

**Direction:** direct host-module usage contributes an exact module requirement such as:

```ts
Module<"node:fs">
```

This is preferred over a coarse platform flag because a provider or host may satisfy one host contract without satisfying another. It is a capability concern, not a portability one: `.sm` may be emitted for Node, Bun, Deno, a browser, or an edge runtime, and those hosts differ.

## Configuration

`.sm` is new source, so there is no legacy `.sm` to grandfather. Soundness
settings MUST therefore be mandatory and MUST NOT vary by JavaScript host: a
file's legality cannot change merely because its emitted code runs on Node,
Bun, Deno, a browser, or an edge runtime.

Imported `.ts` and `.tsx` keep their own configuration. The escape-hatch guarantee in this page protects those files, not `.sm`.

### Mandatory

| Option | Reason |
| --- | --- |
| `strict` | brings `strictNullChecks`, `noImplicitAny`, `useUnknownInCatchVariables`, and the rest |
| `noUncheckedIndexedAccess` | `arr[2]` MUST be `T \| undefined`; an index is a lookup that can find nothing |
| `exactOptionalPropertyTypes` | load-bearing now that absence is `T \| undefined`; without it `{ a?: number }` silently accepts `{ a: undefined }` |
| `isolatedModules` | required for correctness under a per-file bundler transform |
| `verbatimModuleSyntax` | replaces the deprecated `importsNotUsedAsValues` and `preserveValueImports` |
| `useDefineForClassFields` | the legacy-off behavior is a footgun |

program does not own. The library was narrowed and the emitted check now reports
only on the module set it was handed. Six corpus programs were left, all
genuine: they indexed without narrowing, and they were narrowed.

*Three of the six mandatory options are not type rules,* and forcing them onto
this compiler's own emit broke a language guarantee rather than enforcing one.
`verbatimModuleSyntax` and `isolatedModules` decide import elision and
`useDefineForClassFields` decides class-field semantics; with
`verbatimModuleSyntax` on the Go fork's emit Program, `import { type T } from
"./sneaky.ts"` stopped being erased and the named module's initializer RAN,
which is the exact fail-open the module-initialization trust rule exists to
prevent. The same Program carries a project's imported `.ts` and `.cts`, and a
`.cts` module written with `export function` became `TS1287` — this compiler
charging a foreign file for a rule the paragraph above exempts it from. The
mandatory set is therefore applied where §Mandatory speaks, to the checking of
authored `.sm`; the two type-level members travel to the emitted module set as
well, and the three emit-shaping ones do not.

*One spelling became inexpressible, and that is the option working.* A numeric
index into a durable Flow's input ARRAY can no longer reach an Action input:
the read is `T | undefined` and fails the checked input contract, widening the
contract to `T | undefined` fails canonical JSON, and narrowing with `??` is a
computation rather than a projection the Plan can record. The spelling that
survives is a TUPLE, whose read at a constant index the option does not widen.

`noUncheckedIndexedAccess` is noisy in index loops, because TypeScript cannot prove `for (let i = 0; i < arr.length; i++)` is in bounds. An index read is `T | undefined` and MUST be narrowed, or read through an extraction helper.

`arr[i]!` does not silently change meaning, and it compiles when `arr` holds
Results. The `| undefined` an index read adds under `noUncheckedIndexedAccess` is
not the author's — the option widens the *access*, never the container's element
type — so it is seen through, and `arr[i]!` means there what `!` means
everywhere else. A `T | undefined` the author wrote is a different thing and is
still not a `Result` operand: an array declared `(Result<A, E> | undefined)[]`, a
heterogeneous tuple's non-Result slot, or a plain `string | undefined` binding
each make `!` a type error rather than an ambiguity. The two are told apart by
the container's element type, and the line between them is the one this
specification draws everywhere else — `!` is the error axis, `?.` and `??` are
the absence axis.

### Forbidden

Options that upstream has deprecated or removed, and options that select superseded behavior, MUST be rejected rather than ignored: `keyofStringsOnly`, `suppressImplicitAnyIndexErrors`, `suppressExcessPropertyErrors`, `noStrictGenericChecks`, `noImplicitUseStrict`, `out`, `charset`, `importsNotUsedAsValues`, `preserveValueImports`, `experimentalDecorators`, and `emitDecoratorMetadata`.

TypeScript 5.8's `erasableSyntaxOnly` names the TS-only syntax that runtime type-stripping refuses. Smithers treats that set as guidance about which forms are dying.

### Emit-Scoped

Emit, module, and library options select output rather than core language
legality, and MAY differ by JavaScript host and artifact: `target`, `lib`,
`module`, `moduleResolution`, `jsx`, `downlevelIteration`, `importHelpers`,
`esModuleInterop`, `allowSyntheticDefaultImports`. Host-specific libraries and
module formats still constrain whether the complete project can run on the
selected host.

`skipLibCheck` remains configurable; forcing it off is correct in principle and impractical against real `@types` packages.

## Build Tool Integration

Smithers MUST be usable inside an existing JavaScript build without adopting a Smithers-specific build system. A project already using Vite, Rollup, webpack, esbuild, Rspack, Rolldown, Farm, or the Bun bundler MUST be able to add `.sm` support by installing one plugin.

### Plugin Contract

The integration MUST be published as an [unplugin](https://unplugin.unjs.io) factory, so a single implementation produces a plugin for every supported bundler rather than one hand-maintained adapter per tool.

The plugin MUST:

- resolve `.sm` specifiers, including extensionless imports that a bundler would otherwise resolve only to `.ts` or `.js`
- accept a file whose contents are `.sm` source and return TypeScript or JavaScript
- run **before** any other transform in the host tool's pipeline, so every downstream plugin sees ordinary TypeScript and never sees Smithers source
- emit a source map for every transformed file, so diagnostics, stack traces, and debugger stepping refer to the authored `.sm` file
- leave `.ts`, `.tsx`, `.js`, and `.jsx` files untouched

The plugin MUST NOT define language semantics. It is a delivery mechanism for the same lowering the compiler performs; a construct MUST NOT behave differently because it was compiled by a bundler rather than by the CLI.

The five obligations above are unchanged, but the fourth carries more weight than it did. Authored code and emitted code now diverge structurally wherever a function has a non-empty effect row, not only at `!` sites, so a missing or approximate source map degrades every diagnostic, stack trace, and debugger step in an effectful program.

### Checking and Transform Modes

Smithers inference is whole-program: error rows, requirement rows, and must-use analysis cross module boundaries. A per-file bundler transform cannot see that graph.

The plugin MUST therefore support two modes:

1. **Checked** — the plugin drives a Smithers program for the project and reports diagnostics. This is the default.
2. **Transform-only** — the plugin lowers without whole-program checking, for fast rebuilds, with checking delegated to the CLI or an editor. A transform-only build MUST fail closed on any construct whose lowering depends on information the file alone does not carry, rather than emitting a guess.

Transform-only MUST NOT be presented as a conforming implementation of the language.

Whether a called function is emitted in the resumable calling convention is whole-program information. A transform-only build therefore fails closed at nearly every call site that reaches a function with a non-empty effect row. Transform-only mode is a fast-rebuild convenience for files with empty rows and MUST NOT be presented as a general build mode.

:::note[Blast radius, measured 2026-08-30]
The sentence above is a conditional and it is exact: a cross-file call to a callee with a non-empty effect row cannot be lowered from one file, and the build MUST refuse it. It is not a claim that most call sites refuse. Measured over the conformance corpus (242 cleanly-compiling programs, 1205 call sites), 93.2% of call sites are decidable in-file and 6.8% are not; restricted to the multi-module programs, 21.5% of call sites are undecidable in-file and 4.6% reach a non-empty-row callee across a file boundary. Over the reference implementation's own source tree, 10.7% of call sites are cross-file. About one call site in five in a multi-module program, not four in five — and still enough that the mode cannot be offered as a general one, because the refused fifth is not a subset an author can predict or confine. Recorded in `docs/DECISIONS.md` §Build integration.
:::

### Incrementality

The plugin MUST expose accurate invalidation to the host tool's watch mode. A `.sm` file's transform result depends on its own contents, the contents of the modules it imports whose rows it consumes, comptime inputs, and the target — and every one of those MUST invalidate it. This is more sensitive than it was: a callee's row changing from empty to non-empty changes every caller's emitted shape, not only its diagnostics.

### Declaration Emit

A library published from `.sm` sources MUST be consumable by ordinary TypeScript projects. The plugin or the CLI MUST be able to emit `.d.ts` declarations that preserve Result contracts, requirement rows, and each exported function's emitted calling convention. A cross-package caller that cannot read a callee's calling convention MUST fail closed rather than assume the ordinary one.

## Type Assertions

The TypeScript non-null assertion MUST NOT exist in `.sm`. Postfix `!` is the Result propagation operator ([Failure Semantics](/specification/failures)), and the definite-assignment form `x!: T` MUST also be rejected. Removing the assertion meaning entirely is what makes the operator unambiguous.

`as` assertion semantics are **open**. The current candidate is:

- provably safe assertions erase
- reifiable assertions may check and defect on failure
