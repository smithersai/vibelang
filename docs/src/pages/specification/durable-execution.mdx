# Durable Execution [Static Plans, typed Actions, and durable runtime behavior]

{/* brand-gate: allow-start */}
The locked September 6 owner decision adopts the Smithers 1.0 Plan model. This
page describes that current target contract, not ordinary-body replay. The
[withdrawn replay specification](/specification/history/durable-replay) preserves
the previous text and its implementation history.

The comparison reference is
[Smithers revision 6bcbaa2](https://github.com/smithersai/smithers/tree/6bcbaa2d03a10afe8fe59934dabe262f55f012e7).
Its graph, key, approval and journal contracts apply; VibeLang is stricter about
construction: the compiler derives Plans from checked syntax and never invokes
a source Flow, even with symbolic JavaScript proxies.
{/* brand-gate: allow-end */}

## Scope

Durability MUST be opt-in. Ordinary functions and Action implementations remain
eager functions; selecting a Flow boundary does not turn unrelated code into
scheduler work. General Result, capability and effect rules still apply outside
the symbolic Flow description.

A Flow describes typed connections between operations. It is not an ordinary
function re-executed under a different handler. Only behavior represented by the
checked Plan may execute. Unsupported source constructs MUST be rejected, not
silently omitted, interpreted as ordinary body replay, or reduced to a sets-only
Manifest.

## Compiler-Recognized API

`durable` and `Action` come from the compiler-owned `vibelang:flows` virtual
module. `durable(...)` uses ordinary TypeScript call syntax, not a keyword or a
new parser production. Recognition MUST follow the resolved imported binding:
aliases preserve meaning; an unrelated function called `durable` is ordinary.

The compiler MUST statically resolve the selected Flow declaration and its
source-module closure. An opaque runtime-selected function MUST be rejected.
The checked source, contracts and compiler-known inputs MUST determine the
published Plan; authored code MUST NOT run to discover its nodes.

```ts
import { Action, durable } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const Build = durable((input: number) => {
  const first = Double.run(input + 1)!
  const second = Double.run(input)!
  return { first: first * 2, second }
})
```

This describes two independent Action calls and a result that consumes both.
It does not call the Double implementation while compiling or inspecting.

## Action

An Action declares a closed typed operation with an open implementation. The
compiler MUST derive its input, success, failure and capability-requirement
contracts. Authors MUST NOT repeat those types as separate schema arguments.
An abstract fallible signature MUST state its Result return type because no
implementation body exists there from which to infer failures.

Implementations MUST be ordinary VibeLang functions or callbacks. A fallible
implementation returns `Result<A, E>` or `Promise<Result<A, E>>`; ordinary
compiler lifting permits plain success returns and Error throws. It MUST NOT
require an Effect wrapper or a second failure annotation.

Implementation requirements belong to its inferred capability row, not extra
source-level parameters. Provider/deployment configuration MUST satisfy that row
and bind the selected implementation, recovery tier, declared effects and
placement. An abstract Action signature alone MUST NOT imply a provider,
hermeticity, a recovery tier or permission to run.

## Durable Boundary

Inputs, persisted outcomes and data crossing an Action/Flow machine boundary
MUST have a checked durable representation. Plain supported data SHOULD derive
its codecs from types. Functions, capability instances, process handles and
other ephemeral values MUST NOT be smuggled through an arbitrary-JSON fallback.

An explicit codec is required where derivation is impossible, including erased
`any`/`unknown` boundaries. If an implementation cannot validate such a codec
or its identity, it MUST refuse that boundary. A codec declaration is not
permission to trust unchecked data.

Validation MUST occur before using transported or persisted data. Native Error
values need a nominal contract; typed failures, defects and cancellation MUST
remain distinct. A failure MUST NOT become a successful cached value.

Canonical metadata ordering MUST NOT change observable program-value ordering.
When object field order is part of a value's behavior, its wire representation
MUST preserve that order explicitly. Stored evidence and materialized program
values MUST NOT share mutable state merely because serialization succeeded.

Codec representability alone does not define the new Plan's work or identity.
The earlier rule that classified every resumable-body request solely by whether
its answer had a codec belongs to the withdrawn replay model.

## Flow

The compiler MUST lower the selected checked function into Plan data. An
`Action.run` expression creates an Action node and a typed planned Result.
Applying `!` records the Result success/failure boundary; it MUST NOT silently
erase a possible failure. Projecting a planned success and passing it to another
node MUST preserve the typed projection and dependency.

A planned value is not available to ordinary source execution while planning.
The compiler MAY represent checked pure calculations as data expressions, but
MUST reject any operation for which it has no sound representation. It MUST NOT
run a callback, coercion hook or module initializer to obtain an answer.

The executable source function MUST NOT be required to drive or resume the
resulting graph. Source bytes MAY remain as authenticated metadata for identity,
debugging and native re-derivation; this is not a live function side table or an
executable Flow body. Action implementation code is separate and must remain
available in its authenticated worker artifact.

## Flow Determinism and Captures

A Flow description MUST NOT perform I/O or inspect clock, randomness, locale,
environment, process state, services or mutable host state to decide its graph.
Such operations belong behind declared runtime boundaries. General host-member
restrictions in [Compatibility](/specification/compatibility) remain in force.

Ordinary `let`, mutation, loops and recursive body execution are withdrawn
inside the symbolic Flow description. A bounded graph pattern is not permission
to execute an ordinary loop during planning.

Compiler-known immutable inputs MAY be captured only when their provenance,
value and transitive dependencies are represented in the checked identity.
The compiler MUST NOT retain an object's initializer while dropping later
mutations that determine its value. A runtime/mutable capture, unresolved module
initializer or missing dependency MUST be rejected when it cannot be represented.

Local `const` bindings may name planned values; they do not make those future
answers available to host JavaScript. The source compiler MUST preserve
connections, ordering constraints, projection paths and failure contracts through
aliases, child Flows and graph combinators.

Values from separately specified comptime or loader phases are compiler inputs,
not permission to evaluate the Flow callback or a runtime module initializer.

## Plan and Inspection

A Plan MUST publish the complete bounded graph for the current round: structural
node addresses, declared material, dependency/control relationships, node keys,
declared effects, and the digest of its approval projection. A sets-only
Effect Manifest is not a substitute.

Inspection MUST NOT load or invoke the source Flow, an Action implementation or
a callback to discover work. Invalid, incomplete, cyclic or ambiguously addressed
graphs MUST refuse before execution; executing only a valid-looking subset is
not conformance.

A conditional pattern MUST represent the alternatives before execution, and its
driver MUST settle only the selected arm. Merely publishing both arms does not
make them both runnable. Dynamic work MUST use explicit bounded rounds or
handoffs; an unknown collection cannot be silently expanded by running authored
code or by inventing a bound.

The shipped command spelling and limits are documented in
[CLI — Plan](/reference/cli#plan). An inspection provider file contains claims,
not proof of provider bytes or approval.

### Key and Approval Identities

These identities MUST remain distinct:

| Identity | Meaning |
| --- | --- |
| Structural node address | Where work is addressed in one graph; not itself a shared-cache key. |
| Plan node key | A `key1_` commitment to declared material and material-dependency keys. |
| Plan `baseDigest` / `digest` | The generation-zero graph commitment / current graph approval projection. |
| Dispatch/content/environment identity | The concrete input and measured environment needed for a dispatch or eligible reuse. |
| Journal frame | `{ lineageId, seq }`, a position in committed history, not a source occurrence counter. |

Key derivation MUST use the accepted canonical JSON representation, real SHA-256
and the versioned key format. Stored keys MUST be validated as opaque keys, not
hashed again. Duplicate JSON fields, malformed Unicode and unrepresentable
material MUST NOT disappear through a host JSON parser before validation.
A key cannot account for behavior or inputs absent from its declared material.

The graph digest is NOT the complete invocation approval. The Control target
binds the Flow identity, exact input, authority envelope, deployment class,
execution digest when present, and persisted Plan digest. Its digest is plain
lowercase SHA-256 of that canonical projection, not the `key1_` graph digest.
An absent optional execution digest is omitted, not replaced with null.

Approval MUST be checked against the exact principal, target and scope in the
durable admission transaction. A source signature, valid graph, matching digest
or authenticated caller alone MUST NOT be treated as approval.

## Compilation Phases and Deployment Authentication

A conforming toolchain MUST distinguish:

1. Checked source/contract compilation, without running authored Flow code.
2. Provider and worker build, binding executable bytes, codecs, requirements,
   runtime/boundary identity, policy and placement.
3. Non-executing Plan inspection for the exact input and selected declarations.
4. Authenticated invocation restoration and explicit Control admission.
5. Execution or resume through the admitted graph and durable stores.

Compilation and inspection MUST NOT dispatch Actions. All providers needed by
the complete declared graph, including alternatives, MUST be resolved before
their execution can be admitted. Public worker artifacts MUST retain the code
and runtime assets they need independently of a compiler checkout.

Authentication MUST cover the actual source/Plan contract, worker code, codecs,
runtime and policy identities that execution will consume. Structural copies of
an authentication proof MUST NOT acquire its authority. Trust roots must come
from outside the artifact; an envelope MUST NOT appoint its own trusted signer.

Authentication proves the integrity of its signed claims. It does not by itself
prove approval, sandbox enforcement, freshness, revocation, rollback protection
or what a remote process actually loaded. Workers MUST receive only declared
authority; message validation, transport binding and fencing MUST prevent a
weaker worker or sandbox from being silently substituted.

## Ordering and Concurrency

Dependencies and explicit sequencing determine order; source position alone
MUST NOT serialize independent Action calls. The runtime MUST make independent
ready work available for concurrent execution subject to resource limits,
declared conflicts and admission policy.

All inputs and ordering constraints MUST be established before dispatch.
Priorities may order ready work but MUST NOT change a node's material key merely
because priority changed; the Plan approval projection still covers priority.

A failure MUST block work that requires its successful outcome. Cancellation,
failure, retry and branch selection MUST retain their distinct meanings.
A scheduler that only knows dependency readiness MUST NOT eagerly run both
arms of a branch. Unsupported branch or round drivers MUST fail closed.

## Resume, Replay, and Journal Identity

A committed Action outcome and the lifecycle evidence that explains it MUST be
stored atomically. Durable notifications follow commit; a missed notification
MUST NOT lose the recorded state.

Resume continues an existing execution. It MUST reuse its committed outcomes
instead of repeating completed work, and may execute eligible unfinished work.
VibeLang resume MUST NOT require replaying the original Flow function from entry.

Time-travel replay is different: it folds a committed journal prefix, performs
no dispatch and writes no state. Calling ordinary body execution “replay” does
not satisfy this contract.

Journal coordinates MUST carry lineage and sequence. Attempt, content and
execution-environment identities have separate purposes. Neither a source
line/column pair nor `(siteId, occurrence)` replaces the current journal protocol.

Execution ownership, lease renewal, fencing and durable terminal transitions
MUST prevent stale or competing coordinators from committing conflicting work.
Typed failures, defects and cancellation must survive restart without being
reclassified by the attaching process.

## Versioning and Bounded Rounds

Launch and resume MUST validate the pinned graph, source/provider/runtime
identities and approval. Changed work MUST fail closed; it cannot silently attach
to an in-flight execution under the old identity.

An elaboration appends bounded work. Existing nodes and edges MUST NOT be edited
in place; `baseDigest` remains the generation-zero commitment and the current
`digest` advances. The resulting graph and exact invocation MUST be verified
and authorized before newly introduced work is dispatched. Approval of an older
graph MUST NOT authorize a different one.

Resource limits MUST bound graph construction, rounds, fan-out and history
operations. Exhausting a bound MUST produce a refusal, not a partial graph or
silent history truncation. Ordinary unbounded Flow loops are not an alternative.

## Recovery and Reuse

The recovery tiers are `sealed`, `compensable` and `irreversible`. Only eligible
sealed work may reuse results across runs by content key; concrete inputs,
dependencies, implementation/codec behavior and execution environment must match.
A Plan key or a copied attempt row is not sufficient evidence of cache eligibility.

Recovery policy and cross-run reuse MUST remain separate. A “sealed” declaration
does not make arbitrary side effects deterministic, safe to repeat, or exactly
once. An ambiguously committed irreversible Action MUST NOT be retried
automatically. External exactly-once-like outcomes require destination-enforced
idempotency, transactions or fencing.

A recorded failure must remain a recorded failure. Memoizing one acceptable
answer MUST NOT silently promote nondeterministic work into a hermetic shared
cache result.

## History Operations

Replay/inspect MUST read a bounded committed prefix without execution.
Fork MUST preserve the parent, create a child lineage/workspace and copy only
the prefix justified by the selected frame. Copied parent attempts MUST NOT be
treated as proof that run-dependent keys apply in the child; compensable and
irreversible work may execute again under a new run identity.

Rewind MUST validate the frame, own the run, assess affected boundaries, perform
authorized matching compensation, restore the workspace and atomically archive
and truncate the suffix with an audit trail. It MUST NOT rewrite a committed
entry in place or hide an irreversible boundary. Descendant dependencies and
live ownership must be checked before destructive history operations.

Startup recovery MUST finish or roll back interrupted history transitions
before admitting conflicting work, without stealing a live owner's run.
Exact host/API spelling remains a delivery concern, not permission to omit
these semantics.

## Implementation Checkpoint — (SA-2), (SA-8)

As implemented on September 8, native API 52 derives, verifies and appends keyed
Plan data. Checked source modules, child composition, static fan-out, captured
enclosing planned values, closed pure computations, scoped `if` statements,
early returns, native-checked input and nullable Action-success narrowing,
conditional expressions and short-circuit Action work through `&&`, `||` and `??`
reach an authenticated Node/Bun worker. Both branch arms are published; the
worker's local demand adapter executes only the selected arm. Independent work,
shared dependencies and explicit sequencing retain their meanings. An eager
worker sweep refuses branch graphs, and cross-arm effect-conflict edges refuse
until their conditional effect adapter exists.
Logical selections preserve the selected operand and evaluate left-side Action
work once; skipped alternatives do not dispatch. An unconsumed `Result` cannot
lose its must-use obligation by joining a scalar alternative. Nullish selection
uses the current value contract's `null`; it does not widen that contract to
admit `undefined`.
Statement branches retain TypeScript truthiness and lexical scope. Early
returns omit continuation work on the returned path; fallthrough-only branches
leave unrelated continuation Actions independently ready. Consumed Action
statements remain work even when their success is discarded. Guarded input
fields are projected only during selected execution. Unsupported statement
forms and incomplete or over-budget graph construction still refuse.
Narrowing facts come from the fully checked propagation-success program, not
TypeScript's non-null assertion approximation. A `null` success remains a value,
including inside a guarded return. Record-to-null comparisons require no object
identity; general record equality remains outside the closed value operations.
`vibe plan` uses this path by default; `manifest-compat` is
explicit. Installed consumers verify CLI issuance, signed restoration and actual
worker execution. An isolated composition also demonstrates approved independent
work and real process-kill/resume with the reviewed runtime.

This does NOT establish a shipped production scheduler/Control/journal host,
durable branch hosting, bounded-round execution, time-travel administration or
complete default migration.
The ordinary `compile`/`run` body path is still historical. The old body's
crash demo and its conformance expectations are compatibility evidence, not
proof of the new contract.

Module-level runtime captures, ordinary loops and unsupported graph operations
refuse in the current keyed source profile. Explicit codec/provider binding
spellings and capability adapters are not all delivered. The runtime packaging
choice is pending. General cleanup-completion precedence remains open; the Plan
pivot does not decide it.

## Amendment Record

The September 6 owner decision reverses PR-1's sets-only Manifest and PR-2's
source-site occurrence identity. It retains fail-closed versioning, restores
independent-node parallelism and requires bounded rounds, the named recovery
tiers and lineage-based history operations.

The archived replay text is retained for its design and test history. Its
“ordinary control flow executes unchanged,” “program order is order,” body
retention and lost-parallelism claims are withdrawn, not current open questions.
Other specification pages and older durable drafts must be reconciled against
this contract where they still describe that model.
