# Overview

Smithers starts with TypeScript-shaped source, then makes a small set of intentional changes needed to build reliable programs in the AI era.

### It's (almost) TypeScript

Smithers is not a syntactic superset of TypeScript. Shared syntax keeps TypeScript behavior unless a divergence is explicitly documented, while imported `.ts`, `.tsx`, and JavaScript modules retain their own complete syntax and runtime semantics. On the TypeScript target, `.sm` constructs lower to ordinary TypeScript/JavaScript where feasible.

Foreign runtime calls are checked boundaries: an unannotated JavaScript or TypeScript call adds the distinguished `panic` case. Trusted `@throws {never}` metadata opts out and `@throws {T}` declares a more precise channel.

:::code-group{syncKey=""}

```ts [Smithers]
import { clamp } from "lodash-es"

export function normalizeConfidence(score: number) {
  return Result.try(() => clamp(score, 0, 1))
}
```

```ts [TypeScript]
import { clamp } from "lodash-es"

export function normalizeConfidence(score: number): number {
  return clamp(score, 0, 1)
}
```

```ts [Effect]
import { clamp } from "lodash-es"

export function normalizeConfidence(score: number): number {
  return clamp(score, 0, 1)
}
```

:::

LLMs have no issue learning and using Smithers because it's so close to TypeScript.

### Typesafe Errors as Values

One of Smithers's only changes to TypeScript is that errors are treated as strongly typed values that must be handled.

:::code-group{syncKey=""}

```ts [Smithers]
class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

function getUser(
  users: Map<string, User>,
  id: string,
): Result<User, NotFound> {
  const user = users.get(id)
  if (user === undefined) throw new NotFound(id)
  return user
}

const user = getUser(users, id).match({
  ok: user => user,
  error: error => error.match({
    NotFound: () => User.guest(),
  }),
})
```

```ts [TypeScript]
class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

function getUser(users: Map<string, User>, id: string) {
  const user = users.get(id)
  if (user === undefined) throw new NotFound(id)
  return user
}

let user: User
try {
  user = getUser(users, id)
} catch (error) {
  if (error instanceof NotFound) user = User.guest()
  else throw error
}
// NotFound is still invisible in getUser's type.
```

```ts [Effect]
import { Effect } from "effect"

class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

function getUser(users: Map<string, User>, id: string) {
  const user = users.get(id)
  return user === undefined
    ? Effect.fail(new NotFound(id))
    : Effect.succeed(user)
}

const user = getUser(users, id).pipe(
  Effect.catchAll(() => Effect.succeed(User.guest())),
)
```

:::

The compiler sees `Result<User, NotFound>` and lowers the plain return and Error throw into its two variants. The caller must propagate or handle that Result. `error.match` is exhaustive over the known Error union.

Result is an ordinary must-use value. There is no generator ceremony or universal effect interpreter in authored code: you write and call ordinary eager functions, with no `Effect` value, no do-notation, and no `.run()` step. The compiler may emit a function whose effect row is non-empty in a resumable calling convention, but that convention is unspellable in `.sm` and never appears in a type, a declaration, or a diagnostic.

### Dependencies in the function signature

Smithers uses an Effect-inspired context package instead of adding dependency-injection syntax. Its API looks like an ordinary library, but the compiler tracks every accessed service in the function's type signature.

:::code-group{syncKey=""}

```ts [Smithers]
import { Context } from "smthrs/context"

abstract class Clock extends Context {
  abstract now(): Date
}

abstract class AuditLog extends Context {
  abstract write(event: AuditEvent): Result<void, AuditError>
}

function issueToken(user: User): Result<Token, AuditError> {
  const clock = Clock.context()
  const audit = AuditLog.context()
  const token = Token.create(user, clock.now())
  audit.write({ type: "token.issued", userId: user.id })!
  return token
}

// Inferred context: Clock | AuditLog
```

```ts [TypeScript]
interface Clock {
  now(): Date
}

interface AuditLog {
  write(event: AuditEvent): void
}

function issueToken(
  user: User,
  clock: Clock,
  audit: AuditLog,
): Token {
  const token = Token.create(user, clock.now())
  audit.write({ type: "token.issued", userId: user.id })
  return token
}
```

```ts [Effect]
import { Context, Effect } from "effect"

class Clock extends Context.Tag("Clock")<
  Clock,
  { readonly now: () => Date }
>() {}

class AuditLog extends Context.Tag("AuditLog")<
  AuditLog,
  { readonly write: (event: AuditEvent) => Effect.Effect<void, AuditError> }
>() {}

function issueToken(
  user: User,
): Effect.Effect<Token, AuditError, Clock | AuditLog> {
  return Effect.gen(function* () {
    const clock = yield* Clock
    const audit = yield* AuditLog
    const token = Token.create(user, clock.now())
    yield* audit.write({ type: "token.issued", userId: user.id })
    return token
  })
}
```

:::

The inherited `context()` method is compiler-aware. It adds the capability class to the function's inferred context channel, and that requirement propagates through ordinary calls until a context or layer provides it. The function stays eager and callers never pass a context argument by hand.

### Comptime can produce real types

Smithers can run deterministic code during compilation, and the result can be a real TypeScript type. Here, a project-defined comptime function turns a tracked model file into a type the rest of the program uses normally.

:::code-group{syncKey=""}

```ts [Smithers]
import { comptime } from "smithers:comptime"

const model = comptime(JSON.parse(embed("./account.model.json")))
const Account = comptime(deriveType(model))

function displayName(account: Account) {
  return `${account.name} (${account.plan})`
}
```

```ts [TypeScript]
// TypeScript cannot return a type from an ordinary build-time function.
// Declare this by hand or add a separate code-generation step.
type Account = {
  id: string
  name: string
  plan: "free" | "pro"
}

function displayName(account: Account) {
  return `${account.name} (${account.plan})`
}
```

```ts [Effect]
import { Schema } from "effect"

const Account = Schema.Struct({
  id: Schema.String,
  name: Schema.String,
  plan: Schema.Literal("free", "pro"),
})
type Account = typeof Account.Type

function displayName(account: Account) {
  return `${account.name} (${account.plan})`
}
```

:::

Effect can derive a type from an Effect schema, but the schema must become the source of truth. Smithers comptime can execute an ordinary, project-defined derivation and return a type. The compiler tracks every input, caches the result, and reports a compile error if evaluation depends on runtime state.

### Files become typed modules

Compiler-known files participate in the same type system and incremental build graph. Smithers takes the direct-import ergonomics of [Bun's loaders](https://bun.sh/docs/bundler/loaders) and extends them with compile-time types and dependency tracking.

#### JSON that keeps its literals

Ordinary TypeScript can import JSON, but values such as strings and numbers are widened. Smithers's const form preserves the file as a deeply readonly literal value.

:::code-group{syncKey=""}

```ts [Smithers]
import config from "./agent.config.json" with {
  type: "json",
  mode: "const",
}

// "reasoning", not string
type Model = typeof config.model
// readonly ["search", "write"], not string[]
type Tools = typeof config.tools
```

```ts [TypeScript]
// agent.config.ts
// Move the data into TypeScript to keep its exact values.
export const config = {
  model: "reasoning",
  tools: ["search", "write"],
} as const
```

```ts [Effect]
// Effect does not change TypeScript's JSON import inference.
// The exact-value workaround is still a TypeScript source file.
export const config = {
  model: "reasoning",
  tools: ["search", "write"],
} as const
```

:::

#### Markdown is a prompt module

A Markdown file imports as a string at compile time. It can go straight into a model request without runtime filesystem access, a raw-loader suffix, or a declaration file.

:::code-group{syncKey=""}

```ts [Smithers]
import systemPrompt from "./system.md" with { type: "text" }

const response = (await model.generate({
  system: systemPrompt,
  prompt: question,
}))!
```

```ts [TypeScript]
import { readFile } from "node:fs/promises"

const systemPrompt = await readFile(
  new URL("./system.md", import.meta.url),
  "utf8",
)

const response = await model.generate({
  system: systemPrompt,
  prompt: question,
})
```

```ts [Effect]
import { FileSystem } from "@effect/platform"
import { Effect } from "effect"

const response = Effect.gen(function* () {
  const fs = yield* FileSystem.FileSystem
  const system = yield* fs.readFileString("./system.md")
  return yield* model.generate({ system, prompt: question })
})
```

:::

#### Rust and Zig import like source modules

Existing Node-API packages built with napi-rs remain ordinary npm dependencies.
Smithers can also import local Rust and Zig sources, drive the foreign compiler,
and generate checked Wasm bindings that the JavaScript host calls.

:::code-group{syncKey=""}

```ts [Smithers]
import { createCanvas } from "@napi-rs/canvas"
import { rank } from "./rank.rs" with { type: "rust" }
import { tokenize } from "./tokenize.zig" with { type: "zig" }

const canvas = createCanvas(512, 512)
const ranked = rank(tokenize(source))
```

```ts [TypeScript]
import { createCanvas } from "@napi-rs/canvas"
import { rank } from "./native/rank.js"

// napi-rs packages work, but local Rust needs a Cargo build,
// a generated .node binary, a JS wrapper, and declarations.
const canvas = createCanvas(512, 512)
const ranked = rank(tokens)
```

```ts [Effect]
import { Effect } from "effect"
import { rank } from "./native/rank.js"

// Effect can wrap the native call, but it does not build the binding.
const ranked = Effect.try({
  try: () => rank(tokens),
  catch: (cause) => new NativeError({ cause }),
})
```

:::

This follows Bun's proven loader model: text files can import as strings, `.node` files use its N-API loader, and [Node-API](https://bun.sh/docs/runtime/node-api) is its stable native boundary. Smithers adds generated source bindings and records source locations, toolchain versions, and dependency edges so diagnostics, watch mode, and remote caching stay correct across every format.

### Concurrency keeps standard call syntax

Async functions remain ordinary async functions. Authored Smithers consumes Promises only with `await`; a static or library combinator starts concurrent work, and `Result.all` combines expected outcomes.

:::code-group{syncKey=""}

```ts [Smithers]
const results = await Promise.all([
  loadProfile(userId),
  loadActivity(userId),
])
const [profile, activity] = Result.all(results)!
```

```ts [TypeScript]
const [profile, activity] = await Promise.all([
  loadProfile(userId),
  loadActivity(userId),
])
// A rejection does not cancel or join the remaining work.
```

```ts [Effect]
import { Effect } from "effect"

const load = Effect.all([
  loadProfile(userId),
  loadActivity(userId),
])
```

:::

Smithers bans Promise instance `.then()`, `.catch()`, and `.finally()` in authored source. Structured cancellation and child ownership belong in an explicit library combinator rather than custom parser syntax. Effect provides those guarantees through Effect values and its fiber runtime.

Every Promise started in authored `.sm` must ultimately be consumed by `await`, directly or through a recognized combinator whose returned Promise is consumed. There is no detach operation, and Layers do not supervise task lifetime.

### Make execution durable where it matters

Durability is explicit. Actions define persistence boundaries; a function passed
to `durable(...)` stays an ordinary function and simply runs under a **journaling
handler**, so branches, loops, closures, and recursion behave exactly as written.
The runtime coordinates those executions across local or remote worker pools
without changing their source-level contract.

:::code-group{syncKey=""}

```ts [Smithers]
import { durable } from "smithers:flows"

abstract class Research extends Action<
  (input: ResearchInput) => Result<Report, ResearchFailed>
> {}

abstract class Publish extends Action<
  (input: PublishInput) => Result<Publication, PublishFailed>
> {}

const Release = durable(function Release(
  input: ReleaseInput,
): Result<Publication, ResearchFailed | PublishFailed> {
  const report = Research.run({ topic: input.topic })!
  return Publish.run({ report })
})
```

```ts [TypeScript]
async function release(input: ReleaseInput) {
  const report = await research({ topic: input.topic })
  return publish({ report })
}

// Persistence, retries, idempotency, and resume state need a
// workflow SDK or application-specific storage around this function.
```

```ts [Effect]
import { Effect } from "effect"

const release = (input: ReleaseInput) =>
  Effect.gen(function* () {
    const report = yield* research({ topic: input.topic })
    return yield* publish({ report })
  })
```

:::

The compiler derives success and Error schemas and worker contracts from each
Action's Result signature. The durable runtime resumes an execution after
interruption by re-executing the body and answering each request from the
journal, so an Action whose outcome is already committed is not run again —
including when coordination and workers run on separate machines. Effect adds
typed composition and retry policies, but an Effect program is not durably
journaled across process restarts by itself.

### Start with TypeScript, stay with TypeScript

Use the TypeScript ecosystem as it is — its packages, tools, and deployment infrastructure. Smithers emits ordinary TypeScript, so adoption is incremental and reversible, and compute-heavy work can call into Zig or Rust through generated Wasm bindings without switching languages.

TypeScript is the only compilation target. Near-native and general Wasm targets
are outside the language contract. Wasm remains available as a library format
for foreign modules called by a JavaScript host.

Teams can adopt Smithers inside an existing TypeScript codebase and change
JavaScript hosts or deployment topologies without changing the language model.

## Features

Smithers is designed to provide these capabilities out of the box:

- **TypeScript ecosystem:** import TypeScript packages at an explicit foreign boundary while authored `.sm` keeps its own grammar
- **Foreign source imports:** call Zig and Rust through generated, typed Wasm bindings without hand-written glue
- **Comptime type generation:** derive validators, codecs, and real types without maintaining a parallel schema language
- **Durable programs:** run ordinary functions under a journaling handler so they resume after interruption and coordinate work across machines
- **Typed Results:** use must-use `Result<A, E>` values and exhaustive Error matching across synchronous and asynchronous functions
- **Capability-based dependencies:** make databases, clocks, filesystems, and other services visible in function types
- **Typed asset imports:** load JSON, Markdown, MDX, SQL, GraphQL, Zig, and Rust through compiler-tracked loaders
- **Concurrency without Promise chains:** use typed workers, static/library joins, `await`, and cancellation without a fiber runtime

## Built for tools and agents

Reliable agents need more than a tool-call protocol. They need explicit authority, recoverable failures, runtime validation, deterministic compilation, and durable work that can resume after interruption.

Smithers makes those concerns part of one language model. Generated TypeScript runs with an explicit function surface, platform access is capability-based, and Actions or Flows add durability only where the program asks for it.
