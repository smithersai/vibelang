# Getting Started [Start with TypeScript-shaped code, then add Results and requirements]

## Overview

Smithers uses a TypeScript-derived frontend. A `.sm` file opts into Smithers semantics; imported `.ts` and `.js` files retain their normal behavior.

The language focuses on:

- expected failures as `Result<A, E>` values
- capability-based dependency injection
- deterministic compile-time execution
- opt-in durable and distributed execution

Compiler intrinsics such as `comptime(...)` and `durable(...)` are imported functions rather than keywords.

:::warning
Smithers is under active implementation. The root CLI defaults to a checked
TypeScript instrument, and `check`, `compile`, and `run` also expose an opt-in
Go implementation inside the pinned TypeScript fork. The two implementations
are substantial evidence, not a claim that a conforming general-purpose
compiler or production distribution has been released. Documentation examples
describe the accepted language design unless a page gives a narrower current
implementation boundary.
:::

## Build and Verify the Repository

```bash
git clone https://github.com/smithersai/smithers.git
cd smithers
npm install
npm test
```

This builds the checked frontend and packaged runtime, checks compatibility
declarations, runs the Node tests, and runs the Go compiler-contract tests. The
regex transformer under `prototype/` is historical. The checker-backed frontend
under `poc/src/language` is the implementation used by the root package and CLI.

## Try the Checked POC

The current frontend can check, compile, inspect, test, and run its supported
subset across relative `.sm` imports.
For example, save this as `answer.sm`:

```ts
class InvalidAnswer extends Error {}

function answer(valid: boolean): Result<number, InvalidAnswer> {
  if (!valid) throw new InvalidAnswer("invalid")
  return 42
}

answer(true).match({
  ok: value => `answer=${value}`,
  error: () => "failed",
})
```

After `npm test` has built the repository, run:

```bash
node bin/smithers.js check answer.sm --format json
node bin/smithers.js check answer.sm --backend go --format json
node bin/smithers.js compile answer.sm --outDir build/smithers --format json
node bin/smithers.js compile answer.sm --backend go --outDir build/smithers-go --format json
node bin/smithers.js compile answer.sm --outDir build/smithers --declaration --sourceMap
node bin/smithers.js run answer.sm
node bin/smithers.js run answer.sm --backend go
node bin/smithers.js inspect answer.sm --format json
node bin/smithers.js doctor --format json
```

The Go commands require an exact, forkpatch-applied checkout; the [CLI
reference](/reference/cli#compiler-backends) gives the preparation and refusal
rules. Omitting `--backend` selects the TypeScript instrument.

An installed package exposes the same commands through the `smithers` binary.
The default path can emit `.mjs`, `.d.mts`, and composed JavaScript source maps; rejects
mixed `.sm`/TypeScript invocations; and fails on unsupported options,
colliding outputs, unsafe target pins, or any invalid module before committing
the project output. Concrete rows propagate across the discovered `.sm`
graph. The Go backend independently lowers Result/Optional semantics, async
`Promise<Result<...>>`, nominal error matching, both compiler intrinsics, and
all nine Smithers surface-grammar forms through the fork's checker and printer.
Generic row polymorphism, watch/incremental builds, full foreign-value
provenance, and other design-stage surfaces remain outside the current product
boundary. See the [CLI reference](/reference/cli) for the exact division of
responsibility.

## Accepted Design: Your First Fallible Function

```ts
import { Context } from "smthrs/context"

class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

abstract class Users extends Context {
  abstract find(id: string): User | undefined
}

function getUser(id: string): Result<User, NotFound> {
  const users = Users.context()
  return users.find(id).toResult(() => new NotFound(id))
}
```

The ordinary return type tells the whole story:

- `User` is the success value.
- `NotFound` is the expected Error.
- `Users.context()` adds `Users` to the compiler-inferred requirement channel.
- `User | undefined` models a successful lookup with no value.

## Handle or Propagate

Handle both Result variants with `match`, then use `error.match` for a known Error union:

```ts
const user = getUser("42").match({
  ok: user => user,
  error: error => error.match({
    NotFound: () => User.guest(),
  }),
})
```

Use `!` when the enclosing function returns a compatible Result:

```ts
function displayName(id: string): Result<string, NotFound> {
  const user = getUser(id)!
  return user.name
}
```

Inside a Result-returning body, a plain return is lifted to success and a thrown Error is lifted to error. No explicit success/error constructor is needed.

## Provide a Capability

```ts
import { Layer } from "smthrs/provider"

const App = Layer.succeed(Users, new PostgresUsers(databaseUrl))

const name = Layer.provide(App, () => displayName("42")!)
```

Removing the `Users` provider is intended to be a compile error. Tests can provide an in-memory implementation without changing application code. A Layer only supplies the environment; resources are acquired and finalized explicitly outside it.

## Async Results

```ts
async function loadUser(
  id: string,
): Promise<Result<User, Timeout | NotFound>> {
  const response = (await HttpClient.context().get(`/users/${id}`))!
  return (await response.json(User))!
}
```

`await` unwraps the Promise but leaves the Result. Authored Smithers does not use Promise instance `.then`, `.catch`, or `.finally`.
