# Getting Started [Start with TypeScript-shaped code, then add Results and requirements]

## Overview

VibeLang uses a TypeScript-derived frontend. A `.vibe` file opts into VibeLang semantics; imported `.ts` and `.js` files retain their normal behavior.

The language focuses on:

- expected failures as `Result<A, E>` values
- capability-based dependency injection
- deterministic compile-time execution
- opt-in durable and distributed execution

Compiler intrinsics such as `comptime(...)` and `durable(...)` are imported functions rather than keywords.

## Create a Project

```bash
npm install --save-dev vibelang
npx vibe init
```

`vibe init` writes three files into the current directory. Check and run them:

```bash
npx vibe check main.vibe
npx vibe run main.vibe
```

```text
hello, Ada
```

`check` validates the complete project graph without emitting artifacts. `run`
checks the graph and executes the selected entry module. See the [CLI
reference](/reference/cli) for the command contract.

### The three files

The project's `tsconfig.json` sets the six soundness options every `.vibe`
project must carry. `vibe check -p tsconfig.json` refuses a project that weakens
one of them, so start from this file rather than from `tsc --init`.

```json [tsconfig.json]
{
  "compilerOptions": {
    "target": "esnext",
    "module": "esnext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "useDefineForClassFields": true,
    "allowImportingTsExtensions": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["**/*.vibe", "**/*.ts"]
}
```

`main.vibe` is the program. Nothing is ambient in `.vibe`: `console`,
`process`, the clock, and the network are not in scope, so even printing a line
goes through a capability. Here the program declares one, `Console`, and
provides an implementation with a `Layer`.

```ts [main.vibe]
import { Context } from "vibelang/context"
import { Layer } from "vibelang/provider"
import { writeLine } from "./stdout.ts"

abstract class Console extends Context {
  abstract info(message: string): void
}

class StdoutConsole extends Console {
  info(message: string): void {
    writeLine(message)
  }
}

class NotFound extends Error {}

function greeting(id: number): Result<string, NotFound> {
  if (id !== 1) throw new NotFound(`no user ${id}`)
  return "hello, Ada"
}

const App = Layer.succeed(Console, new StdoutConsole())

Layer.provide(App, () => {
  const console = Console.context()
  greeting(1).match({
    ok: text => console.info(text),
    error: error => console.info(`failed: ${error.message}`),
  })
})
```

`stdout.ts` is the one place the program touches the host. It is ordinary
TypeScript, so it may use `console`. Its leading JSDoc carries a trust claim the
compiler honours: with `@module` and `@throws {never}` present, importing it adds
no `panic` case to the caller's failure row. Without the claim, the import is
refused as `VIBE1510` until you wrap the call in a checked adapter.

```ts [stdout.ts]
/**
 * The one place this program touches the host. Ordinary TypeScript, with a
 * trust claim the compiler honours: importing it adds no panic channel.
 * @module
 * @throws {never}
 */

/** @throws {never} */
export function writeLine(text: string): void {
  console.log(text)
}
```

Three things happened in twenty lines. `greeting` returned `Result<string,
NotFound>` without any constructor: the plain `return` became the success value
and the `throw` became the failure value. `Console.context()` added `Console` to
the requirement row of the callback, and `Layer.provide` satisfied it. And the
host boundary was crossed exactly once, in a file whose trust claim is visible.

:::note The shipped platform roster is not importable from `.vibe` yet — measured 2026-09-05
`vibelang/platform` ships `Console`, `SystemConsole`, `Clock`, `FileSystem`,
and the rest of the roster for TypeScript callers, but importing it from a
`.vibe` file is refused with `VIBE1510` because the module carries no trust
marker, and a class declared there is not yet recognized as a capability. That
is why the scaffold declares its own `Console`. The compiler change that closes
this is recorded in the [Standard Library](/reference/standard-library) page.
:::

## Your First Fallible Function

```ts
import { Context } from "vibelang/context"

class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

abstract class Users extends Context {
  abstract find(id: string): User | undefined
}

function getUser(id: string): Result<User, NotFound> {
  const users = Users.context()
  const user = users.find(id)
  if (user === undefined) throw new NotFound(id)
  return user
}
```

The ordinary return type tells the whole story:

- `User` is the success value.
- `NotFound` is the expected Error.
- `Users.context()` adds `Users` to the compiler-inferred requirement channel.
- `User | undefined` models a successful lookup with no value.

## Handle or Propagate

Handle both Result variants with `match`, then use `error.match` for a known Error union:

```ts
const user = getUser("42").match({
  ok: user => user,
  error: error => error.match({
    NotFound: () => User.guest(),
  }),
})
```

Use `!` when the enclosing function returns a compatible Result:

```ts
function displayName(id: string): Result<string, NotFound> {
  const user = getUser(id)!
  return user.name
}
```

Inside a Result-returning body, a plain return is lifted to success and a thrown Error is lifted to error. No explicit success/error constructor is needed.

Here is the same idea as one complete file. The rows `vibe check` reports for it
name `NotFound` as the failure and `Users` as the requirement of both functions.

```ts [users.vibe]
import { Context } from "vibelang/context"
import { Layer } from "vibelang/provider"

type User = { name: string }

class NotFound extends Error {
  constructor(readonly id: string) {
    super(`User not found: ${id}`)
  }
}

abstract class Users extends Context {
  abstract find(id: string): User | undefined
}

function getUser(id: string): Result<User, NotFound> {
  const user = Users.context().find(id)
  if (user === undefined) throw new NotFound(id)
  return user
}

function displayName(id: string): Result<string, NotFound> {
  const user = getUser(id)!
  return user.name
}

class MemoryUsers extends Users {
  find(id: string): User | undefined {
    return id === "42" ? { name: "Ada" } : undefined
  }
}

const App = Layer.succeed(Users, new MemoryUsers())

export const name = Layer.provide(App, () => displayName("42")).unwrapOr("anonymous")
```

## Provide a Capability

```ts
import { Layer } from "vibelang/provider"

const App = Layer.succeed(Users, new PostgresUsers(databaseUrl))

const name = Layer.provide(App, () => displayName("42")).unwrapOr("anonymous")
```

Note the missing `!` inside the callback. A `Layer.provide` body that propagates
with `!` is refused — `VIBE2105`, "fallible `Layer.provide` callbacks need an
explicit `Result` (or `Promise<Result>`) contract so the provided computation
keeps its failure channel". Return the Result from the callback and consume it
outside, which is what keeps `NotFound` visible in the caller's type.

Removing the `Users` provider is intended to be a compile error. Tests can provide an in-memory implementation without changing application code. A Layer only supplies the environment; resources are acquired and finalized explicitly outside it.

## Async Results

```ts
const UserSchema = comptime(Schema.derive<User>())

async function loadUser(
  id: string,
): Promise<Result<User, HttpError | MalformedResponse | ValidationError>> {
  const response = (await HttpClient.context().get(`/users/${id}`))!
  return UserSchema.parse(response.json()!)!
}
```

`await` unwraps the Promise but leaves the Result. Authored VibeLang does not use Promise instance `.then`, `.catch`, or `.finally`.

Note the two steps. `response.json()` is **synchronous** and takes no argument —
it returns `Result<unknown, MalformedResponse>`, the parse and nothing more.
Turning that `unknown` into a `User` is a separate, explicit validation against a
comptime-derived schema; see [Runtime Validation](/guide/runtime-validation).
There is no `response.json(User)` overload.
