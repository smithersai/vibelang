# Project Philosophy [Keep the language familiar, explicit, and analyzable]

## TypeScript-Shaped, With an Explicit Boundary

Imported `.ts` and `.js` preserve host behavior. A `.sm` file uses a TypeScript-derived grammar plus Smithers semantic checks and lowering. This boundary permits must-use Results, Promise-chain restrictions, capability inference, and statically derived durable boundaries without pretending that all JavaScript already obeys those rules.

## Expected Failures Are Values

Smithers uses `Result<A, E>` and `Promise<Result<A, E>>` as ordinary runtime types. The compiler makes them pleasant to author:

```ts
function loadConfig(
  path: string,
): Result<Config, FileNotFound | InvalidConfig> {
  const fs = FileSystem.context()
  const source = fs.readText(path)!
  return Config.parse(source)!
}
```

Plain success returns and Error throws are lifted into the appropriate variant. `!` propagates. Public APIs use normal generic return types, so tools do not need to understand an erased failure annotation.

Absence follows the same philosophy taken one step further: there is no `Optional<T>` at all. `T | undefined` with ordinary narrowing, `?.`, and `??` already expresses it precisely, so a second representation would add a conversion boundary without adding safety.

## Inference Inside, Contracts at Boundaries

The compiler may infer success/error unions and context requirements from a body. Exported APIs should spell their Result return type explicitly. Requirements arise from compiler-recognized `Capability.context()` calls and continue to propagate statically until a Layer supplies them.

## Imported Intrinsics, Not Keywords

Compile-time and durable semantics are anchored by resolved imports:

```ts
import { comptime } from "smithers:comptime"
import { durable } from "smithers:flows"
```

This keeps code visually close to TypeScript, allows aliases, and avoids reserving words. Import identity—not spelling alone—activates the compiler behavior.

## Platform Is a Dependency

Filesystem, network, clocks, randomness, environment variables, and host globals
differ across JavaScript hosts. Modeling them as capabilities gives deployment
configuration and deterministic testing one mechanism.

## Comptime Is Hermetic

`comptime(...)` may generate values, types, validators, and loaders, but it cannot silently observe ambient filesystem state, the network, the clock, or randomness. External compiler inputs arrive through tracked imports or loader contexts. A Flow's durable boundaries are derived by a separate compiler pass initiated by `durable(...)`; a Flow is never run — with proxy values, symbolic values, or otherwise — to discover what it may request, at any phase including replay.

## Standard Imports for Non-Code Inputs

Assets and foreign source use import attributes instead of new grammar:

```ts
import config from "./config.json" with { type: "json", mode: "const" }
import prompt from "./prompt.mdx" with { type: "mdx" }
```

The loader and every string-valued attribute become part of the reproducible build node.

## TypeScript Compilation

The compiler preserves the stock TypeScript pipeline wherever possible. Durable
builds may partition coordinator and worker artifacts while keeping one
source-level contract.

## One Toolchain

The product follows Go's shape: compiler, formatter, language service, tests,
standard library, and build integration as one coherent distribution. Its
compiler architecture is a minimal-diff TypeScript fork with narrow Smithers
seams.
