# Why Smithers [Why application structure belongs in the compiler]

TypeScript describes values well, but serious applications also need to describe expected errors, dependencies, validation boundaries, and durable execution.

## The Missing Parts

```ts
async function getUser(id: string): Promise<User> {
  const response = await fetch(`/users/${id}`)
  if (!response.ok) throw new Error("request failed")
  return response.json()
}
```

The signature hides several facts: the operation can fail, it depends on ambient networking, the response is unvalidated, and tests must intercept global behavior.

## The Library Answer

Effect systems implemented as libraries make success, failure, and requirements explicit. That model is valuable, but it introduces a second execution vocabulary and a runtime interpreter.

## The Compiler Answer

Smithers keeps the useful information in ordinary-looking code while representing expected failure honestly as a value:

```ts
async function getUser(
  id: string,
): Promise<Result<User, NotFound | Timeout | InvalidResponse>> {
  const http = HttpClient.context()
  const response = (await http.get(`/users/${id}`))!
  if (response.status === 404) throw new NotFound(id)
  return (await response.json(User))!
}
```

The compiler lifts plain success returns and Error throws into Result variants. It also tracks `HttpClient.context()` as a requirement until a Layer provides it. No caller manually threads context.

Compiler support enables:

- Result/error inference through ordinary calls
- exhaustive matching over known Error unions
- one visible `Promise<Result<A, E>>` model for async failure
- validators derived from ordinary types at comptime
- target selection and platform capability checking
- durable execution derived from checked source, with ordinary control flow

## Why Result Values?

An earlier design erased a separate failure row and required new propagation and catch grammar. Using `Result<A, E>` makes the public contract readable by existing TypeScript tooling and removes most parser changes. Compiler lifting preserves concise bodies, while callers still see and must use the failure value.

## Why Durable Execution Belongs Here

Durable runtimes commonly repeat schemas, error shapes, dependencies, and RPC bindings that the compiler already knows. Passing a statically resolvable function to `durable(...)` lets Smithers derive those boundaries from types it has already checked.

The function itself stays an ordinary function. `durable(...)` changes only which
handler answers its Action calls, so branches, loops, closures, and recursion all
work inside a Flow, and each completed Action is journaled so a restart resumes
instead of repeating. Inspection reads a compiler-published **Effect Manifest** —
a bound on what a Flow may request — and never executes the Flow or its Actions.

The trade is stated plainly rather than hidden: the previous design could decide
statically and totally whether a live execution could move to a new Flow version,
and could sign an artifact describing *what a Flow will do*. Neither is available
under replay in that form. See
[Durable Execution](/specification/durable-execution) §What Replay Trades Away.

Durability remains opt-in. Ordinary functions do not pay for a scheduler.

## When Smithers Fits

Smithers is for TypeScript teams that want:

- expected failures as must-use values with concise function bodies
- explicit transitive dependencies without manual context arguments
- host-agnostic services across JavaScript runtimes and tests
- type-driven validation and asset loading
- durable workflows written as ordinary functions, with statically derived boundaries

Smithers fits code that can keep foreign reflection and ambient authority behind
explicit boundaries. Programs that depend pervasively on unconstrained
JavaScript reflection cannot retain all of its static guarantees.
