# Results and Errors [Return expected failures as values]

Smithers uses ordinary TypeScript-shaped code and makes expected failure explicit in the return type. A synchronous fallible function returns `Result<A, E>`; an asynchronous one returns `Promise<Result<A, E>>`.

## Declare an Error

Expected failures are normal `Error` subclasses:

```ts
class NotFound extends Error {
  constructor(readonly id: string) {
    super(`Not found: ${id}`)
  }
}

class RateLimited extends Error {
  constructor(readonly retryAfter: Duration) {
    super("Rate limited")
  }
}
```

No tagged-error factory, special declaration, or `_tag` field is required. The compiler derives stable nominal identity and transport metadata while retaining `instanceof`, `cause`, stack traces, and ordinary JavaScript error behavior.

## Write a Fallible Function

Annotate the ordinary return type with `Result`:

```ts
function readSettings(
  path: string,
): Result<Settings, FileNotFound | PermissionDenied | InvalidSettings> {
  const fs = FileSystem.context()
  const source = fs.readText(path)!
  return Settings.parse(source)!
}
```

Inside a `Result`-returning function, Smithers lowers plain `return value` to the success variant and `throw error` to the error variant. Returning an existing compatible `Result` does not nest it. Consequently source code does not need `Result.ok` or `Result.err`, and those constructors are not part of the authoring API.

When a body has no annotation, the compiler infers `A` from returned values and `E` from reachable `Error` throws, returned Results, and `!` propagation points.

## Propagate With `!`

`Result!` is compiler-aware control flow:

```ts
function loadApplication(): Result<Application, ReadSettingsError> {
  const settings = readSettings("app.json")!
  return Application.make(settings)
}
```

On success it produces the value. On error it returns that error from the enclosing `Result`-returning function. In plain JavaScript without Smithers lowering, it throws the original error so a missed compiler transform fails visibly.

Results are must-use values. Discarding a Result is a diagnostic unless the code explicitly acknowledges it.

## Inspect and Transform a Result

Use normal methods for value-oriented handling:

```ts
const label = readSettings("app.json").match({
  ok: settings => settings.name,
  error: error => `unavailable: ${error.message}`,
})

const port = readSettings("app.json")
  .map(settings => settings.port)
  .unwrapOr(3000)
```

The initial quality-of-life surface is:

- `isOk()`, `isError()`, `match(...)`
- `map(...)`, `mapError(...)`, `andThen(...)`, `flatten()`, `recover(...)`
- `tap(...)`, `tapError(...)`, `tapBoth(...)`
- `unwrapOr(...)`, `expect(...)`
- `Result.all(...)`, `Result.try(...)`, and `Result.tryPromise(...)`

There is no `unwrap()`. It was the propagation spelling before postfix `!`
replaced it, and writing it is now a compile error — `SMITHERS1206`, pinned by
`19-retired-syntax/result-dot-unwrap-is-retired`. Use `!` to propagate, `expect`
to panic with an invariant message, or `unwrapOr` to supply a fallback. The
compiler-owned runtime still carries an `unwrap` as its missed-lowering
fallback, so a program that escaped the transform fails visibly instead of
silently; that is not authoring surface.

[Results and Errors](/reference/errors) §Result Methods is the complete list and
the authority. This one repeats it for the guide's narrative, so prefer that page
if the two ever disagree.

`Result.try` and `Result.tryPromise` exist for foreign JavaScript boundaries that may throw or reject. They are not success/error constructors.

## Match Specific Errors

Every `Error` has compiler-supported helpers:

```ts
const message = readSettings("app.json").match({
  ok: settings => `loaded ${settings.name}`,
  error: error => error.match({
    FileNotFound: error => `missing ${error.path}`,
    PermissionDenied: error => `cannot read ${error.path}`,
    InvalidSettings: error => error.message,
  }),
})
```

For a known error union, `error.match` is exhaustive and narrows each handler argument. `error.matchPartial(handlers, fallback)`, `error.is(Constructor)`, `error.matches(...)`, and `error.rootCause()` support partial matching and inspection. Dispatch uses compiler-provided nominal identity, not a user-maintained string tag.

## Async Functions

`await` unwraps only the Promise. The Result remains visible:

```ts
async function loadUser(
  id: string,
): Promise<Result<User, HttpError | MalformedResponse | ValidationError>> {
  const http = HttpClient.context()
  const response = (await http.get(`/users/${id}`))!
  return UserSchema.parse(response.json()!)!
}
```

Authored Smithers bans Promise instance `.then()`, `.catch()`, and `.finally()`. Use `await`, then handle the resulting `Result`. Imported JavaScript and TypeScript libraries may use ordinary Promise internals behind their boundary.

## Propagation

Postfix `!` propagates a Result error to the caller:

```ts
const user = findUser(id)!
```

If the Result is a success, `!` yields the value. If it is an error, the enclosing function returns that error variant — no exception is thrown. This is the job Zig gives `try foo()`, using an operator TypeScript already has, so it costs no grammar.

TypeScript's non-null assertion does not exist in `.sm`. Removing that meaning entirely is what makes the operator unambiguous, and it was an unsound escape hatch most codebases already lint against.

`??` and `?.` are untouched — they still mean exactly what they mean in TypeScript. Failure and absence are separate axes, and both can appear in one expression:

```ts
const name = findUser(id)!?.nickname ?? "anonymous"
```

### Where `!` Is Accepted

Placement is **unrestricted**. Because `!` lowers to an expression in every
position, it preserves the authored evaluation order everywhere, so
`r!.trim()`, `r![0]`, `maybe ?? r!` and `f(r!)` are all accepted alongside the
simple `const x = r!` form.

:::warning The prototype has not caught up — (SA-1)
Re-measured on 2026-08-27 against the conformance reference backend over
`poc/src`: of the six forms [Failure Semantics](/specification/failures)
§Refusal Conditions lists as accepted, **two compile** — `r!.length` and
`r! ?? "fallback"` — and the other four (`r!.trim()`, `r![0]`, `maybe ?? r!`,
`f(r!)`) are refused with `SMITHERS1204` ("would require control-flow-aware
evaluation-order rewriting"), which is the *withdrawn* fourth refusal. The corpus
certifies both the two acceptances and the four refusals in
`02-unwrap-propagation`. Until the implementation catches up, write the
propagation as a simple statement.

This gap is recorded as `(SA-1)`; the marker convention and the register of
current gaps are in [Specification Status](/specification/index)
§Specification–Implementation Gaps.
:::

Exactly three conditions refuse a `!` under the current rule, each with its own
diagnostic:

1. the enclosing function has no Result channel and infers no failures;
2. the operand's provenance is not a Result;
3. the `!` is lexically inside a `try` block that has a `catch` clause.

The third one is worth knowing before you reach for `try`/`catch` at an interop
boundary. The failure exit unwinds the delimited computation: `finally` blocks and
`using` disposals run, and `catch` clauses do not. Authored text that put a `!`
inside a `try`/`catch` would read as though the failure were catchable when it is
not, so it is refused rather than silently lowered. Delivering the failure through
the JavaScript exception channel so that `catch` observes it is prohibited.

[Failure Semantics](/specification/failures) §Refusal Conditions is normative.

## Defects and Foreign Exceptions

Expected domain errors belong in `E`. A failed compiler/runtime invariant uses `Reflect.panic(...)`. Any unannotated TypeScript or JavaScript call adds this distinguished checked `panic` case, including undeclared exceptions, Promise rejections, and signature violations. A caller must propagate it, catch it explicitly, or use a trusted adapter to translate it to a specific `Error` subclass. Trusted `@throws {never}` metadata opts out; `@throws {T}` declares a precise foreign channel. Ordinary Result recovery does not swallow panic implicitly.

JavaScript statement-form `try/catch` remains available for low-level interop. It is not the typed recovery API, and a `!` may not appear inside a `try` block that has a `catch` clause — see §Where `!` Is Accepted.

## Cleanup

Scope-exit cleanup uses TC39 explicit resource management, inherited from TypeScript:

:::warning Illustrative API
`createTemp`, `replace`, and a writable file handle are **not** on the shipped
`FileSystem` capability, which declares exactly `readText`, `writeText`,
`readBytes`, `writeBytes`, `exists`, `remove`, `mkdir`, `readDir`, and a `*Sync`
counterpart for each. The snippets below illustrate the *shape* of failure
handling with `using`; write them against the members above, or against your own
capability that provides the rest.
:::

```ts
function replaceFile(
  path: string,
  contents: string,
): Result<void, FileError> {
  const fs = FileSystem.context()
  using temporary = fs.createTemp(path)!

  temporary.write(contents)!
  fs.replace(temporary.path, path)!
}
```

Cleanup that should run only on failure goes in the failure path rather than in a dedicated statement form:

```ts
return temporary
  .write(contents)
  .andThen(() => fs.replace(temporary.path, path))
  .tapError(() => fs.remove(temporary.path))
```

Smithers previously had `defer` and `errdefer` for this. Both were removed: neither is a TC39 proposal, `using` already covers scope exit, and error-path cleanup is expressible with the Result combinators above. How `using` disposal orders against a compiler-generated `!` early return is [not yet settled](/specification/control-flow).

The same open specification has to cover **abandonment**, which is new: when a
handler declines to resume a suspended computation, every live `using` and
`await using` scope in it is disposed in reverse acquisition order and every
`finally` block runs, while `catch` clauses do not. A computation is never
abandoned with a resource undisposed. Whether a disposal error raised during
abandonment can be observed is **open**.
