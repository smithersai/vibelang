# Control Flow [TypeScript's control flow, plus one standards-track addition]

Smithers control flow is TypeScript control flow. `if`, `switch`, `for`, `while`, blocks, labels, and `break` all behave exactly as they do in TypeScript, and none of them is an expression.

That is a deliberate reversal of an earlier design. Smithers previously added expression-position `if` and `switch`, labeled block and loop values, a value-carrying `break :label`, a loop `else` completion, and `defer`/`errdefer`. All of it worked, and all of it has been removed, because none corresponded to a TC39 proposal and TypeScript could already express every one of them:

| Removed form | What TypeScript already does |
| --- | --- |
| `const t = if (c) a else b` | `const t = c ? a : b` |
| `const t = switch (k) { case "a": x }` | a lookup object, or a conditional chain |
| `label: { break :label v }` | a function, or a `let` assigned on each path |
| `label: for (…) { break :label v } else d` | a `let` initialized to the default, assigned in the loop |
| `defer f()` | `using`, or a `finally` block |
| `errdefer f()` | cleanup written in the failure path |

New grammar is permanent and costs parser, formatter, and language-server work forever. Convenience does not pay for it.

## The One Addition

Declarations in conditionals, adopted early from the TC39 proposal of that name:

```ts
if (const user = cache.get(id); user !== undefined) {
  render(user)
} else {
  renderMiss()
}
```

The binding is visible in the then branch and in every `else` branch, and is out of scope after the construct.

This is accepted because it is standards-track. It is currently **Stage 1**, the earliest stage, so it remains the single form whose inclusion rests on a proposal that could still change or be withdrawn.

## Cleanup

Use TC39 explicit resource management, which TypeScript already supports:

```ts
function write(
  path: string,
  contents: string,
): Result<void, FileError> {
  const fs = FileSystem.context()
  using file = fs.open(path, "write")!
  file.write(contents)!
}
```

:::warning Illustrative API
`fs.open` and the file handle it returns do not exist. The shipped `FileSystem`
capability declares `readText`, `writeText`, `readBytes`, `writeBytes`, `exists`,
`remove`, `mkdir`, `readDir`, and a `*Sync` counterpart for each — no handle
type, so nothing here is disposable. The snippet shows what `using` is *for*; a
working equivalent is `fs.writeTextSync(path, contents)!`. `using` itself is
real and works on any `Disposable` you supply.
:::

Cleanup that should run only when the function fails goes in the failure path rather than in a dedicated statement:

```ts
const database = Database.context()
const transaction = database.begin()!

return transaction
  .commit()
  .tapError(() => transaction.rollback())
```

How `using` disposal orders against a compiler-generated `!` early return is not yet settled; see the [specification](/specification/control-flow).

## Throw

Statement-form `throw` is unchanged, and inside a fallible function the compiler lowers the thrown `Error` to the Result error variant:

```ts
function readPort(config: Config): Result<number, InvalidConfig> {
  if (config.port === undefined) throw new InvalidConfig("port")
  return config.port
}
```

There is no throw expression. The TC39 proposal is at Stage 2; if it reaches TypeScript, Smithers inherits it rather than inventing it.

## Loops

Loops are statements and produce no value. Runtime-sized loops are ordinary runtime loops; comptime-known loops may be evaluated or unrolled when used from comptime code.
