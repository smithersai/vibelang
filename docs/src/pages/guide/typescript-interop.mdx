# TypeScript Interop [Adopt VibeLang without leaving the JavaScript ecosystem]

Imported `.ts` and `.js` modules keep their host behavior. A `.vibe` file opts into must-use Results, Promise-chain restrictions, capability inference, and other VibeLang semantics.

VibeLang is intentionally TypeScript-shaped, but `.vibe` is not a syntactic superset of TypeScript. Complete TypeScript remains in imported `.ts`/`.tsx` modules; only explicitly documented shared syntax and behavior carry across.

## Type-Only Imports

```ts
import type { User } from "./legacy-types"
```

A type-only import has no runtime effect. Runtime use of imported TypeScript or JavaScript adds the checked `panic` channel unless the boundary is annotated or adapted.

## Exact Host Modules

```ts
import { readFile } from "node:fs/promises"
```

The import constrains the program to a host that supplies that module.
Application code should usually depend on a `FileSystem` capability instead.

:::warning There is no `Module<…>` requirement — measured 2026-08-28
An earlier draft said this import "contributes `Module<"node:fs/promises">`". It
does not, and no such type exists. The module-requirement machinery was
part of the portability pin, withdrawn on 2026-08-23. What the import actually
draws today is `VIBE1510` — "foreign module initialization can panic before
a checked call boundary" — unless the import is type-only or the module carries
a leading `@module @throws {never}` JSDoc marker. So the host constraint is
carried by the panic channel, not by a requirement row, and nothing reports it
as a portability fact.

**Corrected 2026-08-28.** This note used to give a second, wrong reason: that
"the frontend's ambient requirement type admits only `Clock`, `Random`, and
`Host`". It does not constrain requirements at all. The requirement **row** is
open — it is every `Context` subclass a program names, so a locally declared
`Scheduler` or `Locale` publishes `requirements: ["Scheduler"]` /
`["Locale"]` with no compiler change — and the `"Clock" | "Random" | "Host"`
union is a *diagnostic-category* discriminator selecting
`VIBE1602`/`1603`/`1601`. `Module<…>` is missing because it was withdrawn,
which is the first reason and the only true one.
:::

## Dynamic Features

`any`, `eval`, unconstrained reflection, Promise subclassing, and custom
thenables can invalidate VibeLang's static guarantees. The compatibility
specification defines which uses add `panic` and which are rejected.

:::note Decided 2026-09-06 — `eval` is refused
`eval`, the `Function` constructor, and `constructor` on a callable are refused
in `.vibe` (`VIBE1604`). The specification and the compiler now agree; see
[Compatibility](/specification/compatibility) §Dynamic Features. Inside a Flow
body the stakes are higher still: an `eval`'d string produces no journal entry,
so there is no divergence to detect.
:::

:::note Open — dynamic import
The ledger, the conformance corpus, and the shipped product disagree three ways.
The lock reads as permitting it; the compiler reads it narrowly and the corpus
certifies **two cases as compiling and running**; and the shipped CLI refuses
**every** dynamic import — including those two — as deferred. Recorded in
`DECISIONS.md` §TypeScript target. No page should move either side first.

Inside a Flow body a dynamic import is also the unresolvable callee the Effect
Manifest's soundness rule governs: reject it, or widen the Manifest to the
callee's whole module. Never narrow.
:::

## Adapt a Throwing Boundary

```ts
class ConnectFailed extends Error {
  constructor(options: { cause: unknown }) {
    super("Connection failed", options)
  }
}

function connect(options: Options): Result<Client, ConnectFailed | Panic> {
  return Result.try(
    () => legacyConnect(options),
    cause => new ConnectFailed({ cause }),
  )
}
```

An unannotated call to `legacyConnect` adds the distinguished checked `panic`
case, and `Result.try` translates a *caught* value to `ConnectFailed`. It does
**not** discharge the channel: `Panic` stays in the contract, and omitting it
draws `VIBE1104`, "Result contract omits reachable failures Panic". That is
the intended design — a panic raised inside a foreign call must not be silently
swallowed by an adapter. Either declare it, as above, or subtract it
deliberately at the boundary with `rethrowPanics` from `vibelang/result`, which
re-throws a panic-valued failure so it keeps unwinding to `catchPanic` and
returns every other Result unchanged.

The same applies to `Result.tryPromise` below.

## Adapt a Rejecting Promise

```ts
async function fetchUser(
  id: string,
): Promise<Result<User, RequestFailed>> {
  return await Result.tryPromise(
    () => legacyFetchUser(id),
    cause => new RequestFailed({ cause }),
  )
}
```

Authored VibeLang consumes Promises with `await`, never instance `.then`, `.catch`, or `.finally`. Imported code may use them internally.

At declaration boundaries, trusted `@throws {never}` metadata removes the default panic case and `@throws {T}` declares the stated failure channel. These annotations are trust claims, not proof that a foreign implementation obeys them.

The JS CLI stages a relative JavaScript library's companion declarations and
their transitive type dependencies with its runtime output. It checks consumers
against those declarations rather than re-inferring erased JavaScript, and
`--declaration` preserves the contracts in the output layout. Declaration files
share the runtime graph's path, alias and size limits. They do not exempt module
initialization: the runtime and its foreign declaration-facing API still need
the separate initialization claim described below. Published VibeLang callable
metadata alone does not grant that trust.

:::note Open — the marker is doing two jobs
The `@module @throws {never}` marker carries **module-initialization safety**,
which it enforces and which is walked transitively, and it sits next to **prelude
access control**, which is enforced not by the marker but by **specifier form**
against an exact registry. The two agree today only because the compiler-owned
runtime modules that construct `Result` variants are unmarked *on purpose*, and
that unmarkedness is the forgery guarantee. A future edit that "tidied up" the
unmarkedness would look like a cleanup and be a forgery hole. Recorded in
`DECISIONS.md` §Compiler and delivery; not resolved here.
:::

## Nullable Boundaries

```ts
const user = legacyLookup(id) ?? undefined
legacyConsume(user ?? null)
```

VibeLang does not reinterpret TypeScript optional properties or null unions. They keep their ordinary TypeScript meaning. There is no `.toNullable()` and no wrapper to convert: `Optional<T>` was withdrawn, absence is `T | undefined`, and crossing to a `null`-based API is the ordinary `?? null`.
