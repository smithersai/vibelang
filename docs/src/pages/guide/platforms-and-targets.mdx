# Hosts [One target, several JavaScript runtimes]

TypeScript is the only compilation target. A `.sm` program emits TypeScript or JavaScript, and the interesting variation is *which JavaScript host* it runs on — Node, Bun, Deno, a browser, or an edge runtime.

## What Was Removed

Smithers previously specified a near-native target through LLVM and a Wasm target, and carried machinery to keep programs checkable against both:

| Removed | Why |
| --- | --- |
| near-native / LLVM target | it expands the language around a second runtime and ABI without serving the TypeScript-first product |
| Wasm compilation target | foreign Wasm modules are useful, but compiling general Smithers programs to Wasm is not part of the product |
| the `TypeScript` requirement | with one target, every program has it, so it recorded nothing |
| portable / `TypeScript`-required / forbidden classification | nothing to be portable *to* |
| the portability pin | nothing to assert |

Two things people associate with that machinery are **not** removed:

- **The checked `panic` channel** on unannotated foreign calls. It exists because JavaScript can throw, reject, or violate a declaration — not because a second target existed.
- **Importing Zig and Rust through Wasm.** That is a loader producing a module the JavaScript host calls, not a compilation target. See [Foreign Sources](#foreign-sources).

## Platform as Capability

Host functionality is a typed capability rather than an ambient global. `process`, `window`, `document`, filesystem, and network are not in scope in authored `.sm`; they arrive as dependencies.

Only facilities present in every JavaScript environment may be unconditional globals, and host-sensitive operations on otherwise universal objects — clock, random — still need capabilities.

Node, Bun, Deno, browser, edge, and test implementations can satisfy the same capability contract.

## Selecting a Host

Use `comptime.target` when the implementation differs by host.

:::warning Host names not reachable under the CLI — measured 2026-08-28
The shipped `smithers` CLI pins the target to `"node-es2022"`, so the `node`,
`bun`, and `deno` keys below never match and the lookup fails with `VCT1004`.
See [Comptime](/reference/comptime) §Target Selection.
:::

```ts
import { comptime } from "smithers:comptime"

const implementations = {
  node: NodeFileSystem,
  bun: BunFileSystem,
  deno: DenoFileSystem,
}

const FileSystemLive = comptime(implementations[comptime.target])
```

Unselected implementations are not emitted.

## Foreign Sources

:::warning Not implemented — measured 2026-08-28
Neither loader is registered; both imports below are refused with
`SMITHERS5213`. The built-in loader types are `json`, `text`, `bytes`,
`markdown`, and `mdx`.
:::

Zig and Rust source modules are intended to import directly, with
compiler-generated typed bindings:

```ts
import { hashMany } from "./hash.zig" with { type: "zig" }
import { parse } from "./parser.rs" with { type: "rust" }
```

These would compile to Wasm modules that the JavaScript host loads and calls. Wasm is a library format here, not a target for Smithers code — which is why this section survives the removals above rather than being withdrawn with them.

The compiler owns toolchain invocation and caching. The import's types, source maps, toolchain versions, feature flags, and foreign dependency graph contribute to its cache identity.

Existing Node-API npm packages also work, including addons built with napi-rs:

```ts
import { parse } from '@acme/parser-native'
```

They keep their published TypeScript declarations and runtime behavior. Node and Bun load `.node` binaries through Node-API, so those packages carry a host-specific dependency that not every JavaScript runtime satisfies.

## Runtime Model

Closures, classes, generics, unions, and async functions are ordinary. Backend-specific lowering is allowed, while source-level failure, requirement, and control-flow semantics stay consistent.
