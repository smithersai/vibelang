# Agent Library [Run generated TypeScript with an explicit authority surface]

Smithers's proposed coding-agent library builds on ordinary TypeScript, typed functions, Actions, Flows, and the built-in MDX loader. It does not add agent-specific language syntax.

:::warning Proposed production API
The root package exposes a narrower working Node-safe POC at `smthrs/agent`:
a coding-agent loop, in-memory TypeScript compiler, explicit function bindings,
prompt renderers, model helpers, Action tools, and a no-permission Deno
subprocess sandbox with timeouts and resource/output/call limits. The Bun-only
`smthrs/agent/bun` entry point adds SQLite turn journaling and durable Flow
tools. Journal rows are digest-checked and hash-chained in append order, so a
restarted process replays the same turn — reusing the recorded model response
and every recorded Action or completed Flow call — instead of re-invoking the
model or the host. The POC also has a
typed `ModelAdapter` seam carrying model identity and version, and adapters that
turn a tool's source into a durable Action-backed function. The `@smithers/agent`
package name, `CodingAgent.make` spelling, MDX integration, provider adapters,
and durable turn API shown on this page remain proposed and are not locked.

Compiled Flows are passable through the Bun-only programmatic `flowTool(...)`
adapter. Each call derives an execution id from the turn, accepted source,
function/ordinal, Flow/Plan identity, and input digest; replay therefore joins
the same durable execution and adopts already-committed Actions rather than
starting a second run. The attachment row is checked for input/Plan divergence.

The in-repo default model remains `ScriptedModel`. A real
`AnthropicModel implements ModelAdapter` exists under `poc/examples/agent` and
can call the Anthropic Messages API, but it is example-only: examples are
excluded from POC emit, the SDK is a POC dev dependency, and neither the adapter
nor SDK enters the published `smthrs/agent` dependency closure. The sandbox
is still a process-level Deno subprocess, not a VM/container, and nothing is
attested. The agent journal and durable store remain separate databases rather
than one atomic history; rows are digest-verified but neither signed nor
redacted, so call inputs are stored verbatim. Remote Flow workers, deployment
signature verification at the agent seam, and cross-process coordinator
handoff are not exercised.
:::

## Define a Coding Agent

An agent receives a model, prompt, sandbox, and table of callable functions:

```ts
import { CodingAgent, TypeScriptSandbox } from "@smithers/agent"
import CodingPrompt from "./coding-agent.mdx" with { type: "mdx" }

const Coder = CodingAgent.make({
  model,
  prompt: CodingPrompt,
  sandbox: TypeScriptSandbox.make({
    timeout: "30s",
    memory: "512mb",
  }),
  functions: {
    readFile: ReadFile,
    editFile: EditFile,
    build: Build,
  },
})

const result = (await Coder.run({ task }))!
```

The `functions` object is the generated program's complete authority surface.

## Generated Programs

On each turn, the model writes ordinary TypeScript with one entry point:

```ts
export default async function turn(functions: Functions) {
  const source = await functions.readFile({ path: "src/index.ts" })
  return functions.build({ source })
}
```

`Functions` is generated from the supplied Action, Flow, and callback signatures. Type-checking catches invalid calls before the sandbox runs the program.

## Turn Lifecycle

The library:

1. renders the MDX prompt and turn state
2. invokes the model and extracts TypeScript
3. checks the source against the generated callable surface
4. optionally returns diagnostics for repair
5. executes accepted code in the sandbox
6. records results and observations
7. continues or returns the final result

JSON tool calling is an adapter, not the fundamental execution model. A tool is a typed function generated code can call.

## Sandboxing

The sandbox begins without ambient filesystem, network, process, environment, module loading, or host-object access. The host grants authority only by passing a function. The current bounded implementation rejects generated source before base64 transport when it exceeds its configured byte limit, caps JSON traversal by depth and node count before serialization, and revalidates the content-pinned Deno executable and runner before launch.

Removing Node or DOM declarations improves diagnostics, but types are not the security boundary. The runtime sandbox must enforce isolation, resource limits, cancellation, and output bounds.

The backend may use an isolate, worker, process, container, or Wasm runtime as long as it preserves the same authority rule.

## MDX Prompts

The agent package supplies ordinary MDX components:

```mdx
<System>You are a coding agent.</System>

<Context>
  <File path="README.md" />
</Context>

<Task>{task}</Task>
```

The Smithers compiler loads MDX as a typed module. The agent library decides how components become provider messages, attachments, and model-specific payloads.

## Durable Turns

Actions and Flows make durability compositional:

- a model request can be a memoized Action
- compilation can be a deterministic content-cached Action
- sandbox execution can be journaled
- the turn protocol can be a Flow
- passed functions retain their individual recovery policies

Replay reuses the recorded model response and completed calls. Generated code remains ordinary runtime TypeScript; it is not silently wrapped in `durable(...)` or converted into a Flow.

In the programmatic POC, `flowTool({ plan, execute })` (or a compatible
`DurableExecutor`) derives the generated callable signature and wire codec from
the Plan's Flow input/success schemas. It commits a call-site attachment, starts
or joins the derived execution id, and records only terminal outcomes. If a
coordinator interruption escapes without a terminal commit, the call is not
recorded as completed; replay reattaches to the same execution instead. A
completed recorded Flow call is served from the agent journal without touching
the executor. Per-site identity is function name plus ordinal, so the proof is
stable for straight-line generated code and does not solve data-dependent loop
call-site identity.

## Building a Custom Agent

The library should expose replaceable primitives for prompt rendering, model invocation, state, source extraction, diagnostics, sandbox creation, function binding, observations, stopping, and optional durable adapters.

A custom agent composes those parts. It does not need to reimplement a hidden loop or adopt one model vendor's tool-call protocol.
