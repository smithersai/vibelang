# Capabilities & Layers [Make dependencies visible and provide them by scope]

Smithers models a dependency as a capability in a compiler-tracked requirement channel. A Context class defines and accesses a service; a base Layer packages an already acquired implementation into an environment.

## Define a Capability

```ts
import { Context } from "smthrs/context"

abstract class Mailer extends Context {
  abstract send(message: Message): Result<Receipt, MailError>
}
```

The class is both the service contract and its nominal key. Two Context subclasses with identical methods remain distinct capabilities.

## Use a Capability

```ts
function welcome(user: User): Result<Receipt, MailError> {
  const mailer = Mailer.context()
  const clock = Clock.context()
  const message = Message.welcome(user, clock.now())
  return mailer.send(message)
}
```

The inherited `context()` call returns the instance and adds the class to the enclosing function's inferred requirements. `welcome` requires `Mailer | Clock`.

## Requirement and Result Composition

```ts
function register(
  input: Signup,
): Result<User, CreateUserError | MailError> {
  const users = Users.context()
  const user = users.create(input)!
  welcome(user)!
  return user
}
```

The compiler propagates `Users`, `Mailer`, and `Clock` through the ordinary calls. `!` propagates the Error variants; these are separate from the requirement channel.

## Build and Provide a Layer

```ts
import { Layer } from "smthrs/provider"

const Production = Layer.merge(
  Layer.succeed(Clock, SystemClock),
  Layer.succeed(Mailer, new SesMailer(credentials)),
  Layer.succeed(Users, new PostgresUsers(databaseUrl)),
)

Layer.provide(Production, async (): Promise<Result<string, RegisterError>> => {
  const user = (await registerAsync(input))!
  return user.id
})
```

The explicit return annotation is required, not decorative, and this is the
easiest rule on the page to trip over. **Any** `Layer.provide` callback that can
fail — whether it propagates with `!`, throws, or is `async` — must spell its
`Result<A, E>` or `Promise<Result<A, E>>` return type. Leaving it to inference is
refused with `SMITHERS2105`, "fallible `Layer.provide` callbacks need an explicit
`Result` (or `Promise<Result>`) contract so the provided computation keeps its
failure channel". Only a callback with an empty failure row may go unannotated.

A base layer is conceptually `Layer<Provides>`. It provides service instances; it does not acquire them or own their lifetime. A missing dependency is a compile error when the closure is known — with one recorded exception: a **subclass** of a capability class is assignable to `typeof Capability` but carries a different nominal key, so such a program can check clean and panic at run time. That is [an open question](/reference/capabilities), not a rule this page can state.

Acquire resources in ordinary code and make cleanup explicit with `using` before constructing the Layer. Resource-building conveniences may be added later, but they are not part of the base Layer contract.

## Test With Layers

```ts
const Test = Layer.merge(
  Layer.succeed(Clock, TestClock.at("2026-08-20T12:00:00Z")),
  Layer.succeed(Mailer, RecordingMailer.make()),
  Layer.succeed(Users, InMemoryUsers.empty()),
)

Layer.provide(Test, (): Result<User, RegisterError> => {
  const user = register(fixture)!
  expect(RecordingMailer.sent).toHaveLength(1)
  return user
})
```

No module replacement or global clock patch is needed.

## Platform Capabilities

```ts
function loadConfig(): Result<AppConfig, FileError | InvalidAppConfig> {
  const fs = FileSystem.context()
  const text = fs.readTextSync("app.json")!
  return parseAppConfig(text)
}
```

Node, Bun, Deno, browser, edge, and tests can provide different implementations of the same platform contracts.

The standard platform roster includes `Clock`, `Random`, `Console`,
`Environment`, `FileSystem`, and `HttpClient`. I/O methods return
`Promise<Result<A, E>>`; operations that have a legitimate synchronous host API
may also expose an explicit `Sync` variant.

:::warning Not importable from `.sm` yet — measured 2026-08-28
The samples on this page declare their own capabilities, which is why they
compile. Reaching the shipped roster instead — `import { FileSystem } from
"smthrs/platform"` — is refused with `SMITHERS1510`, "foreign module
initialization can panic before a checked call boundary", because only six
specifiers are compiler-owned: `smthrs/context`, `smthrs/provider`,
`smthrs/schema-runtime`, `smithers:exceptions`, `smithers:comptime`, and
`smithers:flows`. Every other `smthrs/*` subpath is ordinary foreign code to the
frontend. The roster is real and works under plain `node`; it is not yet
reachable from authored Smithers.
:::

## Scope and Lifetime

`Layer.provide(layer, body)` keeps only the dependency environment active until `body` and the Promise returned by `body` settle. It does not discover, supervise, cancel, or join other Promise work. Every Promise started in authored `.sm` must be awaited directly or consumed by a recognized combinator whose returned Promise is itself consumed; detached work is unavailable.

You do not have to arrange that scope by hand. `Layer.provide` installs a handler
that answers the capability requests inside `body`, and the handler holds the
environment on its own stack rather than in ambient storage, so an environment
cannot outlive the computation it scopes — no revocation step, settlement hook,
or Promise-provenance rule is needed. Any Promise the body returns is fine, and
hosts that cannot observe Promise settlement synchronously are fully supported.
This is a lifetime boundary, not task ownership. See
[Effects](/specification/effects) §Extent Is Structural.

:::note Direction
Merge and nested-override precedence, cycle diagnostics, and
requirement-environment lowering remain under design. Source semantics do not
depend on whether the compiler uses hidden parameters or a scoped environment.
:::
