# Durable Execution [Describe a static Plan, inspect it, then admit durable work]

An **Action** declares a typed operation. A **Flow** connects those operations.
A **Plan** records their graph, keys, effects and approval digest before work
runs. The compiler derives this data from checked `.vibe` source; it never
executes your Flow or its callbacks to discover the graph.

This is the current [durable contract](/specification/durable-execution).
The [ordinary-body replay guide](/guide/history/durable-replay) is retained as
history, not an alpha-0 tutorial.

:::warning[What is delivered today]
The Go compiler, native keyed Plan inspection, source/provider authentication
and Node/Bun worker are implemented. `vibe plan` uses the keyed path by default.
Conditional expressions publish both arms and have a local demand-controlled
worker adapter. A packaged scheduler/Control/journal host, bounded-round drivers,
history administration and the remaining `compile`/`run` default migration
are unfinished. A valid Plan is not approval or evidence that any Action ran.
:::

## Describe and Inspect a Plan

Create these three files together. This is a complete inspection example;
the documentation gate runs it through the actual `vibe plan` command.

```ts [build.vibe] plan=docs/build
import { Action, durable } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const Build = durable((input: number) => {
  const first = Double.run(input + 1)!
  const second = Double.run(input)!
  return { first: first * 2, second }
})
```

```json [input.json]
41
```

```json [providers.json]
[
  {
    "actionId": "build.vibe#Double",
    "implementationId": "double/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

```bash
vibe plan build.vibe --input input.json --providers providers.json \
  --planId docs/build --outFile build.plan.json --format json
```

The two Action nodes are independent; the result consumes both. The arithmetic
is checked Plan data, not JavaScript executed by the planner. `!` carries the
typed Result boundary; it does not read an Action's future answer during
compilation.

The repeated `a` digest above is a placeholder **inspection claim**, not a
provider bundle. Calling an implementation “sealed” does not prove it is
hermetic. Executable deployment must bind real checked implementation bytes,
codecs, runtime/boundary policy and authority. Restoration against signed
artifacts rejects a Plan that names fabricated provider bytes.

The compiler infers Action codecs from the function signature. The provider
file chooses an implementation and policy; it is not a second source of Action
types and cannot grant itself trust or approval.

The output file contains native canonical Plan bytes plus a newline. Malformed
input, duplicate JSON fields, missing providers, unsupported source and output
collisions refuse without replacing a prior artifact. Source, dependency,
input/provider files and aliases are protected. See [CLI — Plan](/reference/cli#plan)
for source-root, export-selection, version and resource-limit options.

## Static Fan-Out

Known input collections can describe a bounded graph. The key function provides
each item's stable address; duplicate or unrepresentable keys refuse.

```ts [map.vibe] plan=docs/fanout
import { Action, durable, fanOut } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const MapValues = durable((input: readonly number[]) => {
  return fanOut(input, n => n, (n: number): Result<number, never> => {
    return Double.run(n)!
  })
})
```

```json [input.json]
[3, 5]
```

```json [providers.json]
[
  {
    "actionId": "map.vibe#Double",
    "implementationId": "double/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

```bash
vibe plan map.vibe --input input.json --providers providers.json \
  --planId docs/fanout --format json
```

This publishes per-item work and its join. It does not dispatch the provider or
print its answers. A collection whose size depends on an unresolved Action
answer needs the bounded-round driver; it is not discovered by running the
source callback. That driver is not yet delivered.

## Conditional Work

Conditional expressions describe a complete graph without reading a planned
answer during compilation. Both alternatives require their provider declarations,
even when the invocation input makes the condition obvious.

```ts [choose.vibe] plan=docs/branch
import { Action, durable } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const Choose = durable((input: number) => {
  return input > 0 ? Double.run(input) : Double.run(-input)
})
```

```json [input.json]
-3
```

```json [providers.json]
[
  {
    "actionId": "choose.vibe#Double",
    "implementationId": "double/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

```bash
vibe plan choose.vibe --input input.json --providers providers.json \
  --planId docs/branch --format json
```

The graph contains a boolean condition, both Action alternatives, their joins
and the final result. Execution demands only the selected alternative. A failed
condition or selected Action does not try the other arm. Nested conditionals,
source child Flows and their static fan-out compositions retain this behavior.
Explicit `sequential` barriers still gate the selected descendants; an unrelated
later Action is not ordered merely because it appears after a conditional.

The current worker's `createControl()` and `executeControlled(...)` methods
provide local demand reservations. Its eager `execute(...)` method refuses a
branch graph. Reservations are not approval, journal receipts or durable attempt
ownership; the admitted host must commit or adopt an outcome before acknowledging
it, and interrupt/drain outstanding work on cancellation. This conditional path
does not yet have a packaged durable host.

Dynamic rounds and effect-conflict edges that cross an arm still refuse pending
their adapters. The compiler never removes an
approval-relevant edge to make a graph run.

### Statements and Early Returns

Ordinary `if` statements, lexical blocks and immutable `const` bindings can
describe the same conditional graph. A return skips the remaining statements
on that path. An `if` uses ordinary TypeScript truthiness; it does not require
its source condition to have type `boolean`.

```ts [guard.vibe] plan=docs/guard
import { Action, durable } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const Guard = durable((input: number | null) => {
  if (input === null) return 0
  return Double.run(input)
})
```

```json [input.json]
null
```

```json [providers.json]
[
  {
    "actionId": "guard.vibe#Double",
    "implementationId": "double/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

```bash
vibe plan guard.vibe --input input.json --providers providers.json \
  --planId docs/guard --format json
```

The Go checker's input narrowing is preserved, including discriminated object
unions. A guarded field is read only when its arm executes; building both arms
does not read a field absent from the other input variant. The example still
publishes and validates `Double` even though this input selects the early return.

An Action statement must consume its Result with `!`; discarding its success
does not discard the work or its failure. Branches which fall through do not
order unrelated following Actions. Use explicit `sequential` where ordering is
required. The existing conditional `const` declaration form retains its native
scope across the entire `if`/`else` construct, but not after it.

All paths must return an encodable value. Unreachable statements after an
unconditional return, ordinary mutation/loops, `switch`, and exception/cleanup
statements still refuse in this graph profile. Structural expansion is bounded;
an exceeded budget refuses rather than publishing a partial graph.

### Short-Circuit Expressions

`&&`, `||` and `??` use the same selected-work protocol when the right operand
contains an Action, child Flow or static fan-out. The left operand is evaluated
first; its Action work is not repeated. The operator returns the selected
operand, not a boolean coercion: `0 ?? action!` retains zero, whereas
`0 || action!` selects the Action. Both paths are published before approval.

```ts [fallback.vibe] plan=docs/fallback
import { Action, durable } from "vibelang:flows"

abstract class Double extends Action<
  (input: number) => Result<number, never>
> {}

export const Fallback = durable((input: number | null): Result<number, never> => {
  return input ?? Double.run(21)!
})
```

```json [input.json]
null
```

```json [providers.json]
[
  {
    "actionId": "fallback.vibe#Double",
    "implementationId": "double/v1",
    "implementationDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "tier": "sealed",
    "effects": { "boundaryMode": "hard", "reads": [], "writes": [] },
    "layers": [],
    "capabilities": []
  }
]
```

```bash
vibe plan fallback.vibe --input input.json --providers providers.json \
  --planId docs/fallback --format json
```

This publishes the fallback work; it does not execute `Double`. The current
durable value contract admits `null`, not `undefined`. A selected failure or
defect remains that channel; it cannot become a falsy value that selects another
operand. The same provider validation and host-delivery limits above apply.

## Ordinary Loops Are Not Plan Construction

The following complete example deliberately refuses under `vibe plan`:

```ts [loop.vibe] plan=docs/refused-loop expect=refuse
import { durable } from "vibelang:flows"

export const Sum = durable((input: number) => {
  let total = 0
  for (let index = 0; index < input; index++) total += index
  return total
})
```

```json [input.json]
3
```

```json [providers.json]
[]
```

Ordinary functions outside a Flow may still use ordinary loops and mutation.
Inside a Flow, use supported graph composition. A passing legacy `vibe check`
or body-emission test is not evidence that this is an accepted keyed Plan.

Similarly, runtime/mutable captures and module initialization cannot be used
to discover graph state. The compiler must not keep an initializer while
silently deleting the mutation that gives it meaning.

## From Inspection to Execution

The public `vibelang/compiler` surface provides
`getNativeCompiler().compileKeyedPlanSource(...)` and
`keyedPlan({ operation: "verify", inputJson })`. They use the same Go engine as
the CLI. Original JSON text is intentional: parsing it first could discard
duplicate-key or number evidence before validation.

The `vibelang/durable` surface separately provides source/provider build,
`buildKeyedSourceDeployment`, signing/authentication,
`compileAuthenticatedKeyedInvocation`,
`restoreAuthenticatedKeyedInvocation`,
`keyedInvocationApprovalTarget` and
`createAuthenticatedKeyedNodeWorker`.

Those are different boundaries:

1. Check and build actual source/provider/runtime artifacts.
2. Authenticate them against separately supplied trust roots.
3. Compile or restore the exact input-bound Plan.
4. Authorize its complete invocation in Control's durable transaction.
5. Let the admitted scheduler drive ready nodes through the authenticated worker.

The worker API is an execution seam, not a standalone admission service.
A plain copied object cannot forge its authentication proof. A graph digest
cannot stand in for the full approval target, which also binds input,
deployment and the authority envelope.

Installed Node/Bun package tests cover inspection through the real CLI,
signed restoration and actual worker execution. An isolated composition with
the reviewed runtime also covers approval, independent work and a real process
kill followed by resume without repeating committed work. It is not yet the
packaged production host. The historical body demo tests a different model.

## Resume, Replay and Reuse

Resume continues the same execution, reusing committed outcomes and allowing
eligible unfinished work to run. It does not run the original Flow function
again. A crash between an external effect and its local commit can still repeat
the request; external idempotency or fencing remains necessary.

Time-travel replay only reads and folds a committed prefix. It never dispatches
Actions. Journal frames contain `lineageId` and `seq`, not source-site occurrence
counters. Fork creates a child lineage; copying parent attempts does not prove
run-dependent keys apply in that child.

Only eligible `sealed` work can share cached results across runs.
`compensable` and `irreversible` are recovery tiers, not shared-cache grants.
Neither a successful old body demo nor a copied journal is proof of these
new-runtime lifecycle guarantees.

## Compatibility and Remaining Work

Historical Manifest inspection remains explicit:

```bash
vibe plan source.vibe --profile manifest-compat --bindings actions.json
```

Its `actions.json` contract is the historical one, not the keyed providers
array above. It does not publish a keyed graph and cannot substitute for a
refused Plan. The old body's eager execution, loops, source-site journals and
handle APIs remain documented only in the linked historical guide.

The remaining work is runtime delivery and admission, durable branch hosting,
round and other
suspension adapters, history operations, provider/capability binding surfaces and
full product-default reconciliation. Cleanup-completion precedence is a separate
open language decision. These are incomplete obligations, not exclusions that
make alpha-0 complete.
