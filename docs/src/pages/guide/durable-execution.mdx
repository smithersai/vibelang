# Durable Execution [Compile selected programs into typed, resumable plans]

Durable execution is opt-in. An **Action** defines a closed persistence boundary, and a **Flow** turns Action calls into a statically analyzable plan.

:::warning Design draft
The Action and Flow model is accepted. A bounded compiler-owned
`durable(...)` lowerer, canonical Plan/manifest validation, SQLite executor,
local Deno worker, and signed local coordinator-admission path are executable
under `vibelang/durable/*`. That lowerer now covers conditionals, durable
timers, one typed external signal, keyed fan-out with bounded multi-step bodies,
explicit `sequential(...)` ordering, a budgeted `loopWhile(...)` round template,
and — in the programmatic POC only, not through the CLI — attached child Flows.
The Bun executor also has provisional `start`/`resume` execution handles,
HMAC-token-gated signal delivery, and post-COMMIT wakeup notifications backed
by a correctness-preserving persisted-state sweep.
General lowering, emitted worker bundles, remote workers, and native/Wasm
deployment are not implemented. Provider spelling, stable IDs, general loop
semantics, wire encoding, and deployment APIs remain under design, and the
control and handle spellings above are provisional.
:::

## Define an Action

An Action closes over one function signature:

```ts
abstract class Compile extends Action<
  (input: CompileInput) => Result<CompileOutput, CompileError>
> {}

abstract class Package extends Action<
  (input: PackageInput) => Result<Artifact, PackageError>
> {}
```

The compiler derives the input, success, and Error codecs from those types. The author does not repeat schemas in an Action constructor.

Action values crossing a persistence or machine boundary must satisfy `Durable<T>`. Plain data derives this automatically. Functions, process handles, and other ephemeral values require an explicit durable representation or are rejected.

## Build a Flow

Import the compiler-recognized `durable` function and pass it a statically resolvable function:

```ts
import { durable } from "vibelang:flows"

const Build = durable(function Build(
  input: BuildInput,
): Result<Artifact, CompileError | PackageError> {
  const compiled = Compile.run({ source: input.source }).unwrap()
  return Package.run({ code: compiled.code })
})
```

`durable` is ordinary call syntax, not a keyword. The compiler recognizes its resolved import identity, so aliases work and an unrelated function named `durable` remains ordinary. An inline function, declaration, or function-valued constant is accepted when the compiler can resolve it statically; a runtime-selected callback is rejected.

The compiler lowers the function's checked syntax, control flow, and data flow. It does not invoke the function with proxy values. `Compile.run` becomes an Action node and a typed symbolic value. Accessing `compiled.code` creates a projection, and passing that value to `Package.run` creates a data edge. No Action implementation runs during compilation or planning.

The durable source function disappears after compilation. The emitted template contains the plan, codecs, inferred failures and requirements, stable identities, and debug map.

## Compilation Phases

Durable programs have four distinct phases:

1. **Template compilation** statically lowers the durable function into target-neutral Plan IR without invoking it.
2. **Deployment build** resolves providers, checks the dependency closure, and partitions coordinator and worker artifacts.
3. **Plan/preview** reads emitted Plan IR, validates and optionally specializes known input, and reports the graph without loading the durable function or dispatching Actions.
4. **Execution** creates or resumes a durable run and dispatches eligible Action nodes from the Plan IR.

Keeping the phases separate allows one plan to deploy across TypeScript, native, and Wasm workers. If a branch or runtime-sized fan-out cannot be resolved from preview inputs, plan mode reports the conditional or parameterized template instead of executing source code to guess its shape.

The bounded POC can wrap the exact validated Plan and deployment manifest in a
canonical, domain-separated Ed25519 envelope. Verification uses public keys
supplied out of band and produces an opaque process-local proof; the
authenticated coordinator entry point requires that proof before creating a
worker transport. Only a pool signed as `in-process-poc` can use the implicit
local worker. Every other sandbox name requires an opaque host-issued transport
token for that exact name, and all pools are checked before any factory runs.
This authenticates manifest provenance and every digest it pins. It does not
attest a live callback's lexical closure or emitted bundle,
provide freshness/anti-rollback or revocation, or prove what a remote worker
loaded. The transport token prevents accidental downgrade; the host is still
trusted to issue it only for a factory that enforces the declared sandbox.

## Provide Implementations

Actions are abstract capabilities. Layers install ordinary function implementations and their policies:

```ts
import { Action, Layer } from "vibelang/provider"

const BuildActions = Layer.merge(
  Action.provide(Compile, compileWithEsbuild, {
    recovery: Action.idempotent,
    reuse: Action.content,
  }),
  Action.provide(Package, packageArtifact, {
    recovery: Action.idempotent,
    reuse: Action.execution,
  }),
)
```

The abstract Action owns the durable contract. A deployment layer chooses its implementation, placement, resource limits, and recovery policy.

## Control Flow in Plans

Branches on comptime values reduce normally. Branches on Flow input or Action output emit plan nodes and compile both arms:

```ts
import { durable } from "vibelang:flows"

const Release = durable(function Release(
  input: ReleaseInput,
): Result<Deployment | FailureReport, TestError | DeployError | ReportError> {
  const tested = Test.run({ source: input.source }).unwrap()
  return if (tested.passed) {
    Deploy.run({ artifact: tested.artifact })
  } else {
    ReportFailure.run({ report: tested.report })
  }
})
```

Pure operations on symbolic values become portable expression IR. An operation the IR cannot represent is a compile error; the compiler never runs the source against a fake placeholder.

## Replay and Retry

Every completed Action invocation is journaled for its Flow execution. After a restart, the same execution observes the recorded success or Error Result instead of repeating completed work.

Retry safety is a separate decision:

- **idempotent** work may repeat after an ambiguous crash
- **compensable** work may repeat with an explicit rollback path
- **irreversible** work does not retry after ambiguity

The safe default is execution-local replay with no ambiguous retry unless the implementation declares how repetition is safe.

## Wait for an External Signal

The bounded POC includes a deliberately provisional single-delivery form:

```ts
import { durable, waitSignal } from "vibelang:flows"

const Approval = durable(function Approval(input: { requestId: string }) {
  const decision = waitSignal<{ approved: boolean; ticket: string }>(
    "approval.decided",
  )
  return { requestId: input.requestId, decision: decision }
})
```

The compiler puts the literal signal identity and derived payload schema in the
Plan; the sender does not provide a schema. Execution initialization pins that
contract. A delivery then addresses the exact execution and node, supplies an
idempotency key, and persists one canonical schema-checked payload. A duplicate
of the same key and payload is harmless, while a conflicting key or payload is
rejected. Waiting uses no worker lease, and delivery/consume journal transitions
survive restart and coordinator races. The POC rejects more than 100,000
durable-JSON nodes/own fields before canonicalization and retains the
independent 8 MiB canonical message limit; request identities are separately
byte-bounded before storage.

`waitSignal` and the POC delivery APIs are not final spellings. The Bun POC's
default delivery path requires a `vst1_` HMAC-SHA256 sender token minted by
`executor.grantSignal(executionId, signalId)` and bound to that execution and
signal. Forged, cross-execution, wrong-signal, and foreign-database tokens fail
before execution state is read; tokenless delivery exists only behind explicit
`{ unsafeLocalDelivery: true }`. The HMAC secret lives in the same SQLite
database, so this proves a local-trust gate, not remote identity,
authorization, rotation, or revocation.

Signal delivery, cancellation, failure, and timer scheduling notify local
waiters strictly after COMMIT. That notifier is only a latency optimization: a
coordinator re-reads persisted state at the next timer/deadline boundary or a
bounded fallback sweep (`wakeupSweepMs`, 250 ms by default), so a missed or
cross-process notification cannot change correctness. Remote transport and
authorization, queues/broadcast, schema migration, and final public spellings
remain design work.

## Execution Handles

The Bun programmatic POC exposes the provisional long-running control surface:

- `executor.start(input, { executionId })` starts or resumes work and returns a
  `DurableExecutionHandle` immediately;
- `executor.resume(executionId)` reconstructs a handle from the persisted,
  digest-verified input, including for an already-terminal execution;
- `handle.status()` reads committed status, `handle.result()` awaits the typed
  Flow success or the modeled terminal failure, `handle.cancel(reason?)`
  durably cancels, and
  `handle.signal(signalId, { idempotencyKey, payload })` performs authenticated
  handle-scoped delivery; and
- `executor.execute(...)` remains the start-and-await convenience.

Every method is bound to the handle's execution id; a handle cannot address a
sibling run. This is executable programmatic POC evidence, not a root CLI
command or a locked public API. Remote control transport, public principal
authorization, subscription/history/fork administration, and migration remain
open.

## Memoization and Content Caching

Cross-execution reuse has two meanings:

- **Memoization** records one acceptable result for an explicit key, even when the operation is nondeterministic.
- **Content caching** asserts that complete keyed inputs, implementation, dependencies, and execution semantics reproduce an equivalent result.

These policies are never interchangeable. A memoized model response must not be promoted to a hermetic shared cache entry.

## Planned Distributed Builds

A future deployment build can emit:

- a coordinator artifact
- several tree-shaken worker artifacts
- derived RPC bindings and schemas
- a signed routing manifest

Different worker pools can use TypeScript, native, or Wasm implementations of the same Action. Placement belongs to the deployment layer, so the durable signature stays independent of one machine topology.

## Security Boundary

The Action signature describes data, not authority. Worker implementations receive only their declared providers, and coordinator-to-worker messages are validated against derived codecs.

OS isolation, secret delivery, fencing, artifact storage, and worker attestation remain runtime responsibilities built around the compiler-derived contract.

A manifest signature is an admission check, not sandbox attestation. Production
also needs protected signing-key custody, rotation/revocation and rollback
policy, authenticated transport, and evidence that a worker actually loaded the
authorized artifact.
